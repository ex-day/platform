# ユーザー投稿（Contribution）ユースケース

- 状態：初稿
- 目的：自然な投稿を受け取り、曖昧さを保ったまま必要に応じて解釈・補完・確認し、Discoveryとの関係を検討するためのユースケースを整理する。

## 1. 基本方針

- **投稿体験は短文SNSのように気軽にし、蓄積する情報は再利用できる知識として構造化する。** ユーザーは体験・疑問・知識を自然文や写真などで残せる。場所、日時、Subject、既存Discoveryの選択を一律に必須とせず、構造化の負担を投稿者に押し付けない。
- **情報不足だけを理由にContributionを拒否しない。** 不明な場所や時期そのものが問いになる場合もある。投稿原文・添付資料・出所を保持し、後から補完・関連付けできるようにする。
- AIは自然文等からContext Candidateを抽出し、不足や矛盾を見つける支援を行う。候補の検索や比較には通常のDB検索、地理検索、意味検索も利用し、**必要な場合のみユーザーに確認する**。
- **AIがDiscoveryの内容やContributionとの関係を独断で確定しない。** 投稿者や他の利用者、必要に応じた運営の判断を中心に、既存Discoveryへの関連付け、新しいDiscoveryの成立、保留を扱う。候補の確からしさと投稿内容の事実性は別に考える。
- 投稿された時刻・場所と、Contributionが述べている出来事の時刻・場所を区別する。端末の現在地や写真の撮影場所を、対象場所と自動的に同一視しない。

## 2. 代表ユースケース

### 2.1 フジサンケイビル前のキッチンカー

- 状況：ユーザーが仕事の合間に昼食を買いに外出し、フジサンケイビル前でキッチンカーを見つける。弁当を買い、職場へ戻ってから投稿する。
- 投稿文：「さっきお昼ご飯を買いに外出したらフジサンケイビルの前でキッチンカーが出ていて買ってきたよ」
- 添付資料：キッチンカーの写真。
- 抽出候補：Locationは「フジサンケイビルの前」、Timeは投稿時刻を基準にした「さっき」「昼頃」、Subjectはキッチンカー・昼食など。写真の撮影位置や撮影日時があれば補助材料とする。
- 期待する扱い：本文に対象場所が明示されているため、まずその周辺のDiscovery候補を検索する。写真や端末位置が別の場所を示しても、投稿者が職場に戻ってから投稿した可能性を考慮する。既存Discoveryへの関連付けや新規成立は候補として提示し、人の判断につなげる。出店・販売の情報は観測時点のものとして扱い、現在も営業中だと保証しない。

### 2.2 場所が曖昧なビル入口の疑問

- 投稿文：「ふと疑問に思ったんだけど、このあたりのビルって何で一段高い位置に入り口があるんだろう？」
- 添付資料：ビルの入口の写真。
- 抽出候補：本文の「このあたり」は場所を特定しない。写真に位置メタ情報、建物・看板などの手掛かりがあればLocation候補を作る。許可を得て取得できた端末位置は別の候補として扱う。Subjectは建物の入口や段差、投稿の意味は疑問として捉える。
- 期待する扱い：候補が絞れれば建物や関連Discoveryを提示し、必要に応じて「この建物のことですか？」と確認する。候補が割れる場合は複数提示する。場所を特定できなくても疑問のContributionとして保持し、後から他の利用者による補足や関連付けを可能にする。

## 3. EvidenceとContext Candidate

Evidenceは候補を作る根拠であり、それ単独で対象の事実を確定するものではない。各候補について、どのEvidenceから得たか、対象を示すのか投稿・撮影時点を示すのか、不明な点や食い違いを追えるように考える。

| Evidence | 得られる可能性がある情報 | 留意点 |
| --- | --- | --- |
| 自然文 | 地名・建物名、「さっき」「去年の夏」などの時間表現、話題や疑問 | 指示語や相対表現は文脈と基準時点が必要 |
| 添付資料とメタ情報 | 写真に写る建物・看板、撮影位置・撮影日時など | メタ情報は欠けることがあり、撮影時点・場所が投稿対象と異なることもある |
| 端末Context | 許可を得て利用できる現在地、投稿時刻など | 移動後の投稿では対象の場所・時刻と一致しない |
| ユーザー明示入力 | 指定した地名・地点・日時、候補への回答や訂正 | 投稿時の必須項目にはせず、必要な確認や訂正に利用する |

抽出するContext Candidateの例：

- **Location**：本文の地名・建物名、写真の位置や写り込み、端末位置、ユーザー指定地点から、対象場所の候補を作る。
- **Time**：本文の日時・相対時間、撮影日時、投稿日時、ユーザー指定日時から、出来事の対象時点・期間の候補を作る。投稿日時は「さっき」の基準になり得るが、出来事の日時そのものではない。
- **Season**：本文の「毎年春」「今年の初秋」等や対象期間から、季節・旬・反復時期の候補を作る。Seasonが合うことだけで「今年も始まった」「現在開催中」とは判断しない。
- **Subject**：本文と添付資料の意味から話題の候補を作る。Subject候補としての確からしさと、投稿内容が事実である確からしさを分ける。

## 4. Locationの確定度と食い違い

本文の対象場所を「明確／曖昧・なし」、添付資料の位置手掛かりを「あり／なし」、端末位置を「利用可／不可」で組み合わせる。ここでの「あり」は対象場所を保証せず、複数の根拠がある場合は整合性も評価する。固定の優先順位（例：写真の位置を常に本文より優先）では決めない。

| 本文の場所 | 添付資料の位置 | 端末位置 | 基本的な扱い |
| --- | --- | --- | --- |
| 明確 | あり | 利用可 | 三者が整合すれば対象場所の有力候補。食い違えば各候補の意味を確認する |
| 明確 | あり | 不可 | 整合すれば本文の地点を軸に検索。食い違えば複数候補を保持して確認する |
| 明確 | なし | 利用可 | 本文を対象場所の候補とし、端末位置が移動後の現在地である可能性も考える |
| 明確 | なし | 不可 | 本文から候補を作って検索し、必要なときに確認する |
| 曖昧・なし | あり | 利用可 | 写真と端末から候補を作る。整合しても対象場所か確認し、食い違えば候補を提示する |
| 曖昧・なし | あり | 不可 | 写真から候補を作る。確定できなければ質問または未確定で保持する |
| 曖昧・なし | なし | 利用可 | 現在地や近隣を候補として「この辺りですか？」と確認する。移動中・移動後を考慮する |
| 曖昧・なし | なし | 不可 | 必要なら「どのあたりですか？」と聞き、答えられなければ場所未確定で保持する |

例えば本文が「浜松町周辺」、写真の位置が愛宕、端末位置が新橋の場合、三地点を混ぜて一つのLocationにしない。写真の撮影時刻や投稿文脈を踏まえ、地名または近くの建物・Discovery候補を提示して投稿者に選択・訂正してもらう。端末位置だけが異なる場合も、移動後に投稿した可能性を先に考える。

TimeとSeasonにも同じ考え方を適用する。本文の「昨日」と写真の撮影日時が異なる、例年の旬と今年の観測情報が異なる、といった場合はそれぞれの候補と根拠を残し、対象時点や現在性を安易に確定しない。

## 5. Discovery候補検索とユーザー確認

1. Contributionの原文・添付資料を受け取り、利用可能なEvidenceからLocation / Time / Season / Subjectなどの候補を抽出する。
2. 候補の確定度と相互の整合性を評価する。情報不足や矛盾を検出しても、この段階でContribution自体を捨てない。
3. 候補を使い、通常のDB検索、PostGIS等の地理検索、Vector Search等の意味検索を組み合わせて既存Discoveryや関連するValueを探す。場所の候補が複数なら、それぞれで検索することもできる。
4. 関連先が分かりやすければ候補として示す。複数の場所・Discoveryが考えられる場合は選択肢を示し、候補が得られなければ不足している点だけ短く質問する。建物を見せて尋ねる方が地名を選ばせるより分かりやすい場合もある。
5. 回答や後日の補足を踏まえ、ContributionとDiscoveryの関係を人間中心で判断する。既存への関連付け、新しいDiscoveryの成立、関連はあるが別のDiscovery、保留を区別する。

```text
Contribution（原文・添付資料）
  → Evidence抽出
  → Context Candidate生成（Location / Time / Season / Subject）
  → 確定度・整合性評価
  → DB / PostGIS / Vector SearchによるDiscovery候補検索
  → 必要な場合のみユーザー確認
  → 人間中心の判断による関連付け・新規成立・保留
```

## 6. 未確定Contribution

場所、時間、Subject、関連するDiscoveryを確定できない場合も、Contributionを原文と根拠付きで保持する。未確定であることを明示し、後から投稿者の訂正、他の利用者の回答、新しいEvidenceによって補完・再検討できるようにする。未確定の候補を確定事実のように表示・推薦しない。公開範囲や推薦の扱いは別途設計する。

## 7. 実装時に再検討すること

この文書は投稿体験と判断の原則を示す初稿であり、AIの利用範囲や検索方式を確定しない。実装時には、自然文解析・画像理解・矛盾検出のどこにAIを使うか、ルールや通常検索で代替できる部分、処理コスト、確認頻度、候補の表示方法をMVPの条件に合わせて再評価する。AI利用量を変えても「まず投稿を受け取り、必要な不足情報だけ尋ね、人間が確定する」という体験の原則を保つ。
