# apps/api の作業ルール

このディレクトリは ex-day の API（バックエンド）を置く場所である。ここで作業するエージェントは、ルートの `AGENTS.md` と `docs/development/ai-collaboration.md` に加えて、以下の書き方に従う。ルールの根拠は Issue #89 の「API の土台の技術（決定）」および関連コメントにある。矛盾がある場合は作業を止めて人間に確認する。

## 使う技術

| 項目 | 決定 |
|---|---|
| 言語 | Java 25（LTS） |
| フレームワーク | Spring Boot 4.1 系（最新の安定版） |
| ビルド | Gradle（Kotlin DSL） |
| DB アクセス | Spring の `JdbcClient`（JPA・MyBatis は使わない） |
| テスト | JUnit ＋ Testcontainers（`db/Dockerfile` と同じ構成の PostgreSQL＋PostGIS） |
| Spring Security | 認証（#75）の実装まで**入れない** |

万一動かない部品があれば Java 21（LTS）に下げる（Gradle の指定 1 行）。判断は人間に確認する。

## DB アクセスの書き方

- DB アクセスは Spring の `JdbcClient` を使う。JPA・MyBatis は使わない。
- SQL は Java のテキストブロック（`"""..."""`）で書く。文字列の連結はしない。
- SQL は**クエリ用のクラスの先頭に定数としてまとめる**。メソッドの中はパラメータの受け渡しと結果の詰め替えだけにする。
- **値は必ずパラメータで渡す**。SQL の文字列に値を埋め込まない（SQL の解析・実行計画のキャッシュを効かせ、SQL インジェクションを防ぐ）。
- PostGIS 等の型は、できるだけ SQL の側で数値・文字列に変えて返す（アプリ側で型の対応を持たなくて済むようにする）。

## 読み取りの一貫性と公開制御

PR #152 のレビュー（2026-11-17）で決めた、取得用の API の共通の方針。

- **一般のユーザー向けの読み取りは、公開のビュー（`visible_*`）を通す**（DB 設計 2.5節）。ビューはアクセスの制御そのものではない。運営・本人向けの読み取りは表を直接読み、権限を API で確かめる。
- **1つの応答を複数の SQL で作るときは、`@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ)` の中で読む**。PostgreSQL の REPEATABLE READ では、トランザクションの最初の問い合わせの時点のスナップショットを、すべての問い合わせで使う。そのため、公開のビューで見えた対象の識別子を使って区画を読む間に、別の処理が非公開にしても、区画ごとに公開状態が食い違わない。
- **応答が保証するのは、そのスナップショットの時点の公開状態**とする。読み始めたあとに非公開になったものは、その応答には出ることがあり、次のリクエストから出なくなる。`readOnly` だけではスナップショットはそろわない（既定の READ COMMITTED では、問い合わせごとに時点が変わる）。
- 各 SQL に公開の条件を機械的に重ねない。公開のビューで見えた対象の中身（関わる場所・Value 等）は、同じトランザクションの中で表から読んでよい。ほかの対象を指して返すもの（統合先、会話、企画、関係する Discovery）は、公開のビューで引く。
- 書き込みの API のトランザクションの境界は、書き込みの API を作るときに決める。

## 機能の責務と名前空間

PR #153 のレビュー（2026-11-17）で決めた方針。

- **画面をまたいで使う部品は、独立した機能として切り出す**。ある画面の詳細を組み立てるクラス（例：S03 の `discovery` の Assembler・Queries）に、別の画面のコードから依存しない。
- 切り出した機能は、**クラス名・パッケージ（名前空間）・依存の向きで責務を表す**。共用のものを1つのパッケージ（`shared`・`common` 等）に集めない。
- 画面設計で独立させたコンポーネント（Cxx）・ファンクション（Fxx）の分け方を、実装でも踏襲する。たとえば、Discovery Card（C03）は `card.discovery`、企画カード（C29）は `card.project`、会話カード（C40）は `card.conversation`、わかってきたこと（C25）は `card.finding`、会話の Post（C26）は `card.post` に置き、それぞれの見せ方の決まり（カードの見出しにする場所の決め方等）をそこに持たせる。画面をまたぐドメインの決まり（統合をたどって最後の統合先を決める、場所の推定の値の選び方、場所の会話の範囲等）は、その決まりの名前のパッケージ（`merge`・`estimate`・`placeconversation`・`projectconversation`）に置く。画面に依らない技術の部品（GeoJSON の変換等）は、その技術の名前のパッケージ（`geometry`）に置く。
- **Cxx・Fxx と実装のクラスを機械的に1対1にしない**。実装の段階で新たな共用の部分が見つかることも、設計の時点で想定した機能の分け方が適切でないと分かることもある。そのときは実際の責務で分け方を見直し、必要に応じて設計にも反映する。
- **先回りした抽象化はしない**。1つの画面でしか使わない部品は、その画面のパッケージに置き、2つ目の画面で使うときに切り出す（例：探していますのカード C30 は、今は S13 の `place` に置く）。

## マイグレーション

- API の起動時にマイグレーションを流さない。
- `db/` のマイグレーションは `compose.yaml` の flyway サービスで流す。

## テスト

- DB を使うテストは Testcontainers で書く。使う PostgreSQL＋PostGIS は `db/Dockerfile` と同じ構成にする（本番と同じ拡張で SQL の正しさを確かめられるようにする）。
- 取得用の API のテストは `DbApiTestSupport` を継承する。DB はテストのクラスをまたいで1つを共用し、テストごとにサンプルデータを入れ直す。そのため、**このテストを並列に実行しない**（並列にすると、別のテストの入れ直し・書き換えが混ざる）。並列に実行するときは、テストごとに DB（またはスキーマ）を分ける仕組みを先に作る。

## Spring の使い方

- Spring の暗黙の仕組みを使いすぎない。依存はコンストラクタで渡す等、素直な書き方に寄せる。

## Spring Security

- 認証（#75）の実装まで**入れない**。
- 理由：今回の API はログインなしの読み取りだけ。入れると全 API が既定で認証必須になり、中身のない許可の設定だけが増える。
- いずれ入れるときは、外部の認証サービスのトークンを検証する部品（OAuth2 Resource Server）として使う。

## その他

- OpenAPI（`docs/api/openapi.yaml`）を約束事の正とする。API 側のインターフェースと、画面側（TypeScript）の型は、OpenAPI から生成する方針（#89）。
- 「今」と「いる場所」は開発用の設定ファイルで指定できるようにする（#89 のコメント参照）。値は API 側で読む。
