# ユーザー投稿（Post）ユースケース

- 状態：第2版（DEC-0005〜DEC-0010との整合のため改訂。Issue #67）
- 目的：自然な投稿（Post。画面では「声」）を受け取り、曖昧さを保ったまま投稿後の会話の解析で理解を深め、Discoveryとの関係を検討するためのユースケースを整理する。
- 用語：ドメイン上の「Contribution」は[DEC-0008](../decisions/DEC-0008-rename-contribution-to-post.md)により「Post」へ改称した。ファイル名（`user-contribution-usecases.md`）は変えていない（改称の要否はIssue #67に判断待ちとして記録）。
- 概念の定義は[ドメイン設計](../ex-day_domain_model.md)2.1・3.3・3.5・4.3〜4.6節を正とする。

## 1. 基本方針

- **投稿体験は気軽にし、蓄積する情報は再利用できる知識として構造化する。** ユーザーは体験・疑問・知識を自然文や写真などで話せる。疑問／知識等の型を選ばせず（DEC-0005 決定1）、場所、日時、Subject、既存Discoveryの選択を投稿時に求めない。構造化の負担を投稿者に押し付けない。
- **場所・時期等はPostの属性にしない。** 場所・時期・分類・Valueといった構造化されうる情報と、写真・資料の提供はDiscovery（成立前を含む）に帰属させる（DEC-0005 決定8）。以下の「候補」は、1件のPostに付ける属性ではなく、会話から読み取る話題（Topic）・発見の仮説（DiscoveryHypothesis）の中身である（DEC-0009 決定3・5）。
- **情報不足だけを理由に投稿を拒否しない。** 不明な場所や時期そのものが問いになる場合もある。投稿原文・資料・出所を保持し、後から補完・関連付けできるようにする。
- **投稿してから解析する。** 投稿は解析の完了や候補の確認を待たずに成立する（DEC-0005 決定7）。入力中にAIによる解析・対話は行わない（DEC-0003）。投稿前の確認画面は設けない（旧S11（知識・疑問登録確認画面）は廃止した）。解析は[F02（投稿後の会話の解析）](functions/F02-conversation-analysis.md)が投稿後に行う。
- **単一の投稿を確定情報へ変換しない。** 手がかりは複数の発言にまたがって蓄積・組み合わせ、話題・発見の仮説・わかってきたこととして育てる（DEC-0005 決定9、DEC-0009）。矛盾する解釈は、複数の仮説・説として並べてよい。
- **AIがDiscoveryの内容やPostとの関係を独断で確定しない。** 突き合わせの結果は提案（Proposal）として出し、判断を経て採用・却下する（DEC-0009 決定7）。候補の確からしさと投稿内容の事実性は別に考える。成立の判断責任をユーザーに負わせない（DEC-0006 決定3）。
- **会話の重複は歓迎し、Discoveryの乱立は避ける。** 投稿前に既存の同じ問い・話を確かめさせない。投稿直後に似たDiscoveryとわかってきたことを示し、既存の会話に加わる選択肢を示す。同一かどうかの判断と統合は投稿後に行う（DEC-0010 決定1）。
- 投稿された時刻・場所と、Postが述べている出来事の時刻・場所を区別する。端末の現在地や写真の撮影場所を、対象場所と自動的に同一視しない。

## 2. 代表ユースケース

### 2.1 フジサンケイビル前のキッチンカー

- 状況：ユーザーが仕事の合間に昼食を買いに外出し、フジサンケイビル前でキッチンカーを見つける。弁当を買い、職場へ戻ってからヘッダーの「話す」で新しい話を始める（C27（新しい話を始める））。
- 投稿文：「さっきお昼ご飯を買いに外出したらフジサンケイビルの前でキッチンカーが出ていて買ってきたよ #キッチンカー」
- 資料：キッチンカーの写真（器となる成立前のDiscoveryへ提供される）。
- 投稿時：本文と写真だけで投稿が成立する。タグは本文中に「#」で付け、「#」のあとの補完で既存のタグを選べる。付けた#タグは入力欄の中でも投稿後も同じ見た目で強調される（[F04（タグの補完）](functions/F04-tag-suggest.md)）。場所・時期の入力は求めない。
- 投稿直後：似たDiscovery（同じ場所のキッチンカーの話等）があれば、そのわかってきたこと（例：価値「平日の昼にキッチンカーが並ぶ」）とともに示す（[F03（似たDiscoveryの案内）](functions/F03-similar-discovery-guide.md)）。加わるかどうかはユーザーが選ぶ。
- 投稿後の解析：話題の発見の仮説として、場所の候補「フジサンケイビルの前」、時の候補「投稿時刻を基準にした昼頃」、Subjectの候補（キッチンカー・昼食など）を持つ。写真の撮影位置や撮影日時があれば補助材料とする。本文に対象場所が明示されているため、その周辺の既存Discoveryと突き合わせる。写真や端末位置が別の場所を示しても、投稿者が職場に戻ってから投稿した可能性を考慮する。既存Discoveryとの同一・類似は提案として出し、判断を経る。出店・販売の情報は観測時点のものとして扱い、現在も営業中だと保証しない。

### 2.2 場所が曖昧なビル入口の疑問

- 投稿文：「ふと疑問に思ったんだけど、このあたりのビルって何で一段高い位置に入り口があるんだろう？」
- 資料：ビルの入口の写真。
- 投稿時：問いのまま投稿が成立し、問いを起点とした成立前のDiscovery（器）が生まれる。問いはわかってきたことに含めない（DEC-0009 決定4）。
- 投稿後の解析：本文の「このあたり」は場所を特定しない。写真に位置メタ情報、建物・看板などの手掛かりがあれば、発見の仮説の場所の候補を作る。許可を得て取得できた端末位置は別の候補として扱う。Subjectの候補は建物の入口や段差とする。
- 会話が進むと：別の参加者の声（「水害対策では？」「昔ここに〇〇があった名残では？」）から、解釈の異なる複数の発見の仮説と、わかってきたこと（説）が並ぶ。対立する説は無理に一つにまとめない。説へのリアクション（「そうかも」）を正しさの証拠にしない（DEC-0009 決定9）。場所を特定できなくても問いのPostとして保持し、後から他の利用者による補足や、既存Discoveryとの関連の提案を可能にする。

## 3. EvidenceとContext Candidate

Evidenceは候補を作る根拠であり、それ単独で対象の事実を確定するものではない。各候補について、どのEvidenceから得たか、対象を示すのか投稿・撮影時点を示すのか、不明な点や食い違いを追えるように考える。候補は話題の発見の仮説（場所・Subject・価値等）の材料であり、Postの属性として保存しない（DEC-0009 決定5）。Post単位の抽出結果は、解析の内部データ（キャッシュ）として扱ってよい。

| Evidence | 得られる可能性がある情報 | 留意点 |
| --- | --- | --- |
| 自然文 | 地名・建物名、「さっき」「去年の夏」などの時間表現、話題や疑問 | 指示語や相対表現は文脈と基準時点が必要 |
| 資料とメタ情報 | 写真に写る建物・看板、撮影位置・撮影日時など | メタ情報は欠けることがあり、撮影時点・場所が投稿対象と異なることもある |
| 端末Context | 許可を得て利用できる現在地、投稿時刻など | 移動後の投稿では対象の場所・時刻と一致しない |
| タグ・Post間の参照 | ユーザーが付けた表示するタグ、返信先等 | タグは重み付けされた入力として扱い、判断そのものにしない（DEC-0007 決定10）。返信等の参照は話題の推定で優先して使う |
| 会話の他の声 | 別の参加者の補足・回答・資料 | 単一の声から確定しない。1人の参加者の1つの発言だけからは確定候補・派生候補にしない（DEC-0009 決定7） |

抽出するContext Candidateの例：

- **Location**：本文の地名・建物名、写真の位置や写り込み、端末位置から、対象場所の候補を作る。
- **Time**：本文の日時・相対時間、撮影日時、投稿日時から、出来事の対象時点・期間の候補を作る。投稿日時は「さっき」の基準になり得るが、出来事の日時そのものではない。
- **Season**：本文の「毎年春」「今年の初秋」等や対象期間から、季節・旬・反復時期の候補を作る。Seasonが合うことだけで「今年も始まった」「現在開催中」とは判断しない。
- **Subject**：本文・資料・タグの意味から話題の候補を作る。Subject候補としての確からしさと、投稿内容が事実である確からしさを分ける。

## 4. Locationの確定度と食い違い

本文の対象場所を「明確／曖昧・なし」、資料の位置手掛かりを「あり／なし」、端末位置を「利用可／不可」で組み合わせる。ここでの「あり」は対象場所を保証せず、複数の根拠がある場合は整合性も評価する。固定の優先順位（例：写真の位置を常に本文より優先）では決めない。

| 本文の場所 | 資料の位置 | 端末位置 | 基本的な扱い |
| --- | --- | --- | --- |
| 明確 | あり | 利用可 | 三者が整合すれば対象場所の有力候補。食い違えば複数の候補として保持する |
| 明確 | あり | 不可 | 整合すれば本文の地点を軸に突き合わせる。食い違えば複数候補を保持する |
| 明確 | なし | 利用可 | 本文を対象場所の候補とし、端末位置が移動後の現在地である可能性も考える |
| 明確 | なし | 不可 | 本文から候補を作って突き合わせる |
| 曖昧・なし | あり | 利用可 | 写真と端末から候補を作る。整合しても対象場所とは断定しない |
| 曖昧・なし | あり | 不可 | 写真から候補を作る。確定できなければ未確定で保持する |
| 曖昧・なし | なし | 利用可 | 現在地や近隣を弱い候補とする。移動中・移動後を考慮する |
| 曖昧・なし | なし | 不可 | 場所未確定で保持し、会話の他の声による補足を待つ |

例えば本文が「浜松町周辺」、写真の位置が愛宕、端末位置が新橋の場合、三地点を混ぜて一つのLocationにしない。写真の撮影時刻や投稿文脈を踏まえ、複数の候補として保持する。端末位置だけが異なる場合も、移動後に投稿した可能性を先に考える。

TimeとSeasonにも同じ考え方を適用する。本文の「昨日」と写真の撮影日時が異なる、例年の旬と今年の観測情報が異なる、といった場合はそれぞれの候補と根拠を残し、対象時点や現在性を安易に確定しない。

## 5. 投稿後の解析と既存Discoveryとの突き合わせ

1. Post（原文・資料・タグ・返信先）を受け取り、投稿を成立させる。解析の完了を待たない。
2. 新しい話を始める投稿の場合は、投稿直後に似た既存のDiscoveryとわかってきたことを示す（F03（似たDiscoveryの案内））。投稿を止めず、加わるかどうかはユーザーが選ぶ（DEC-0010 決定1）。
3. 「既存の話題の要約＋新しいPost」を入力に、話題・発見の仮説・わかってきたことを作成・更新する（F02（投稿後の会話の解析））。利用可能なEvidenceからLocation / Time / Season / Subjectなどの候補を仮説の中身として持つ。情報不足や矛盾を検出しても、Post自体を捨てない。
4. 発見の仮説を既存のDiscoveryと突き合わせる。通常のDB検索、PostGIS等の地理検索、Vector Search等の意味検索を組み合わせてよい。
5. 候補にする判断材料（中身の成熟・人の支え・時間の安定）を満たしたものを提案（補完・新しいValueの追加・関連・派生・同一）として出し、判断を経て採用・却下する（DEC-0009 決定7）。判断の時点で根拠のPostを判断記録に固める（DEC-0009 決定1）。

```text
Post（原文・資料・タグ・返信先）
  → 投稿の成立（解析を待たない）
  → 投稿直後の似たDiscoveryの案内（新しい話の場合）
  → 話題・発見の仮説・わかってきたことの作成・更新（Evidence → Context Candidate）
  → DB / PostGIS / Vector Searchによる既存Discoveryとの突き合わせ
  → 提案 → 判断（採用・却下）と根拠の固定
```

投稿者本人に場所等を尋ねる確認（「この建物のことですか？」等）を投稿後に行うかどうか、行う場合の見せ方は未確定とする（Issue #67に判断待ちとして記録）。現時点では、曖昧さは複数の仮説として保持し、会話の他の声による補足で絞り込むことを基本とする。

## 6. 未確定のまま保持するPost

場所、時間、Subject、関連するDiscoveryを確定できない場合も、Postを原文と根拠付きで保持する。未確定であることを明示し、後から投稿者の訂正、他の利用者の声、新しいEvidenceによって補完・再検討できるようにする。未確定の候補を確定事実のように表示・推薦しない。わかってきたことは見立てであることが分かる見せ方とする（C25（わかってきたこと））。公開範囲や推薦の扱いは別途設計する。

## 7. 実装時に再検討すること

この文書は投稿体験と判断の原則を示すものであり、AIの利用範囲や検索方式を確定しない。実装時には、自然文解析・画像理解・矛盾検出のどこにAIを使うか、ルールや通常検索で代替できる部分、処理コスト、候補の表示方法をMVPの条件に合わせて再評価する（判断材料の数値の閾値はIssue #61）。AI利用量を変えても「まず投稿を受け取り、投稿後に会話から理解し、判断を経て採用する」という体験の原則を保つ。
