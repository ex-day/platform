# S15 企画のページ（project）

> 2026-11-16 新規（[Issue #135](https://github.com/ex-day/platform/issues/135)）。画面 ID は画面一覧のとおり案（人がレビューで確定する）。本書で使う新しいコンポーネント（C28〜C41）・機能（F05〜F12）の番号も候補。

## 画面概要

1つの企画（運営のお題、またはユーザーの作品）を見せる。並び（項目と順番・順位、根拠）、作った人、企画そのものの会話、企画をきっかけにした会話を1か所にまとめ、会話の取っかかりにする（[DEC-0021](../../decisions/DEC-0021-projects-by-operator-and-users.md)、[MVP スコープ](../../ex-day_mvp_scope.md) 8節）。

企画は作った人の作品であり、ex-day の認定ではない。作った人を出し、根拠と並べ、人気投票だけで順位を決めない（DEC-0021 決定5）。

## 画面パス

- `/projects/[id]`
- `[id]` は企画の、画面・URL に出す識別子。識別子の形式は物理設計で決める

## 対象端末

- PC
- モバイル

## アクション

- 初期表示
  - 指定された識別子の企画を表示する
  - 企画が非公開なら、一般のユーザーには表示しない（直接の URL でも返さない）。運営と、**その企画を作った人**は表示でき、非公開であることを出す（作った人には「この企画は運営により非公開になっています」と理由の分類を出す。画面一覧「運営の権限」）
  - 並びは ProjectItem の順番・順位で出す。項目が指す Discovery が統合済みなら最後の統合先へ案内し、非公開・成立の取り消し（統合先を含む）なら、その項目を「表示できません」として位置を残す（決めたこと、2026-11-18、PR #155）
  - 項目の根拠は、場所の推定の値と、その場所の会話の数から導いて出す
- 項目（場所カード・Discovery カード）を押下：S13（場所のページ）・S03（Discovery のページ）へ
- この場所の話をする を押下
  - C27 を、入口＝この企画で開き、会話の始まりの時点でこの項目の場所を採用する（主体＝会話を始めた人、根拠＝入口。論理設計 4.3節）。場所の共有の誘いは出ない
  - 項目が Discovery を指すときは、その Discovery の出す位置の場所を採用する（**案**。論理設計 4.3節）
- 企画そのものの会話に書く（C26）
  - 返信の確定時に F10 を通す。未ログインなら C08 でログインを求める
  - 「この坂も入れて」などの提案も、ここに声として書く。専用の提案の操作は MVP では作らない（MVP スコープ 8節）
- 編集する を押下：S16 へ（作った人だけ。非公開の企画も直せる。直しても非公開は解除されない）
- 項目の地図のピンを押下：並びの中のその項目を目立たせ、表示位置を合わせる。並びの項目を押下したときも、地図のピンを目立たせる
- 会話カード を押下：S14 へ
- 通報する（C39）：企画を通報する。F10 を呼ぶ

## 構成方針

- 上から「型・状態」「表題・呼びかけ・作った人」「並び（と項目の地図）」「企画そのものの会話」「企画をきっかけにした会話」の順に置く。**PC** は並びを本文の列、項目の地図と企画をきっかけにした会話を横の列にする。**モバイル** は1列
- 作った人は表題のすぐ下に必ず出す。ユーザーの企画は「ex-day の認定ではありません」を添え、運営の企画と見分けられるようにする
- 根拠は並びの横に必ず添え、順位だけを大きく見せない。データから作った番付は、表題か並びの上に「推定」と出どころを出す
- 企画そのものの会話は、並びのすぐ下に置き、「この坂も入れて」「順番はこっちが上では？」と書きたくなる案内文を添える。作った人が読んで、自分で並びを直す（S16）

### 項目の地図

コースでは、位置関係と回る順が企画の価値そのものなので、MVP で地図を出す（2026-11-16 の人の判断）。

| 型 | ピン | 線 | 地図の置き方 |
|---|---|---|---|
| コース | 順番の番号つき | 順番どおりに項目の代表の地点を**直線**でつなぐ。「回る順を示す線で、道順ではありません」と添える | 並びと同じ重みで出す。モバイルは並びの上、PC は横の列で並びと一緒に見える位置に固定する |
| 番付 | 順位の番号つき | 引かない（順位は位置の順ではないため） | 並びの補助。モバイルは並びの下に小さく、押すと大きく開く |
| まとめ | 番号なし | 引かない | 番付と同じ |
| 記憶 | 番号なし | 引かない | 項目に場所があるときだけ、番付と同じ |

- 項目が経路の形の場所（散歩道、定期航路）なら、その形を描く。項目が Discovery なら、その Discovery の出す位置の場所（DiscoveryPlace の役割が体験できる場所・始まり）を使う。順番のある Discovery（コースの Discovery）を項目にしたときは、その Discovery の中の順番も細い線で描く（**案**）
- 経路の探索・道路に沿った道順・移動時間の計算は MVP では行わない（寄り道の到達圏とも分ける）
- 地図の表示範囲は、全部の項目が入るように合わせる。項目が多いときにピンをまとめるか（数の目安）は要検討
- ピンと並びの項目は、番号をそろえ、押すと互いに目立たせる

### 企画の変更の出来事

企画そのものの会話のタイムラインに、企画の変更の出来事（「坂Bを足しました」「坂Aが3位から2位に」）を出す（2026-11-17 の人の判断、PR #150 のレビュー）。会話を通して企画が育つ過程を見せ、参加した人が自分の声が反映されたことを感じられるようにするため。

- 出来事は、項目の追加・外す・順番の変更（4つの型とも）。データは企画の変更の履歴（論理設計 4.6.2節、DB 設計 3.5節）
- 出来事は企画に属し、会話には属さない。企画そのものの会話がまだなくても出せる。出来事を出すために空の会話を作らない（会話は最初の発言のときに作る）
- 見え方は企画の公開状態に従う。動いた項目が指す Discovery が非公開・成立の取り消しになっていれば伏せ、統合なら統合先へ案内する
- **検討事項**：出来事の文言と、まとめ方（1回の保存で多くの項目が動いたとき）。表題・呼びかけ・説明を変えたことも出すか（中身は写さず、変えた事実だけを持つ）。運営の企画でも出すか。過去の並びを再現して見る専用の画面（継続検討）。提案の Post と変更の結び付け（継続検討）

### 企画を閉じること

- **閉じる機能は MVP の対象外（決定）**。将来、機能を足す必要が生じた時点で設計し、それまでは再検討しない（2026-11-16 の人の判断、PR #144・#149）。コースを完成させる企画と、近くのコースや場所を続けて集める企画とでは、「終わり」の意味も必要性も違う。また、企画の中身が完成することと、そこから生まれる会話が終わることは別である
- 将来設計するときの前提：権限は作った人（と運営）に限り、閉じることは公開の制御（非公開）とは別のものとして扱う
- 作った人がいなくなった企画は、そのまま残す。ほかのユーザーが新しい企画を作り、元の企画の会話で紹介したり、関連付けたりして続けられる。企画どうしの関連付けの仕様と、初期の MVP での範囲は別途整理する。双方の合意による企画の譲渡は後続の MVP の検討課題とし、今は作らない（運営による強制的な継承や、不在の判定もしない）

## 取得用 API で返すもの

> 2026-11-18 追加（Issue #135 の「API」の段、PR #155）。取得用の API の約束事（OpenAPI）を書く前に、区画ごとに読む表と返すものを決めた（1段目のレビュー）。件数は暫定の値で、実際の画面・運用で調整する。S17（企画の一覧）は、本画面のあと別の PR で扱う（対象を小さくするため）。

**API**

- `GET /projects/{projectId}`：企画のページの全部の区画。タイムラインは新しい側から一定数だけ
- `GET /projects/{projectId}/timeline`：「これまでのやりとりを見る」で、それより前のタイムライン（Post と変更の出来事）を段階的に読む（S14 の Post の続きと同じ考え方）

**共通**

- 一般のユーザー向けの読み取りなので、公開のビュー（`visible_project`・`visible_project_change`・`visible_conversation`・`visible_discovery` 等）を通す。1つの応答を REPEATABLE READ の読み取り専用トランザクションで作る
- 企画が非公開なら 404（直接の URL でも返さない）。運営と、その企画を作った人の表示（「この企画は運営により非公開になっています」）・「編集する」は認証（#75）のあと
- 公開状態は対象ごとに独立して扱う（DB 設計 2.5節）。Post が非公開なら S14 と同じく枠だけを出す
- 画面をまたぐ部品は共用する（`apps/api/AGENTS.md`）：Discovery Card と出す位置の場所の決め方（C03、`card.discovery`）、会話カード（C40）、Post（C26。S14 の PostItem）、統合のたどり（`merge`）、地図の形（GeoJSON）

**区画ごとの読み方**

| 区画 | 読む表・ビュー | 返すもの・並び | 件数 |
|---|---|---|---|
| 見出し | `visible_project`、`user_profile` | 型、表題、呼びかけ、説明、作った人（種類と今のニックネーム） | ― |

**並びの項目**（決めたこと 1）

- `visible_project_item` は、非公開・成立の取り消しの Discovery を指す行を除くので使わない。企画の公開を `visible_project` で確かめたあと、`project_item` を読み、**指す先だけを公開の判定にかける**
- 指す先は3つの形のどれか：
  - **場所**：場所の参照と種類（場所は公開状態を持たない）
  - **見える Discovery**：Discovery Card。統合されていれば、最後の統合先が見えるときだけ統合先のカードを出す
  - **表示できない項目**：Discovery が非公開・成立の取り消し、統合先が非公開・成立の取り消し、統合が循環・深さの上限で決められないとき。**順番の位置だけを残し**、元の識別子・中身・理由は返さない（番付・コースの順位を飛ばさないため）
- 統合によって同じ Discovery を指す項目が複数になっても、企画の並びなので位置はまとめない

**Discovery の項目の会話の数**（決めたこと 2）

- 由来の会話（その Discovery が生まれた会話）と、その Discovery から始まった会話は意味が違う。前者は根拠に近く、後者は根拠とは限らない
- そのため**分けて**返す：由来の公開の会話の数、その Discovery から始まった公開の会話の数。それぞれ同じ会話は1回だけ数える
- 場所の推定の値は Discovery 自体の根拠のように見えるので、Discovery の項目には付けない

**地図の形と代表点**（決めたこと 3）

- Discovery の項目は、S03 の `displayPlaces` と同じ選び方（`card.discovery` の出す位置の場所）を共用する：関わる場所のうち役割が体験できる場所・始まりのもの（関わる場所の順番、識別子の順）。なければ関わる場所の最初の1つ
- 出す位置の場所が複数あれば、その全部の形を返す
- **代表点**（コースの回る順の線を結ぶ点、ピンの位置）：場所の形が点ならその点、経路なら始点、エリアなら形の中の1点（PostGIS の `ST_PointOnSurface`）。Discovery の項目は、出す位置の場所の最初の1つの代表点

**タイムライン**（決めたこと 4・5）

- Post と変更の出来事を混ぜる。**全順序は、時点 → 種類（変更の出来事を先、次に Post）→ 識別子（文字コードの順）**。Post は投稿の時点、変更の出来事は変更の時点
- 新しい側から20件（暫定）を選び、各ページの中は画面の表示どおり古い順に返す。それより前が残っていれば、カーソルを返す。カーソルは並びのキー（種類と識別子。時点はサーバーが引く）を含み、画面は中身を解釈しない
- 最初の Post をいつも返すことはしない（企画を作った出来事がタイムラインの最初になるため）
- 非公開の Post は S14 と同じく枠を残し、タイムラインの件数に含める
- 変更の出来事は運営の企画にも出す。表題・呼びかけ・説明は、中身を写さず「変えた」という事実だけを出す。1回の保存を1つの出来事として保ち、出来事の中の項目はページングしない（1回の保存で動かせる項目の数を有限にする。下の「件数の上限」）。多くの項目が動いたときのまとめ方は画面が決める

**件数の上限**（暫定。企画の作成・編集の API（S16）で守り、取得の応答にも `maxItems` を置く）

- 1つの企画の項目：最大100件
- 1回の保存で動く項目（変更の出来事の中の項目）：最大200件（全部の項目を外して、同じ数を足すときの最大）
- これらは企画の作成数の上限（一定期間内に1人が新しく作れる企画の数。累計の上限ではない。MVP スコープ 8節、DEC-0021）とは別のもの。作成数の上限は、取得の API では使わない

**今回は返さないもの**

- 非公開の企画を、運営・作った人が見る形、「編集する」を出せるか：認証（#75）のあと
- 運営の操作（C38）：認証のあと
- 企画への Reaction：MVP では付けない（S15 の判断待ちのとおり）
- 企画どうしの関連付け：仕様が決まるまで扱わない
- 企画をきっかけにした会話の続き：上の表のとおり

## 判断待ち・検討事項

- 企画どうしの関連付けの仕様と、初期の MVP での範囲（会話で紹介するだけにとどめるか）
- 項目の地図で、項目が多いときのピンのまとめ方
- 項目が指す Discovery が非公開・統合済みになったときの見せ方：統合は最後の統合先、非公開・成立の取り消しと統合先が見えないときは「表示できません」の枠で位置を残す（決めたこと、2026-11-18、PR #155）。枠の文言は画面で決める
- 企画そのものの会話の「話す」の扱い（入力欄へ移る案）
- 企画への Reaction（DEC-0021 の要検討。番付の根拠の声の数と混ぜない）は MVP では付けない
