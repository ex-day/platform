# 各種設計資料の作成方針について
## 概要
生成AIと各種設計を行う上でどのように作業を進めるか方針をここに決定する

## 対象AI
### 壁打ち・レビューAI
- ChatGPT
- Claude

### 実装AI
- Codex
- Claude code

### デザインAI
- Claude Design
- ~~Figma AI~~：Issue #4での検証の結果、利用しない方針とした。指定したリポジトリではなく指定外のリポジトリへアクセスしようとする挙動が確認され、設定側の問題であっても安全側に倒れない点の信頼性を懸念。加えて無料クレジットも少数画面の試行で枯渇しており、有償プランへの切り替えは行わず対象から除外する（詳細はIssue #4参照）

## 作成すべき資料
- 論理モデル
- Entity関連図
- ワイヤーフレーム

- API定義書

## 作成するにあたって必要な資料
- 画面定義書
- コンポーネント定義書
- MVPシナリオ

## 行いたいこと
### 論理モデル
1. MVPシナリオ、画面定義、コンポーネント定義を元に、粗めに要素を抽出
2. 抽出した要素を元にAIと壁打ちを実施し、MVPシナリオが通ることを確認
3. MVPシナリオに足りない要素がないか確認
4. AIと再度レビューを実施し、論理モデル設計書を出力し完了

### ワイヤーフレーム作成

1. issueをインプットとして作業指示を行い、Claudeでワイヤーフレームを複数案作成する（成果物はClaude Designのアーティファクトとして保持し、リポジトリにはコミットしない。issueに成果物へのリンクを記録する）
2. 複数案のうち、イメージに近いもの・実現時のユーザー体験がより良いと考えられるものを1案に絞り込む。人間自身の判断に加え、作成を指示した以外のAI（Codex等）にもレビューを依頼し、ダブルチェックする
3. 絞り込んだ案に対して変更したい点をフィードバックし、Claudeに反映させる
4. フィードバックを反映した案をもとに、`apps/web`にNext.jsの動くモックアップとして構築する（ダミーデータ・API未接続の状態。技術構成は`フロントエンド技術方針.md`に従う）
5. モックアップ上で画面遷移・操作性を確定する
6. ワイヤーフレーム作成完了。以降はこのモックアップをベースに実装を進める

（本方針は #4 での検証結果に基づく。旧方針ではFigmaへの登録とFigma AIによる修正を前提としていたが、検証の結果Figma AIは利用しない方針としたため、Claude中心のフローに置き換えた）

### コンポーネントの新規追加（採番）

コンポーネント定義（`docs/ui/components/`）に存在しない要素を、ワイヤーフレーム作成や実装の過程で「独立したコンポーネントとして切り出すべき」と気づいた場合の手順。

1. ワイヤーフレーム作成時点では、対象の要素をコンポーネント化せず、画面内のインライン要素として作成する。
2. 独立コンポーネント化すべきと判断した場合は、既存の「設計書へのフィードバック」と同様の枠組みで、対象・理由を記録し提案する（提案自体はAIが行ってよい）。
3. 提案の採否はレビュー（人間）で判断する。コンポーネントID（番号）はこの時点で初めて確定させる。AIが独自判断で採番することはしない。複数AIが並行して作業する場合に番号の衝突・不整合が生じるため。
4. 採用が決まったら、`docs/ui/components/`へ新しいコンポーネント定義（`C0X-xxx.md`）を追加する（下書き自体はAIに作成させてよい）。
5. コンポーネント定義の追加後、実装側で対応するコンポーネントを作成する（詳細は`フロントエンド技術方針.md`のコンポーネント構成に従う）。

### 画面項目定義書作成

1. 作成されたワイヤーフレーム、画面定義書、コンポーネント定義書を元に画面項目定義書作成を指示
2. yaml形式で画面項目定義書を作成
3. 作成された画面項目定義書を作成したAI以外でレビュー
4. 作成された画面項目定義書をhtml形式もしくはMarkdown形式で出力
5. html形式の画面項目定義書をもって最終確認
6. 画面項目定義書作成完了

### API定義書

1. 画面項目定義書および画面定義書、コンポーネント定義書をインプットとしてAIへ作業指示
2. OpenAPI形式でドキュメントを作成
3. 作成されたドキュメントを作成したAI以外でレビュー
4. レビューが完了したOpenAPI形式の定義書を最終確認
5. API定義書作成完了
