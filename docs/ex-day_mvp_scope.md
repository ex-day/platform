## 1. MVP の目的

ex-day が一番やりたいことは、Wiki や Google では見つかりにくい、地域の細かな発見を、実際の体験につなげることである（DEC-0019）。体験の順位は次のとおりで、A・C が集まり、E（会話）を通して D（体験へ誘う）につながる。

| | 体験 | MVP での位置 |
|---|---|---|
| A | 地域の記憶 | 会話から集まる（最初はデータがない） |
| B | 寄り道 | **最初にサービスを支える**（データがなくても成り立つ） |
| C | 今昔 | 会話から集まる。資料（古写真）は二次開発 |
| D | 体験へ誘う | Discovery が、場所のページ・TOP・寄り道で次の人を誘う |
| E | 会話 | A・C を D につなぐ過程。企画がきっかけになる |
| F | 問い | 会話の中の問いと「探しています」 |

MVP では、次の仮説を確かめる。

1. **初期のデータがなくても成り立つか**：Discovery がほとんどない状態でも、寄り道（B）・場所のデータ・企画で、人が来て、使って、また来るか
2. **企画が会話のきっかけになるか**：運営とユーザーの企画（番付・まとめ・コース・記憶）に、場所の会話が集まるか
3. **参加の入り口を軽くできるか**：投稿した人に場所の入力を求めなくても（DEC-0023）、場所が入口・言葉・周りの人から集まるか
4. **場所の分からない話が届くか**：場所未定の会話・問いが「このあたりで探している人がいます」「探しています」で周りの人に届き、答えが返るか
5. **会話から発見が生まれ、次の人を誘うか**：会話から Discovery（どこで、何を、どう体験できるか）が成立し、場所のページ・TOP・寄り道から、次の人の体験につながるか
6. **ユーザーの企画が過信されずに参加を生むか**：「自分の番付を作れる」が参加のきっかけになり、作った人が見える・根拠と並ぶ形で、ex-day の認定のように受け取られないか
7. **興味が明確でない人も出会えるか**：興味を登録しなくても、寄り道・TOP から知らなかった発見に出会えるか

初期の場所のデータと運営の企画は、横浜周辺から用意する。閲覧と投稿は地域を限らない。始める地域の外にいる人への見せ方は DEC-0022 決定3 に従う。

## 2. 基本思想

### 場所が先にあり、会話が器になる

場所は Discovery や会話がなくても最初から存在する。会話（投稿と返信）は場所・Discovery・企画を入口にして、または入口なしで始まり、Post は会話に属する。Discovery は「どこで、何を、どう体験できるか」であり、場所を1つ以上持ち、成立したときに作る（DEC-0020）。

### 参加の入り口を軽くする

このサービスは、ユーザーに参加してもらわなければ成立しない。コミュニティの機能は薄いが、ソーシャルな部分はしっかりある。

- 閲覧・寄り道・検索にログインを求めない。投稿・企画の作成の確定時にログインを求め、入力内容はログイン後に引き継ぐ（DEC-0010 決定2）
- 投稿した人に場所の入力を求めない。場所が決まっていないときは、投稿の直後に共有を任意で誘う（1つの投稿で1回まで）。場所未定でも不利に扱わず、届く機会が減ることは隠さない（DEC-0023）
- 場所・時期・関連先が分からなくても投稿は必ず通る。解析の結果を待たない

### 会話も主役

Post は単独でも成立し価値を持つ（DEC-0004）。Discovery に還元できた投稿だけを価値のある投稿として扱わない。

### Discovery は完成しない

Discovery に「完成」はない。成立のあとも、会話で場所・価値が足され、補強される。成立と補強は自動を基本にし、多少のぶれは許す。その代わり、あとから直せる（成立の取り消し、場所・価値の付け替え、統合）ようにする（ドメイン設計 5.9節）。派生・統合は MVP では自動で確定せず、必要なときに運営が判断する（7節）

### 編集ではなく、足していく

他の人が作ったもの（Post、Discovery、企画の並び）を直接書き換えない。足すのは会話として行い、企画の並びは作った人が直す（DEC-0021 決定4）。相反する情報は、一方を消さずに並べる。

### 採用は正しさの保証ではない

議論の結果として場所・回答を選ぶことは「採用」と呼び、「確定」「解決済み」と言わない。新しい情報で再検討・採用し直しができる（ドメイン設計 1.2節）。

### 情報の出所を残す

Discovery・わかってきたことから、もとの会話・Post・投稿した人をたどれる。企画は作った人を出す。

### レビューサイトにしない

店舗・施設の評価や口コミを目的にしない。番付は作った人の作品の並びであり、品質の評価ではない。人気投票だけで順位を決めない（DEC-0021 決定5）。

### 地図は主役ではないが、入口になる

主役は場所の発見と会話。地図は、TOP の小さな地図と寄り道の画面で、「ここから行ける」を見せる入口として使う（DEC-0022）。

## 4. 寄り道

### 目的

「この時間で、どこに寄れるか」に答え、データがない初期からサービスを支える（DEC-0013・0019）。場所の発見に出会う入口にもなる。

### MVP 実装範囲

- 起点（場所）と使える時間で探す。時刻では聞かない（DEC-0014）。終点は、なし（片道）・起点に戻る（往復）・別の場所（帰り道）
- URL：`/detour?from=<場所の識別子>&to=<場所の識別子>&t=<分>`。`to` を省くと往復、`to=none` で片道。座標を URL に出さない（DEC-0022 決定5）
- 結果は、寄れる場所と「そこで何分過ごせるか」（寄れる時間＝使える時間 −（起点からそこまで）−（そこから終点まで））。終点ごとに：往復は「そこから起点まで」、帰り道は「そこから終点の場所まで」を引く。片道（終点なし）は最後の項を 0 とし、寄れる場所で旅程を終える（2026-11-19、PR #162 のレビュー）。地図の色はこの時間で塗る
- 寄り道先のまとまり（「○○のあたり」）で束ねて出す（場所どうしの関係の観光・生活のエリア）
- 寄れる場所の上の Discovery を出す。Discovery のない場所も「声のない場所」として出す
- 移動時間は時刻表を使わず、駅と表定速度から「だいたい○○分」として出し、誤差は「行けない」側に寄せる（DEC-0013 決定1）。駅から先の行き方は、あとから足せるデータ（DEC-0013 決定2・3）
- 入口：ヘッダーの「寄り道」、TOP の小さな地図、場所のページ・Discovery のページの「ここから行ける」（DEC-0022 決定1）
- 全画面の地図から戻ったときに、遷移元（TOP・探す・Discovery のページ・場所のページ）に戻り、その状態を保つ（DEC-0022 決定4。探すからの遷移を足した）

### MVP の対象外

- 速達列車の扱い（poc#44）、駅以外の起点、時刻表を使った経路、乗り継ぎの詳細（乗換案内のサービスに任せる）
- 順番のある Discovery（コース）の「始まりまで ＋ コースの時間 ＋ 終わりから」は、移動時間が分かる場合に限って出す。出せないときは出さない

### 判断待ち

- ~~DEC-0013・DEC-0014 の Accepted の扱い~~：2026-11-19 に両 DEC を Accepted にした（PR #162）。行き方・到達点・駅の番号・到達圏のデータの形と、計算の値は F06 の設計（#161）で決める

## 5. 場所と場所のページ

### 目的

場所を発見と会話の土台にする。Discovery がない場所にも、会話・企画・寄り道の入口がある。

### MVP 実装範囲

- オープンデータから場所を取り込む（横浜周辺から）。行政区域（都道府県・市区町村・町丁・字）は全国の受け皿として用意する（DEC-0020 決定3）
- 場所の形は地点・エリア・経路。種類（城跡・公園・駅・坂等）を持つ
- 場所どうしの関係（行政の階層、地理的な包含、観光・生活のエリア）
- 場所の推定の値（坂の勾配等）を、番付の最初の並びの根拠に使う
- **場所のページ**：その場所の Discovery（観点ごと）、会話、「このあたりで探している人がいます」、関わる企画、「ここから行ける」（寄り道の入口）、「話す」（入口＝この場所の会話を始める）
- 会話から育つ場所（今はない跨線橋、店）は、採用されるまで場所にしない。採用されたら場所として足す（論理設計 4.2・6.1節）

### MVP の対象外

- 場所の情報の訂正の提案、場所の重複の統合（運営が手で直す）、旧地名・境界の時間変化
- 会話のない場所を一覧で出すか（寄り道の「声のない場所」と TOP の「声を待っている」は出す）は画面の設計で決める

## 6. 会話と投稿

### 目的

A（地域の記憶）・C（今昔）を持ち寄る場であり、E（会話）を通して D（体験へ誘う）につなげる。

### MVP 実装範囲

- **新しい話を始める**：ヘッダーの「話す」、場所のページ・Discovery のページ・企画のページの「話す」。入口から場所が決まる会話は、始まりの時点でその場所を採用する（論理設計 4.3節）
- **投稿の入力**：本文だけを必須にする。場所の入力欄を置かない（DEC-0023）。写真の添付は MVP では扱わない（資料は二次開発。14節）
- **場所の共有の誘い**：会話を始めた時点で採用した場所がなければ、投稿の直後に誘う。候補があればワンタップで確かめる、なければ地図で指す・現在地の近くから選ぶ。文字を打たせない。1つの投稿で1回まで。誘いは「自分の話」に残る（DEC-0023）
- **返信**：会話への返信。返信・メンションの参照（PostReference）
- **場所の候補と採用**：投稿直後の照合・解析・返信から出た場所の候補（検討中）。「ここかも」「違うと思う」の声。採用は、問いを立てた人・投稿した人、または運営。採用中に新しい情報が寄せられても自動で取り消さず「再検討中」にする（論理設計 6.1・6.2節）
- **問い**：会話の中の「どこ？」「なぜ？」。回答の採用を「投稿者が採用した回答あり」「現在の回答あり」「新しい情報が寄せられ、再検討中」「引き続き募集中」で見せる。「解決済み」と言わない
- **場所未定の会話を届ける**：候補の場所のページの「このあたりで探している人がいます」、TOP の「探しています」、投稿した人の「自分の話」（ドメイン設計 3.4節）
- **わかってきたこと**：会話から読み取った説・価値を見せる（見立て。DEC-0015）
- **Reaction**：Post への共感、価値への「わかる」「行ってみたい」、裏付けのない説への「そうかも」。種類の細部は画面の設計で決める
- **自分の話**：自分が始めた会話・返信、場所の共有の誘い、自分の会話から分かってきたこと・成立した Discovery。返信や答えが来たことが分かる

### MVP の対象外

- 写真・資料の添付と、資料のページ（二次開発の筆頭。14節）
- 通知の配信（メール・プッシュ）。MVP では「自分の話」の中で分かる形にとどめる（**要検討**：最小限の通知を入れるか）
- 会話の分割・統合、別の会話の Post の引用

## 7. Discovery

### 目的

会話・投稿・企画から、「どこで、何を、どう体験できるか」を取り出し、次の人の体験に誘う（D）。

### MVP 実装範囲

- **成立**：会話・1つの投稿・企画の登録・運営の登録のどれからでも、同じ基準で成立を判断する（DEC-0020 決定5・7）。MVP では、解析が出した Discovery の候補を、**自動で成立させるのを基本にする**（人の判断、2026-11-14）。多少のぶれは許し、その代わりあとから直せるようにする：
  - 自動で成立したことは、判断の記録に「方式＝自動」と、適用した規則・解析の版とともに残す
  - 運営は、自動で成立した Discovery を事後に一覧で見直し、成立の取り消し、場所・価値の付け替え、統合ができる。直しても行を消さず、判断の記録を足す
  - 閲覧する人の異論は、会話で受ける（「この発見について話す」、もとになった会話への返信）。正誤を言い切るボタン（「これは違う」）は置かない。何が違うのか・その根拠は会話でしか伝わらず、異論を唱える人の知識が正しいとも限らないため（2026-11-16 の人の判断。S03「リアクション・会話・通報の役割」）。会話から取り出した異論は、事後の見直しの材料になる
  - Discovery のページには由来（どの会話から取り出したか）を出し、ex-day の認定に見せない
  - 自動で成立させる条件・閾値（確からしさ、根拠の Post の数、場所の有無など）と、運営の確認に回す条件は [Issue #46](https://github.com/ex-day/platform/issues/46) で決める。最初は条件を緩めに置き、見直しの結果で調整する（DEC-0020 決定8：自動の範囲は精度の評価に応じて決める）
- **運営が登録する Discovery**（#57）：初期の見本として、始める地域に用意する（TOP の「ex-day の発見（見本）」）。運営専用の登録画面は作らない。ファイル・SQL 等で初期投入し、将来は運営用の MCP でも登録できるようにする。具体的な登録の手段は後続の設計で決めるが、どの手段でも場所との関係・由来（運営の登録）・判断の記録を残す
- **場所との関係**：場所を1つ以上、役割・順番つきで持つ（1か所、役割の違う複数の場所、順番のある組み合わせ）
- **Discovery のページ**：何を体験できるか（価値と条件）、関わる場所の地図、由来の会話、わかってきたこと、関わる企画、「ここから行ける」、「話す」
- **表示**：場所のページ（役割つき）、TOP の「いま、この時期」「近くの発見」、寄り道の結果
- **補強**：会話から価値・場所が足される（成立と同じく自動を基本にし、あとから直せる）
- 推薦の順位付けは、時期の条件（Season 等）と「今・ここ」の一致、近さで行う。高度なパーソナライズはしない

### MVP の対象外

- 派生・統合・関連の自動の確定。既存の Discovery と同じ・近いという候補は解析が出してよいが、確定は運営が手で行い、判断の記録を残す（統合・派生はほかの Discovery・会話・企画の項目に影響するため）。専用の画面は作らず、運営の管理の画面で扱う（人の判断、2026-11-14：当初は手動でよい。将来はユーザーの参加を検討する。14節）
- Discovery への提案（補完・新しい Value の追加など）の受付の画面
- 出来事（単発の予定）

## 8. 企画

### 目的

会話の取っかかりにする（人の判断、2026-11-14）。運営の「いま募集中」のお題と、ユーザーの作品（「自分の番付」）の両方を扱う（DEC-0021）。

### MVP 実装範囲

- **型**：コース（順番）・番付（順位）・まとめ（条件で集める）・記憶（声が中心）の4つを扱う。ユーザーが作れる型は **要検討**（案：4つとも）
- **企画のページ**：表題、呼びかけ、作った人、並び（項目と順番・順位、根拠を横に添える）、企画そのものの会話、企画をきっかけにした会話
- **項目**：場所 または Discovery を指す。番付は場所の推定の値の順を最初の並びにし、作った人が直せる
- **企画そのものの会話**：「この坂も入れて」などの提案は、ここに声として書く。作った人が読んで、自分で並びを直す
- **作る画面**：企画の作成・編集の画面を1つ作り、運営もユーザーも同じ画面で作る（最初の数本は、画面ができる前に運営がデータで入れてよい）。場所を選ぶ部品は、場所の共有の誘いの部品と共通にする
- **歯止め**（DEC-0021 決定5 の最小限）：作った人を出し、ex-day の認定に見せない。根拠（推定の値、声の数）と並べる。人気投票だけで順位を決めない。作るにはログインが要る。一定期間内に1人が新しく作れる企画の数に上限を設ける（累計の上限ではない。期間と件数は作成の API・運用の段階で決める。2026-11-18 の人の判断、PR #155）。通報と、暫定公開＋事後チェックの対象にする
- **項目の地図**：コースは、項目の場所を順番の番号つきで地図に出し、順番どおりの直線でつなぐ（道順ではない）。番付・まとめ・記憶は番号（番付だけ）つきのピンで出す。作成・編集の画面でも出す。経路探索・道路に沿った道順は MVP では行わない（S15「項目の地図」。2026-11-16 の人の判断）
- **編集できるのは、その企画を作った人だけ**。運営かどうかではなく作った人かどうかで判定する（運営が作った企画は運営が編集できる）。運営の権限では、ほかの人の企画の中身を直さず、規約違反などへの非公開（公開の制御）だけを行う（企画は作った人の作品であり、運営が直すと権利・帰属の問題が生じるため。2026-11-16 の人の判断）
- 非公開の措置を受けた企画も、作った人は確認・編集できる。編集の権限と公開の制御は分け、直して保存しても非公開は自動で解除しない。公開に戻すかは運営が判断する
- 項目には、既存の場所なら、オープンデータ由来などで会話がまだない場所も足せる。まだ採用されていない場所の候補は足せない
- 企画をきっかけにした会話は、中身は場所の会話であり、企画とは別に場所の会話として残る
- **企画の変更の履歴**（2026-11-17 の人の判断、PR #150 のレビュー）：項目の追加・外す・順番の変更を、4つの型とも変更の出来事として持ち、企画そのものの会話のタイムラインに出す。会話を通して企画が育つ過程を見せ、参加した人が自分の声が反映されたことを感じられるようにするため。提案のもとの Post と変更を明示的に結ぶことは継続検討（まずは時系列の上の会話と変更の出来事から経緯が分かればよい）。運営の事後チェックのための更新の検知とは目的を分ける（F10）

### MVP の対象外（二次開発）

- 提案を取り込む専用の流れ（提案の状態、取り込み・却下のボタン）
- 過去の並びを再現して見る専用の画面（**継続検討**。MVP に設けるかを含む）。企画の変更の履歴のデータは MVP で持ち、企画そのものの会話のタイムラインに変更の出来事を出す（8節の実装範囲「企画の変更の履歴」。決定）
- 似た企画を作る前の案内
- 企画を閉じる機能：MVP の対象外（決定）。コースを完成させる企画と、続けて集める企画とでは終わりの意味が違い、企画の中身の完成と、そこから生まれる会話の終わりも別のため。将来、機能を足す必要が生じた時点で、状態の持ち方と権限（作った人と運営に限り、公開の制御とは分ける）を含めて設計し、それまでは再検討しない（2026-11-16 の人の判断、PR #144・#149）
- 作った人が退会・離脱したとき：企画はそのまま残す。ほかのユーザーが新しい企画を作り、元の企画の会話で紹介したり関連付けたりして続けられる（企画どうしの関連付けの仕様と、初期の MVP での範囲は別途整理する）。退会後の表示の継続などの規約の定めは、外部公開の前に要る（12節・14節）
- 企画の譲渡（原案を作った人が戻ったときに、続けていた関連の企画の作った人が譲るなど、双方の合意による譲渡）：後続の MVP の検討課題。作った人の履歴と帰属の扱いも考える。運営による強制的な継承や、不在の判定はしない
- フォロー・メッセージ等のソーシャルの機能

## 9. TOP

DEC-0022 に従う。

- **PC**：真ん中に企画と発見、余白に小さな地図（ここから行ける範囲）。**スマホ**：一番上に地図のカード、その下に企画と発見のカード
- **枠**：企画、いま・この時期、近くの発見、ここから、番付（推定）、ex-day の発見（見本）、声を待っている、探しています（場所未定の会話。DEC-0023・ドメイン設計 3.4節）
- **中身のある枠だけを出す**。空の枠や「0件」は出さない。データの量に合わせて重みが自然に移る（初日は企画・ここから・番付・見本・声を待っているが中心）
- Discovery が少ないときは範囲を広げて探し、少なさを隠さず余白を数字で見せる（DEC-0022 決定3）
- 既定を地図にする設定は MVP の対象外（DEC-0022 決定6 の扱いに従う）

## 10. 認証・ユーザー

### 認証

Amazon Cognito を使う（DEC-0016）。SNS 認証（Google 等）とメールでのログインを扱う。ex-day 自身はパスワードを持たない。メールアドレスは ex-day に保存せず、Cognito だけが持つ。内部では認証サービスとは独立した User の識別子を持つ。

認証プロバイダから受け取る名前・顔写真は使わず、初期値にもしない（[Issue #75](https://github.com/ex-day/platform/issues/75)）。

### ユーザープロフィール

使い道のない情報は持たない（[Issue #76](https://github.com/ex-day/platform/issues/76)）。

- **必須**：ニックネーム。初回ログイン時に、本名と関係のない候補が入った状態で確認して決める。全角12文字（半角24文字）相当まで、重複可、変更回数の制限なし。運営と紛らわしい名前（「ex-day」「運営」「公式」を含むもの）は使えない（[Issue #74](https://github.com/ex-day/platform/issues/74)）
- **任意**：興味のある地域（複数可）、興味（複数可。項目名・単位・入力方法は [Issue #73](https://github.com/ex-day/platform/issues/73) で決める）。どちらも他の人には表示しない

年代、性別、住んでいる地域・生活圏、プロフィール説明は持たない。ユーザー名（重複不可の識別用の名前）は持たない。内部の連番は画面・URL に出さない。表示名は表示のたびに今のニックネームを引く。ニックネームの変更履歴は運営だけが見られる（#74）。

### 分析

閲覧した地域・場所、Reaction、Post、検索・寄り道の条件を集計できるようにする。MVP では行動からの興味の推定とパーソナライズはしない。

## 11. 会話の解析

- **投稿直後の照合**：LLM を使わず、本文を地名の辞書と照合して場所の候補を出す。場所の共有の誘いを出すかの判定にも使う。辞書は始める地域から用意し、ありふれた地名は単独では候補にしない（[#82](https://github.com/ex-day/platform/issues/82)）
- **会話の解析（バッチ）**：Post から主張（Claim）を取り出し、わかってきたこと（Finding）・問い・場所の候補・Discovery の候補を作る（DEC-0015）。バッチで回し、予算・段階・縮退に従う（DEC-0018）
- 解析の未完了・失敗は投稿の成立を妨げない。解析で遅れていることは画面で分かるようにする（DEC-0018）
- 解析の結果は見立てであり、更新・分割・統合・失効してよい。人が作ったもの（Post・会話・企画）と、採用したもの（場所の採用、Discovery）を書き換えない

## 12. 安全・運用

会話（Post）・企画の両方に、次を適用する。

- 禁止語などのテキストのチェック
- 通報（対象：会話・Post・Discovery・企画）。規約違反・権利侵害・安全上の問題など、運営の確認・介入が要るものに限り、通常の知識への異論は会話で扱う
- 安全性に関する公開制御（通常公開・注意喚起付きの公開・非公開。会話の公開と Discovery の成立・公開の区別）は後続で検討する。運営は知識の正しさを裁定せず、知識が安全に蓄積される環境を保つ（[機能一覧](function-list.md)「F10 の後続検討」）
- 暫定公開と事後チェック（DEC-0021 決定5。Post にも同じ流れを使う）
- 問題のある Post・企画を非公開にできること
- 運営の操作：通報・事後チェック、非公開、自動で成立した Discovery の見直し（成立の取り消し、場所・価値の付け替え、統合）、場所の採用の直し、企画の非公開（企画の中身は直さない）。MVP では次の形で行う（人の判断、2026-11-14〜15。PR #141 のレビュー）
  - **専用の管理画面は最小限**：一覧が要るもの（通報・事後チェックの一覧、自動で成立した Discovery の見直しの一覧）だけ
  - **詳細の確認と直しは一般の画面を共用する**：運営としてログインしたときだけ、Discovery・場所・会話・企画のページに運営の操作が出る。権限の判定はサーバー側で行う
  - **足りないところは運営が SQL・データの投入で補う**：利用者に直接出す機能ではなく、当初は手動の運営で対応できるため。管理画面を作り込むより公開を優先する
- 運営が共用の画面で見るとき：非公開・統合済み・取り消された対象も、運営は一覧から詳細を開ける（一般のユーザーには見えない）。詳細では判断の記録（いつ・誰が・なぜ）をたどれる。戻すとき（非公開を戻す、統合や成立の取り消しを戻す）は、前の判断を書き換えず、新しい判断の記録を足す。MVP で戻す操作を画面に出すか、SQL で補うかは画面の設計で決める
- 将来の運営用 API・MCP に備えて、業務の処理・権限・監査（判断の記録）を画面に依存させない

### 利用規約等の確認の時期

**ベータ版を含め、一般のユーザーから投稿を受け付ける外部公開の前に**、次を利用規約等で定め、必要な法務の確認を終える（PR #140 のレビュー）。MVP では Post・企画・自動で成立した Discovery を公開し、退会後もサービス上に残す可能性があるため、正式リリースまで待たない。

- 投稿（Post・企画）の利用許諾（ex-day が表示・要約・Discovery への取り出しに使うこと。外部の知識ベースへの還元の可能性を含む。要求仕様 13節）
- 退会後の表示の継続と、そのときの投稿者の表示
- 削除の求めへの応じ方
- AI の要約・場所の推定・自動で成立した Discovery の扱い（ex-day の認定ではないこと）

退会時の自動の処理は二次開発に回してよいが（作った人が退会した企画はそのまま残す。DEC-0021 の補足）、上の規約の定めは外部公開の前に要る。

**資料に固有の確認**（写真・資料の著作権、写っている人の肖像権、他人が撮った写真の扱い）は、上とは分けて、資料の機能（二次開発）を作る前に行う。

## 13. 事業者・団体等の扱い

MVP では一般のユーザーと同じユーザーモデルとして扱う。事業者専用の機能や専用の投稿画面は設けない。

将来、事業者本人からの情報、自治体・団体等からの情報、地域に詳しいユーザー、資料を根拠とした Post 等を識別できる余地を残す。投稿者・Post の一般的な重み付け・信頼度のスコアは MVP に入れない。成立の判断に投稿者の権限・信頼性を使うかは [Issue #46](https://github.com/ex-day/platform/issues/46) で決める。

## 14. MVP の対象外・二次開発

### 二次開発の筆頭：資料

資料（古写真・地図・文書）は早めにやりたい（人の判断、2026-11-14）。C（今昔）の「昔の側」の入口であり、「この写真の場所はどこ？」は強い参加のきっかけになる。MVP から外す理由は、写真の権利・肖像の確認、資料のページ、撮影場所の候補と採用の流れが増えるため。

資料は企画に近い面がある：どちらも自分のページを持ち、そこに人が集まって話す入口になる。違いは中身で、企画は作った人の意図と並び、資料は写真そのものと「どこ？いつ？」の問いである。二次開発の整理では、この共通点を画面と運用で生かせるかを検討する。

論理設計（Media、PostMedia、DiscoveryMedia、撮影場所の場所の候補と採用）は v0.2 で用意済み。

### 1.5次開発（ベータ公開の直後）

- **運営用の MCP サーバー**：Claude・ChatGPT 等とのチャットで指示して、結果を取得したり、登録・操作したりできるようにする（「今日自動で成立した Discovery を見せて」「この3件は統合して」「この会話の内容で Discovery を登録して」）。見本の Discovery など、運営による **Discovery の登録**もここでできるようにする（人の判断、2026-11-15）。ベータ公開の前提条件にはしない（人の判断、2026-11-15）。具体的な機能の範囲と、変える操作の承認の方式は 1.5次開発で決める。Sites を使うかは未定
- 接続の方式の候補（2026-11-16 の人の判断。今は決めない）：既存の運営の API 経由、参照用の GraphQL、踏み台（SSH・SSM 等）経由の読み取り専用の DB 接続。DB を外部に公開しない。更新は原則として、業務の処理・権限・判断の記録を担保する API を使う
- 検証の意義：運営の管理機能を足すだけでなく、AI と動的な UI で専用の管理画面をどこまで代わりにできるか、逆に専用の UI が要る業務は何かを、実際の運用で確かめる。ただし MVP の設計・実装の範囲は広げない
- 検討の前提とする歯止め（AI が読むのはユーザーの投稿なので、投稿に仕込まれた指示（プロンプトインジェクション）で操作されないようにする）：読むだけの操作と変える操作を分け、変える操作は人がその場で確かめてから実行する。変える操作は戻せるものに限り、消す操作は出さない。判断の記録に「主体＝運営（AI 経由）」と承認した人を残す。運営の権限は Cognito の運営のグループで分け、AI 用の鍵は範囲と期限を絞る

### 二次開発（整理してから入れる）

- 企画：提案を取り込む専用の流れ、過去の並びを再現して見る専用の画面（継続検討）、似た企画の案内
- 退会したときの扱い：企画・Post・資料をどう残すか・消すか（企画はそのまま残す。DEC-0021 の補足）。システムの仕組みだけでなく、利用規約の話でもある（退会後も投稿を表示し続けてよいか、作った人の表示、削除の求めへの応じ方）。自動の処理は二次開発で整理する。規約の定め（退会後の表示の継続、投稿者の表示、削除の求めへの応じ方）は外部公開の前に要る（12節）
- Discovery の派生・統合・関連の判断の仕組みと、Discovery への提案の受付。将来は**ユーザーの参加**を検討する方向とする（人の判断、2026-11-14）：閲覧・参加した人が「これとこれは同じ話では？」「これは別の発見では？」と提案・声を寄せ、判断の材料にする。誰が確定するか（運営、規則、参加した人の声の集まり）、誤った統合を防ぐ歯止め、統合を戻す流れは、論理設計の提案（Proposal）・関係の候補・可逆の統合（DEC-0020 決定10）を土台に整理する
- 通知の配信
- 出来事（豪華客船の寄港、祭りの開催日などの単発の予定）

### 後続検討（やるか・やる時期を含めて決める）

- **対立する説があることの目印**（案。2026-11-16 の人の発案）：会話の中に対立する説・異論が出てきたとき、もとの投稿や Discovery に「ほかの見方もあります」「別の説が寄せられています」のような目印を出す。ボタンで付けるのではなく、対立する説（別の Finding。論理設計 5.2節）が出てきたことから ex-day が導いて付ける。目印を押すと、異論を書いた投稿へ進める。Discovery に付いた目印は、自動で成立した Discovery の見直し（F12）のきっかけにもなる。言葉は、もとの投稿が誤りだと見えないように柔らかくする。**時期・条件・対象の違いで両立する説（「昔は○○だった」と「今は△△」、春と秋の話など）を、対立と取り違えないこと**も検討事項とする。具体的な見分け方と、やるか・やるならいつ（二次開発か、それより後か）は後続で決める

### MVP の対象外

- 行動からの興味の推定（UserInterest のシステム推定）と、高度なパーソナライズ
- あとから直す手段のない、Discovery の完全自動の生成・運用（MVP の自動の成立は、事後の見直しと直しを前提にする）
- 寄り道の速達列車（poc#44）、駅以外の起点、時刻表を使った経路、高度なナビゲーション
- 事業者・自治体・団体向けの機能
- 歴史情報の場所・年代の高度な検証
- 既定を地図にする設定（DEC-0022 決定6）
- タグ（投稿の「#青柳」。DEC-0009 決定10）。タグで表していたものは、会話から取り出す価値・Subject と重なる（人の判断、2026-11-15）
- 投稿の直後の、似た Discovery・会話の案内（F03）。投稿の直後は場所の共有の誘いを出すので、案内を重ねない（人の判断、2026-11-15）
- フォロー・メッセージ等のソーシャルの機能

## 15. 主要ユーザーフロー

### 寄り道から発見に出会う

TOP の小さな地図、またはヘッダーの「寄り道」
→ 起点と使える時間を入れる（スマホでは現在地の近くの駅を起点の候補にする）
→ 寄れる場所と「そこで何分過ごせるか」、寄り道先のまとまりを見る
→ 場所のページ・Discovery のページを開く
→ 行ってみる／「話す」で体験を話す

### 企画から話す

TOP の企画の枠（「みんなの知ってる急坂はどこ？」）
→ 企画のページで並びと根拠を見る
→ 企画そのものの会話に「この坂も入れて」と書く、または項目の場所の会話を始める（入口＝企画、場所は項目から決まる）
→ 作った人が並びを直す／会話から Discovery が成立する

### 場所を決めずに話す

ヘッダーの「話す」
→ 本文だけを書いて投稿する（投稿確定時にログイン）
→ 投稿直後の照合で候補があればワンタップで確かめる／なければ地図・近くから選ぶ／「あとで」「共有しない」
→ 場所未定の会話は「このあたりで探している人がいます」「探しています」で周りの人に届く
→ 返信で場所が分かり、採用される
→ 「自分の話」で返信と、分かってきたことを見る

### 場所のページから話す

場所のページの「話す」
→ 入口＝この場所の会話が始まる（場所は始まりの時点で採用される。誘いは出ない）
→ 返信が集まり、わかってきたことが見える
→ 解析で Discovery が自動で成立し（あとから運営が見直せる）、場所のページ・TOP・寄り道に出る

### 自分の番付を作る

企画の枠の「こんな番付、作ってみませんか？」または企画の一覧
→ 型・表題・呼びかけを入れ、項目の場所を選んで並べる（ログインが要る）
→ 暫定公開される（事後チェックの対象）
→ 企画そのものの会話に声が集まり、作った人が並びを直す

## 17. MVP の検証項目

- 初期（Discovery が少ない）でも、TOP・寄り道・企画から、人が場所のページ・Discovery のページへ進むか。再訪するか
- 寄り道の結果（寄れる時間、まとまり）が、使える時間に見合う提案として受け取られるか。移動時間の目安の誤差が許容されるか
- 企画の会話・企画をきっかけにした会話が、どれだけ生まれるか。ユーザーの企画がどれだけ作られ、声が集まるか。認定のように受け取られていないか
- 場所の入力を求めない投稿で、場所が決まる割合（入口・照合・誘い・周りの人のどれで決まったか）。誘いに答える割合、断る割合
- 場所未定の会話・問いに、返信と回答がどれだけ返るか。届くまでの時間
- 会話から自動で成立した Discovery の数と、そのうち事後の見直しで取り消し・付け替え・統合された割合、直す手間。成立した Discovery が、場所のページ・TOP・寄り道から見られているか
- 興味を登録していない人が、知らなかった発見に出会えているか（Reaction・閲覧の広がり）
- 解析（バッチ）の遅れ・費用が、運用の予算に収まるか（DEC-0018）
