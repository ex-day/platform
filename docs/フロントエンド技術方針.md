# フロントエンド技術方針

## 位置づけ

- 本方針は `各種設計資料作成方針.md` のワイヤーフレーム作成フローのうち、Figma中心の想定（Figmaへの登録→Figma AIによる修正）を見直すにあたって、フロントエンド側の技術構成を先に確定しておくためのもの。
- ワイヤーフレーム段階で確認したいことを「ビジュアルデザインの精度」から「画面遷移・操作性の確認」に重点を移すため、Figma AIではなくHTML/Reactによる動くモックを採用する。
- ここで決めるのは、モック〜実装初期の一貫性に影響する技術選定に限る。API接続方式など、実装が進んでから確定すればよい事項は対象外とする。

## 決定事項

### フレームワーク: Next.js（App Router）

- ex-dayは「発見（Discovery）」を人に共有する性質のプロダクトであり、個別Discovery詳細ページのOGP・SEO・SSRへの対応を見込んで、素のReact SPAよりNext.jsを採用する。
- ファイルベースルーティングなど規約が強いフレームワークを採用することで、Codex / Claude / その他AIそれぞれにモック・実装を行わせた際のディレクトリ構成・実装方針のブレを抑える。
- `api` は別ディレクトリで管理する前提のため、Next.jsのAPI Routes機能は現時点では前提としない（将来的にBFFとして使う可能性は残す）。

### コンポーネント構成: 設計書のコンポーネントIDを一次的な分類キーとする

- Atomic Design（atom / molecule / organism）のような汎用的な粒度分類は、`docs/ui/components/C01`〜`C18` の分類軸と一致しないため、今回は採用しない。
- `docs/ui/components/C0X-xxx.md` と1対1で対応する形で、`components/C0X-xxx/` のようにコンポーネントIDをディレクトリ名に用いる。設計書とコードの対応を機械的に照合できるようにするため。
- コンポーネントIDは使い切り（append-only）とし、設計書確定後も番号の振り直し・再利用は行わない。既存IDの指す内容を変えないことで、過去のIssueやドキュメント中の番号参照が将来にわたって有効であり続ける。
- ディレクトリ名にコンポーネントIDを付与する目的には、設計書とコードのトレーサビリティに加えて、`docs/ui/components/` 配下の一覧と `components/` 配下のディレクトリ一覧を突き合わせることで、実装漏れを機械的に確認できるようにする狙いも含む。
- 設計書のC番号に対応しない汎用的なUI部品（ボタン・入力欄・アイコン等）は `components/primitives/`（仮）に分離する。
- 「Components定義（C0X）にない＝すべて`primitives/`」ではない。次の3区分で判断する。
  - 汎用的でドメインに依存しないUI部品（ボタン・入力欄・ダイアログ等、主にshadcn/ui由来） → `components/primitives/`
  - ドメイン上は意味を持つが設計書にまだ定義がないもの（例：一覧が0件のときの表示など） → 無名のコンポーネントとして実装せず、先に設計書側へ新しいコンポーネントとして追記しC番号を付与してから実装する。実装漏れ確認の仕組みを機能させ続けるため。
  - ドメインにもUI部品カタログにも属さない、純粋なレイアウト・構造要素（ページ全体のラッパー、グリッド等） → `components/layout/`（primitivesとは別枠）
- shadcn/uiのCLIは既定で `components/ui/` に生成するため、`components/primitives/` を採用する場合は `components.json` の生成先を明示的に設定する（未設定のまま実装を始めると配置がAIによってブレるため）。
- コンポーネントID（C0X）はディレクトリ名にのみ用い、コンポーネント自体の名前（エクスポート名・呼び出し名）には含めない。例：`components/C03-discovery-card/DiscoveryCard.tsx` を `DiscoveryCard` としてエクスポートする。IDは振り直さない運用にしたが、呼び出し名は`DiscoveryCard`のような自然な名前の方がJSX上で読みやすく、AIによる実装間でも表記が揺れにくいため。ファイル冒頭に対応する設計書へのコメント（例：`// see docs/ui/components/C03-discovery-card.md`）を残すことで、ファイル単体でもトレーサビリティを確保する。

### スタイリング: Tailwind CSS

- 「動くワイヤーフレーム」として早期に状態を伴うUIを組む必要があるため、CSS設計を都度検討するコストを避け、Tailwind CSSを採用する。
- Next.js・shadcn/ui等の周辺エコシステムとの親和性が高く、複数AIが実装した場合もスタイルの記述方法が揃いやすい。

### UIコンポーネントライブラリ: shadcn/ui

- ボタン・ダイアログ・ドロップダウンメニュー等の見た目や基本的な操作性（フォーカス制御・キーボード操作等）は、自分でデザイン判断をせずに済むshadcn/ui（Radix UIベース）を採用する。
- shadcn/uiは依存パッケージとしてではなく、コンポーネントのソースコードをリポジトリへコピーする方式のため、`components/primitives/` 配下にそのまま配置する形で運用する。
- 設計書コンポーネントとの対応例：C07-dropdown-menu → DropdownMenu、C08-login-dialog → Dialog、C10-reaction-button → Button、C06-search → Input / Select。個別の対応は各実装issueで確認する。

## 各種設計資料作成方針.md との関係

- `各種設計資料作成方針.md` の「ワイヤーフレーム作成」フロー（Figmaへの登録→Figma AIによる修正）は、本方針により見直しの対象となる。同ドキュメントの更新は別途検討する。

## 検討事項

- 設計書のC番号コンポーネントとshadcn/uiプリミティブの対応関係は、実装issueごとに確認・記録する（本方針では一律には定めない）。
- Next.jsのサーバーコンポーネント / クライアントコンポーネントの使い分けについて、AIへの指示時に明示するルールが必要か検討する。
