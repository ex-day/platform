# ex-day 設計レビュー（要求仕様v0.3 × ドメイン論理設計書v0.5 × 論理エンティティ設計書v0.1 × MVPスコープv0.2）

- レビュー実施日：2026-09-15
- 対象：`ex-day_requirements.md`(v0.3) / `ex-day_domain_model.md`(v0.5+追補) / `ex-day_logical_entity_design.md`(v0.1) / `ex-day_mvp_scope.md`(v0.2)
- 位置付け：4資料の内容から読み取れる論点整理であり、決定事項ではない。画面定義・コンポーネント定義の主筆は引き続き人間側という前提に沿い、ここでは「決めておくとワイヤーフレームが描きやすくなる論点」を提示する。

## 総評

4資料は相互参照が丁寧に保たれており、要求仕様のシナリオ番号・節番号がドメイン論理設計書・MVPスコープの記述にそのままトレースできる状態になっている。特に以下は一貫性・充足度が高い。

- 中核四概念（User/Discovery/Contribution/Reaction）の責務分離と、Discoveryの「成立と事実確定の分離」「成長 vs 派生」の区別は、要求6・7・13・14節の狙いを論理設計・MVPスコープまで一貫して落とし込めている。
- 品質評価（星評価・ランキング等）を明示的に対象外とする方針（要求25節周辺の「掲示板/SNS/Q&Aにしない」という狙い）が、ドメイン論理設計書・MVPスコープ双方に確定事項として重複して明記されており、後戻りしにくい形になっている。
- Scenario 06（未知の興味発見）とScenario 07（生麦の派生）がMVPの代表シナリオとして選ばれ、小机城址（成長型）と浜松町（疑問からの成立型）が補助シナリオとして論理設計書にも対応付けられている。要求仕様のScenario 04・05（団体・事業者）が中核外・将来拡張として明示的に切り離されている点も、ドメイン論理設計書9.5節・MVPスコープ12節・13節で足並みが揃っている。

一方で、「論理設計としては成立しているが、MVP画面仕様の入力・表示項目としては明記されていない」ため、ワイヤーフレーム段階で手が止まりそうな箇所がいくつかある。これが今回のレビューの中心的な指摘になる。

## 1. 要求充足性：整合が取れている主な箇所

- **Context/Discovery/Action全体構造**（要求2節）：ドメイン論理設計書2章で踏襲され、MVPスコープ3章の基本情報モデルにも反映されている。
- **「今・ここ」を基本としつつ条件変更可能**（要求3節）：SearchContext（ドメイン論理設計書5.1節、論理エンティティ設計書7.3節）が非永続Value Objectとして定義され、MVPスコープ4章の一覧画面仕様と整合している。
- **ジャンルで分断しない**（要求6節）：Theme（粗い入口）とSubject（統制された意味概念）の役割分担（ドメイン論理設計書5.7節）で対応。
- **疑問をコンテンツとして扱う／Q&Aと異なる体験にする**（要求13・14節）：Discoveryの成立条件が「疑問からでも成立可」であることが3.2節・4.5節で確定事項化され、浜松町シナリオ（7A節）で具体的に検証されている。
- **固定ロールを持たせない**（要求10節）：User定義（ドメイン論理設計書3.1節、論理エンティティ設計書4.1節）で明記。
- **興味を持っていないユーザーも対象**（要求9節、Scenario 06）：UserInterest・Themeを任意とする設計と、MVPスコープの検証項目が対応している。
- **情報の出所・信頼性の表現**（要求24節）：Source／Evidence／ContributionOrigin／Discoveryの知識状態という4つの概念に分解されており（ドメイン論理設計書5.11節）、単純な人気・件数で事実の信頼度を代替しない原則も明記されている。
- **投稿可能＝推薦ではない**（要求25節）：Discoveryの論理属性に「公開・推薦上の状態」を成立状態と別枠で持たせている（論理エンティティ設計書4.2節）。

これらは論理レベルでは要求を満たす設計になっていると評価できる。

## 2. 要求に対して弱い・意図的に見送られている点

以下は「モデルの欠陥」というより「要求はあるが、現時点の資料では対応方針が明示されていない、または意図的にMVP対象外とされている」項目。後続資料に反映すべきかどうかの判断材料として整理する。

1. **移動経路・複数地点（要求4節、Scenario 01）**：PlaceはPoint/Areaのみが確定区分で、複数地点や経路は論理エンティティ設計書7.1節で「要検討」のまま。Scenario 01（出張帰りに寄り道）はMVPスコープ15節の代表シナリオに含まれておらず、対象外という判断は一貫しているが、その旨がMVPスコープ本文には明記されていない。要求仕様には要求として残っているため、「Scenario 01は現時点でMVP対象外」という判断を文書上にも残しておくと、後で読み返す人（自分自身を含む）が混乱しにくい。
2. **疑問と詳しい人をつなぐ（要求15節）**：UserInterestという受け皿はあるが、それを使った通知・マッチングはMVPスコープ9章で「将来拡張」に位置付けられている。要求15の狙い（詳しい人が疑問を発見できる）は、MVPでは「一覧を能動的に探索すれば出会える」という間接的な充足に留まる。この割り切りが要求の意図と乖離しないか、一言だけ確認しておく価値がある。
3. **ex-dayによる編集／オープンデータ由来のコンテンツ（要求18・19・20節）**：ContributionのEntity属性は「提供User」を前提にしており（論理エンティティ設計書4.3節）、運営自身が初期コンテンツを投稿する場合や、個人に紐づかないオープンデータを取り込む場合の「提供者」の扱いが未定義。MVPスコープ1章は「初期の運営側コンテンツは横浜周辺を中心に用意する」と明言しているため、この運営投稿の主体（運営アカウント？個人以外の主体？）をどう表現するかは、Contribution一覧・情報提供者表示に直結するため早めに決めておいた方がよい。
4. **公式情報の識別（要求21節）**：本来の情報提供者（事業者・団体）が後から参加して公式情報を追加する、という循環自体はContributionの仕組みで表現可能だが、「これは公式情報である」という識別属性は論理エンティティ設計書には見当たらない（MVPスコープ12章では明示的に将来拡張・対象外）。整合はしているが、Discovery詳細画面で「情報提供者」を表示する際に一般ユーザーと事業者を区別しない前提でよいか、確認事項として残る。

## 3. ワイヤーフレーム着手前に詰めておくと良い論点（優先度順）

ここが今回のレビューで一番実務的に効くと考える部分。論理設計としては矛盾していないが、「画面に何を置くか」を決めるには情報が足りない、または資料間で温度差がある箇所。

### 優先度：高（決めないと入力・表示項目が描けない）

1. **歴史的時間（年代・時代）の入力欄がMVP画面仕様に明記されていない**
   要求5節は「年代・時代・推定期間・年代不明」を時間概念として明確に求めており、ドメイン論理設計書5.10節・論理エンティティ設計書7.2節もTimeExpressionを「歴史的時間」と「季節・反復時間」の2系統に分けて確定事項としている。ところがMVPスコープ6章（知識追加画面）・7章（新規Discovery投稿画面）の「入力情報」欄はどちらも「季節・時間帯」のみを明記しており、年代・時代の入力欄が見当たらない（「その他Context」に含める想定なのか不明）。小机城址（中世）・生麦（昔の暮らし）・浜松町（過去の道路面）はいずれも歴史的時間が主題の核であり、この入力欄がないままワイヤーフレームを描くと、代表シナリオを実現できない画面になりかねない。少なくとも自由記述レベルでよいので、歴史的時間の入力欄を明示的に追加するかどうかを先に決めた方がよい。

2. **Discoveryの知識状態（問いかけ中／調査中／情報不足／複数説あり）を表示するUI要素がMVP画面仕様にない**
   ドメイン論理設計書3.2節・4.2節は「成立と事実確定は別」「知識状態は排他的な一覧ではないが状態を持ちうる」ことを繰り返し確定事項としており、これはex-dayが完成記事メディアやレビューサイトと違う体験であることの中核部分。しかしMVPスコープ5章（Discovery詳細画面）の表示情報一覧には知識状態に相当する項目が明記されていない。「答えが出ていないDiscoveryでも堂々と一覧・詳細に出す」という要求9・13節の狙いをUI上で伝えるには、最低限「問いかけ中」等のラベル表示が要ると思われる。

3. **Reactionの具体的な種別が未確定のまま**
   ドメイン論理設計書3.4節・論理エンティティ設計書4.4節はReaction種別を意図的に「仮の例」に留めており、MVPスコープ3章も「将来的に検討」としている。ボタンやアイコンを画面に置くには、たとえ暫定であっても2〜4種類程度の具体的なラベル（例：気になる／行ってみたい／知らなかった、等）を先に仮決めしておく必要がある。バックエンド側の柔軟性は保ったまま、UI用の暫定セットだけ先に決める、という進め方が資料の意図と矛盾しないはず。

### 優先度：中（画面の有無・範囲に関わる）

4. **DiscoveryDecision（既存へ統合／新規／関連の判断）を行う画面がMVP優先画面リストに含まれていない**
   MVPスコープ7章は「新規Discoveryの形成・派生はMVPでは人間が判断し、手動運用でも成立させられるものとする」と明記しており、これは論理エンティティ設計書6.1節のDiscoveryDecisionに対応する。しかしMVPスコープ14章の優先画面リスト（7画面）には、この判断を行うための画面（運営向け管理画面など）が含まれていない。実証実験でこの判断を「DBを直接触る」「別の管理画面を作る」「新規投稿画面の一部機能として作る」のどれで行うかによって、ワイヤーフレームの対象範囲が変わるため、着手前に決めておくと手戻りが少ない。

5. **UserInterestの可視化・本人による確認／訂正のUI範囲**
   ドメイン論理設計書3.1A節・5.3A節は「UserInterestは内部プロファイルではなくユーザーに見える形で返す」「本人が確認・訂正・否定できる」ことを確定方針としている。一方でMVPスコープのScenario 06検証観点は「新しい興味への気づきは実証実験での聞き取りやアンケートで確認する」としており、対応する専用画面がMVPスコープ14章の優先画面リストにない。ドメイン論理設計書の「確定（今回の設計方針）」という強い書き方と、MVPスコープの「UIには出さずアンケートで代替する」という扱いには温度差があるため、ワイレフレーム段階でこの機能をどこまで画面化するか（完全に見送るのか、「自分の投稿」画面に軽く含めるのか）を一度言語化しておくと良い。

### 優先度：低（決めておくと後が楽）

6. **元Contribution一覧の表示順序・関係種別の最小仕様**
   MVPスコープ6章は「会話はContributionのやり取りとして検証し、専用チャットや複雑な返信階層を必須としない」としつつ、具体的な表示順（時系列一覧か、疑問→回答のようなまとまりか）までは踏み込んでいない。論理エンティティ設計書6.2節のContributionDiscovery関係種別も「要検討」のまま。Discovery詳細画面の「元Contribution一覧」をワイヤーフレームに落とすには、最低限「時系列フラット表示でよいか」だけでも仮決めしておくと描きやすい。

7. **Discovery Cardが「情報」ではなく「体験」を伝える表現**
   要求8節は単なる事実提示ではなく「あなたなら今こんな体験ができる」という提案型の見せ方を狙いとして掲げているが、MVPスコープ4章のCard表示情報（代表写真／要約／場所・距離／季節・時間帯Context）は事実情報の列挙に近い。要求8の狙いを一覧画面でどこまで表現するか（コピーライティングの問題として後回しにするか、ワイヤーフレームの時点で「なぜ今か」を示す要素を入れるか）は、優先度は低いが認識をそろえておくと良い論点。

## 4. まとめ

論理設計としての一貫性・トレーサビリティは高く、要求仕様との対応も概ね取れている。今回見つかった指摘の大半は「モデルが間違っている」のではなく「MVP画面仕様（特にmvp_scope.mdの入力・表示情報リスト）が、ドメイン論理設計書ほど詳細に踏み込めていない」というギャップに起因する。特に優先度「高」の3点（歴史的時間の入力欄／知識状態の表示／Reaction種別の暫定確定）は、ワイヤーフレームの入力項目・表示項目に直接関わるため、着手前に一度結論を出しておくことを勧める。
