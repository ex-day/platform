# ex-day UI設計レビュー（platform/docs/ui: screens / components / functions / user-contribution-usecases）

- レビュー実施日：2026-09-18
- 対象：`docs/ui/user-contribution-usecases.md`、`docs/ui/screens/S01〜S09, S11`、`docs/ui/components/C01〜C18`、`docs/ui/functions/F01`
- 参照した設計条件：要求仕様v0.3 / ドメイン論理設計書v0.5 / 論理エンティティ設計書v0.1 / MVPスコープv0.2（前回レビュー `design/ex-day_design_review_v1.md` の続き）
- 位置付け：画面定義・コンポーネント定義の主筆はご自身という前提のもと、粗いワイヤーフレーム作成前に確認しておくと手戻りが減ると思われる論点を、根拠となるファイル・節を添えて整理したもの。決定事項ではない。

## 総評

前回レビュー（ドメイン論理設計書〜MVPスコープの突合）で指摘した論点のうち、いくつかはこのUI設計で具体的に解消・前進している。特に、Contributionを「短文SNS的に気軽に投稿し、後からAIが候補を抽出して人間が確認する」という体験（`user-contribution-usecases.md`、S04→S11）は、歴史的時間・場所の曖昧さを許容しつつ構造化するという要求（要求16節、ドメイン論理設計書4.4節）に対する具体的な回答になっている。また、S09/C17で「投稿がDiscovery形成・Value向上にどう使われたか」を投稿者に返す仕組みができており、要求22節（情報提供者への価値）に対する回答が前回より具体化された。

一方で、S03（Discovery詳細）を中心に、ドメイン論理設計書が確定事項としていたいくつかの区別（派生 vs 関連、知識状態）が画面定義上は区別されずに一つの表示項目にまとまっている箇所があり、これは代表シナリオ（特にScenario 07：生麦の派生）の核心部分が画面上で成立するかに直結する。また、C03/C12/C13/C17に現れる「Value（価値／魅力）」という概念は、これまでの4資料（要求・ドメイン・論理エンティティ・MVPスコープ）のどこにも定義がなく、今回はじめて画面層に現れた新しい概念に見える。ほぼ全画面の中心的なデータ項目になっているため、ドメイン側への位置付けの明文化を先に済ませておくことを推奨する。

## 1. 代表シナリオが画面定義上「通るか」の確認

### 1.1 Scenario 06（未知の興味発見型）：概ね通る

S01（TOP）→ C11 discovery-sections（F01でセクション取得、PCは複数section／モバイルはタブ）→ 各C05内のC04/C03カード群 → カード押下でS03へ、という導線は、興味未指定・検索語なしでジャンル横断的に発見できるという要求（要求9節、MVPスコープ4章）を満たしている。S03のC13「今のおすすめ」＋「おすすめ理由(recommendationReason)」は、要求8節が求めていた「単なる情報ではなく体験の提案」という見せ方に、前回レビュー時点（Card表示情報が事実の羅列に近いという指摘）よりも具体的に応えているように見える。C10リアクションで関心表明もできる。

ただし後述1.3・2.4の通り、「情報不足時のCTA」がS02/S03のどこにも見当たらないため、「知らなかった話題を見る」体験は通るが、「気になったのでその場で知っていることを足す」への接続がやや弱い可能性がある。

### 1.2 Scenario 07（生麦・青柳：Discovery形成・派生型）：核心部分に要確認あり

一連の流れをS01〜S11で追うと、次のようになる。

1. Discovery A「生麦周辺はかつて漁師町だった」をS03で閲覧する。
2. 複数ユーザーがC07「新規知識登録」からS04（type=知識/疑問、本文・写真・場所・時間・季節を任意入力）→保存→S11（場所・時間・内容分類の候補確認、「関連しそうなDiscovery」候補からAを選択 or 「関連付けずに進む」）という流れでContributionを積み上げる。ここは`user-contribution-usecases.md`の設計方針（自然文投稿→AI候補提示→人間確認）とも整合しており、個々のContribution投稿自体は問題なく通る。
3. 蓄積したContributionから「生麦の食文化」という別の意味のまとまりを認め、Discovery B を成立させ、AからBへの派生（DiscoveryRelation）として関連付ける工程がある（MVPスコープ7章、ドメイン論理設計書4.5節）。**この「Discoveryを新規に成立させる／DiscoveryRelationを設定する」ための画面が、S01〜S11のどこにも存在しない。** MVPスコープ7章は元々「検証は運営による手動操作でも成立させられるものとする」としているため、画面が無いこと自体は既定路線と解釈できるが、その前提が今回のUI設計一式に明記されていないため、意図的な省略か検討漏れかが読み取れない状態になっている。
4. Discovery Bが成立した後、**S03の「関連Discovery」（→C03を0..n）は一つの汎用リストであり、「Aからの派生（派生元／派生先）」と「Subjectを介した意味的関連」を区別する表示になっていない。** ドメイン論理設計書4.3節・8章17項は明示的Discovery RelationとSubject由来の意味的関連を区別することを確定事項としており、MVPスコープ5章の元の表示情報リストでも「人が設定した派生元・派生先Discoveryへの導線」は「その他のContribution提供者」等と並ぶ独立した表示項目だった。現在のS03定義のまま画面化すると、Bを見たユーザーが「Bは何と、どう繋がっているのか（派生なのか、単に似ているだけなのか）」を判別できず、Scenario 07の「Aは漁師町の意味を保ちつつ、Bが派生先として関連付く」という体験の核（MVPスコープ15章の成立させる体験、論理エンティティ設計書10.3節の検証結果）が画面上では伝わらない可能性が高い。

**この2点（Discovery成立・派生設定のワークフローの明記、S03での派生／関連の表示区別）は、粗いワイヤーフレームを描く前に方針を決めておくことを強く勧める。** ワイヤーフレームの段階で「関連Discovery」を1ブロックとして描いてしまうと、後から「派生元/派生先」と「関連」を分けるレイアウト変更が手戻りになりやすい。

### 1.3 補助シナリオ：小机城址（成長型）：概ね通る

既存Discoveryへ複数ユーザーが知識を積み増す流れ（S04→S11で毎回既存の「小机城址」候補を選択）は無理なく通る。C12/C13のValueが時間・季節条件を持てる設計になっているため、「城に興味がある人には城跡として、公園を探す人には公園候補として」異なる見え方をする、というドメイン論理設計書10.1節の検証内容も、Value単位での出し分けとして表現できそうに見える（ただしこの対応関係もVAlue概念が正式に定義されて初めて確認できる。2.2節参照）。

### 1.4 浜松町（疑問からの成立型）：Discovery成立の扱いが同じ論点にかかる

疑問の投稿自体（S04で type=疑問、写真添付→S11で場所・時間候補確認→関連候補なしなら「関連付けずに進む」で保留）は問題なく通る。ただしその疑問が独立したDiscoveryとして成立する工程は1.2と同じく画面定義に現れないため、「Discoveryは問いかけ中のままでも成立できる」という確定事項（ドメイン論理設計書3.2節）が、どの画面操作を経て実現されるのかが今のままでは追えない。

## 2. 設計条件との整合性チェック（前回レビューからの差分を中心に）

### 2.1 前回指摘の解消状況

- **歴史的時間の入力欄**：S04/S11に「時間（contribution_time）」「季節（contribution_season）」が独立項目として存在し、`user-contribution-usecases.md`も「投稿日時」と「出来事の対象時点」を明確に区別している。前回の懸念（入力欄が無い）は解消したと言ってよい。ただし2.3で述べる通り、粒度の詳細（時間帯）は要確認。
- **体験としての見せ方**：C13「おすすめ理由」の追加により、要求8節が求める「あなたなら今こんな体験ができる」という提案的な見せ方への回答が具体化された。前回指摘（Cardが事実の羅列に近い）は改善方向にある。
- **投稿の成果の可視化**：S09の状態フィルター／C17「知識・疑問の成果」により、UserInterestの可視化ほどではないが、投稿者への価値還元（要求22節）を扱うUIが明確になった。

### 2.2 「Value（価値／魅力）」という新概念の位置付けが未確定

C03（discovery_value）、C12（discovery-value：subject/value/picture/条件[time,season]/body）、C13（discovery-recommendation：C12＋おすすめ理由）、C17（value_impact）と、ほぼ全ての画面がこの「Value」に依存している。しかし要求仕様・ドメイン論理設計書・論理エンティティ設計書・MVPスコープのいずれにも「Value」という概念は登場せず、最も近い概念は「Discovery Subject」（ドメイン論理設計書5.5節：Discoveryは複数のSubjectで構成される意味情報を持つ）である。

- ValueはDiscovery Subjectの各要素を、時間・季節条件付きで個別に見せるための表示単位なのか。
- それとも、Subjectとは別に新設するEntityなのか（だとすると論理エンティティ設計書への追記が必要）。
- 「今のおすすめ」と「その他の魅力」の振り分け条件（現在の時間・季節と条件が合致するかどうか、と推測される）は、ドメイン論理設計書のどの確定事項に対応するのか。

論理エンティティ設計書12章は「要検討事項を物理都合だけで確定した場合は、論理設計へのフィードバックと決定記録を残す」ことを引き継ぎ条件として明記している。Valueがほぼ全画面の中心データになっている以上、ワイヤーフレームを本格的に描き始める前に、この対応関係を一度言語化して論理設計側にも反映しておくと、後続の画面が総崩れになるリスクを避けられると思う。

### 2.3 時間帯（朝／昼／夕方／夜）の粒度がどこにも見当たらない

MVPスコープ6章は季節・時間帯を並列に「季節：春/夏/秋/冬/いつでも」「時間帯：朝/昼/夕方/夜/いつでも」という具体的な粒度で挙げていた。現在のS04/S11には「季節（contribution_season）」はあるが「時間帯」に相当する独立項目が無い。ドメイン論理設計書5.10節の「反復時間」には季節・旬・曜日・時間帯等が含まれるとされているため、「季節」フィールドが時間帯も内包する想定なのか、単純に漏れているのかが読み取れない。C06検索の「利用可能時間」は検索側のContextなので、投稿側の時間帯とは別軸。

### 2.4 「情報不足時のCTA」「Discovery文脈を保った知識追加」導線が見当たらない

MVPスコープ4章・5章は、Discovery一覧・詳細それぞれに「情報が少ない場合に知識を促すCTA Card」を明記しており、MVPの検証項目にも「情報不足時のCTAから新規投稿につながるか」を挙げていた。現在のS02（discovery-list）、S03（discovery-detail）の表示項目・アクションにはこのCTAが見当たらない。また、S03から新しい知識を追加する専用の導線（「知識を追加する」ボタン等）も見当たらず、Contribution作成への入口はC07ドロップダウンメニューの「新規知識登録」（Discoveryの文脈を持たない汎用入口）のみに見える。

`user-contribution-usecases.md`の「まず自然文で気軽に投稿し、後からAIが候補を提示する」という設計方針からすると、この省略は意図的（どのDiscoveryから来たかに関わらず、S11の候補マッチングで結び付ければよいという考え方）である可能性が高い。その場合でも、以下は確認しておくと良い。

- S03から「この発見について知っていることを教えてください」のように、あらかじめDiscoveryが分かっている状態でS04に遷移する経路を残さなくてよいか（S11での候補選び直しの手間が発生する）。
- MVPの検証項目にある「情報不足時のCTA」自体を今回のUI設計で意図的に落としたのか、後続で追加する想定かの整理。

### 2.5 Discovery詳細での情報提供者表示が深い階層に移動している

MVPスコープ5章は「Discovery作成元の情報提供者」「写真提供者」「その他のContribution提供者」をDiscovery詳細画面の主要表示項目として挙げていたが、現在のS03には該当項目がなく、投稿者情報（C14の「投稿者」フィールド）を見るにはS03→S06→S05と2階層掘り下げる必要がある。要求22節（「自分を探していなかった人に発見してもらえること」という提供者への価値）を考えると、Discovery詳細の時点で「誰が教えてくれたか」がある程度見える方が、その価値を伝えやすいと思われる。意図的な簡略化であれば問題ないが、確認しておくと良い点として記載する。

### 2.6 Discoveryの知識状態（問いかけ中／調査中／情報不足／複数説あり）を示すUI要素が引き続き見当たらない

前回レビューの指摘と同じ状態が続いている。S03、C12、C13のいずれにも、Discoveryが「まだ答えの出ていない話題」であることを伝えるラベル・バッジ相当の項目がない。ドメイン論理設計書3.2節・4.2節が繰り返し確定事項としている「成立と事実確定の分離」を画面上で伝える最後のピースとして、优先度は中程度ながら残っている。

## 3. 粗いワイヤーフレーム作成に影響しうる論点（優先度順のまとめ）

1. **（高）S03「関連Discovery」で、明示的な派生（派生元/派生先）とSubject由来の関連を区別する表示にするかどうか。**　Scenario 07の核心的な体験に直結するため、レイアウトを分ける前提で進めるかを先に決めておきたい。
2. **（高）「Value（価値／魅力）」がDiscovery Subjectとどう対応するかの言語化。**　ほぼ全画面の中心データであるため、ここが曖昧なまま各画面のワイヤーフレームを個別に進めると、後で表示ロジックの前提が崩れるリスクがある。
3. **（中）Discovery成立・DiscoveryRelation設定という運用フローを、今回のUI設計一式の前提（MVPでは運営手動運用）として明記しておくか。**　画面が無いこと自体は既定路線だが、その旨がこの資料群のどこにも書かれていないため、初見の人（将来の自分を含む）が「抜けている」のか「意図的」なのか判断できない状態になっている。
4. **（中）Discovery文脈を保った知識追加導線・情報不足時CTAを、今回のAI候補マッチング方式に置き換えて廃止する、という理解でよいか。**　MVPスコープの検証項目と齟齬がないかだけ確認しておきたい。
5. **（低〜中）時間帯（朝/昼/夕方/夜）の粒度をどの項目で扱うか。**
6. **（低）Discovery詳細での情報提供者表示の階層。**
7. **（低）Discoveryの知識状態を示すUI要素。**
8. **（低）ファイル番号のS10欠番。**　実害はないと思われるが、リネーム漏れでないかだけ一応確認。

## 4. まとめ

要求・ドメイン・論理エンティティ・MVPスコープと今回のUI設計群との間で、致命的な矛盾は見当たらなかった。むしろContribution投稿体験（`user-contribution-usecases.md`）や成果の可視化（S09/C17）は、前回レビュー時点の懸念に対する具体的な前進と言える内容になっている。

残っている論点の多くは、「モデルが壊れている」のではなく、「ドメイン論理設計書が区別している概念（派生 vs 関連、知識状態）が、画面定義の時点でひとつの表示項目にまとめられてしまっている」「新しく出てきた概念（Value）の位置付けがまだ言語化されていない」という、上位資料と画面定義の間の解像度の差に起因している。特に1章で述べたScenario 07の派生表現（3.の1番目）とValueの位置付け（2番目）の2点は、粗いワイヤーフレームのレイアウトそのものに影響するため、先に結論を出しておくことを勧める。
