# ex-day AI協働開発ルール v0.1

本書は、AIを設計・実装・レビューに参加する開発メンバーとして利用するための基本ルールである。[Issue #5](https://github.com/ex-day/platform/issues/5)に基づく採用案として作成し、採用と最終mergeは人間が判断する。

## 1. 仕様・設計と作業の記録

仕様・設計のSource of TruthはGitHub上の設計ドキュメントとする。AIへの作業依頼は原則としてIssueを起点にし、目的、対象、参照資料、完了条件を共有する。会話やAIの出力だけで仕様を確定しない。

作業開始時にIssue本文・コメント、関連する設計ドキュメント、対象ディレクトリの作業指示を確認する。参照した資料のパスと基準commitをIssueまたはPRへ記録し、レビュー対象を辿れるようにする。未採用の提案と既存の確定事項を区別する。

リポジトリ内で作業するAIには、ルートおよび対象ディレクトリの`AGENTS.md`を常に適用する。各Issueへ同じ指示を重複して記載する必要はない。利用するAIや作業環境が`AGENTS.md`を自動で参照しない場合は、Issueまたは作業依頼からルートの`AGENTS.md`を参照するよう明示する。

Issue・会話・設計書に矛盾がある場合、AIだけでどちらかを正しいと決めず、該当箇所と影響をIssueへ記録する。人間が方針を決めたら、その判断をIssueへ残し、必要な設計書の更新を同じ作業または明示した後続作業で行う。判断が仕様へ反映されたことを確認できるようにし、会話だけに決定を残さない。

設計書の状態はGit commitとPRで追跡する。独立した手動バージョン番号の更新は必須としない。本書の「v0.1」はIssue #5で指定された初回採用案の呼称であり、全資料に番号管理を追加するものではない。

特に ex-day_requirements.md は、Discovery/Contributionの目的・動機・サービス全体のコンセプト（2軸構造、疑問と知識の位置付け、情報提供者への価値等）を定義する基礎資料である。MVPスコープや個別画面・Componentの詳細設計を進める中で参照が薄れやすいため、Discovery/Contributionの役割分担、投稿動機、疑問と知識の使い分けに関わる判断を行う際は、本資料（特に13〜15章、22章、巻末の利用シナリオ集・サービス全体の循環図）を参照する。

## 2. 人間・Maker・Reviewerの責務

- **人間**：目的・優先順位・仕様・重要なUX・未確定事項の最終判断を行う。レビュー結果を踏まえて採用・修正・保留を決め、最終mergeを行う。GitHub上のAssigneeは当面人間とし、AI専用アカウントは前提としない。
- **Maker**：Issueと既存仕様の範囲で設計案や実装・文書を作成し、適切な検証を行う。成果物、判断理由、検証結果、制約、判断待ち、後続作業をIssue・PRに残す。
- **Reviewer**：問題、不整合、仕様からの逸脱、検証漏れ、改善候補を提示する。仕様決定者ではなく、レビューで新しい仕様を確定しない。指摘には根拠・影響を添え、既存仕様に対する不具合と、新たな提案・人間への質問を区別する。

可能な範囲でMakerとReviewerを別AIにする。担当AIと役割をIssueまたはPRへ記録し、同じAIによる自己点検を別AIレビューと表示しない。別AIを利用できない場合は、その旨と実施済みの確認を記録し、人間が追加レビューの要否を判断する。

### Human Intervention Log（人間介入記録）

人間による介入自体は禁止しない。AIだけでは作業を完結できない場合や、人間の判断・対応が必要な場合は、工程を進めるために必要な介入を行う。その際は、後からAI協働開発の課題と改善点を分析できるよう、介入の種類と理由をIssueまたはPRへ軽量に記録する。コードや文書の変更を伴う作業では原則としてPRへ記録し、それ以外の工程では元Issueへ記録する。同じ内容をIssueとPRの双方へ重複して記載する必要はなく、相互に辿れるリンクがあればよい。

介入の種類は、次を目安とする。

- 設計判断。
- 実装方針の修正。
- コード修正。
- Git操作の代行。
- 環境・権限対応。
- その他。

記録には、介入した人、種類、理由、実施内容、AIの成果物への影響を含める。該当しない項目を埋めるための詳細な報告は求めず、例えば次の形式を利用できる。

```text
Human Intervention
実施者：
種類：Git操作の代行
理由：AIの作業環境からGitHubへpushできなかったため
実施内容：人間が作業branchをpushした
成果物への影響：コードの変更なし
```

第2節で人間の責務として定めた通常のレビュー、採用判断、最終mergeは、それだけを理由に介入記録へ重複して記載しなくてよい。ただし、人間がAIの想定していた作業を代行した場合、成果物を直接修正した場合、または方針・結果を変更した場合は記録する。設計・仕様の決定は第1節および第5節に従って根拠と決定内容も残し、介入記録だけを仕様決定の記録にはしない。

現時点では「AI 80%」等の主観的な寄与率は記録しない。介入の有無を工程の成否やAIの評価とみなさず、種類と理由をIssue・PRから集計し、どの工程・状況で人間の支援が必要になったかを今後のAI協働開発へ応用するための事実記録として扱う。介入記録の有無は、Blocking／Non-blockingの分類、後続Issueの作成条件、PR・mergeによる工程境界を変更しない。

## 3. AIが判断できる範囲と人間へ確認する範囲

AIは、既存仕様とIssueの範囲内で、実装方法、作業手順、ファイル構成の調整、検証方法などを判断できる。既存仕様に照らして明確な誤記・参照切れ・不具合の修正も行える。変更理由と検証結果は残す。

次のような事項はAIだけで確定しない。

- 新しい仕様、ドメイン概念、状態の種類・遷移、データの意味や成立条件。
- 重要なUX、画面の役割、利用者の行動や表示内容を変える判断。
- 設計書やIssueの不足・矛盾、複数の有力な選択肢があり目的や体験に影響する判断。
- 作業範囲・完了条件の変更や、未採用の提案を前提とした実装。

通常の実装上の選択肢が複数あるだけで、すべてを判断待ちにする必要はない。仕様や重要なUXへの影響があるかを根拠に区別する。Reviewerの提案も同じ基準で扱う。

## 4. Issueからmergeまでの基本フロー

1. **Issueを確認する**：目的・完了条件・参照資料・人間の決定を読む。対象ディレクトリの`AGENTS.md`も確認する。作業ツリーに他の作業がある場合は混在させず、第7節に従って作業場所を分離する。
2. **必要に応じて作業branchとworktreeを用意する**：Gitリポジトリの変更を伴う工程では、mainを基準にIssue単位のbranchとworktreeで作業する。branch名とIssueを相互に辿れるようにする。例：`docs/issue-5-ai-collaboration`。この名前を全作業の固定命名規則とはしない。外部artifact等が成果物となりリポジトリを変更しない工程では、branch、worktree、PRを必須としない。
3. **作成・検証する**：Makerが既存仕様の範囲で作業し、必要な検証と自己点検を行う。判断が必要になった部分は第5節に従う。
4. **レビュー可能な形で成果を共有する**：成果物、検証結果、未解決事項をIssueから辿れるようにする。コードや文書の変更はPRにしてIssueと関連付ける。外部artifact等はIssueにリンクと必要な説明を記録する。
5. **別AIによるReviewを行う**：可能な範囲でMakerと異なるAIが、対象commit・差分と参照仕様を確認する。結果をPRまたは関連Issueへ記録する。
6. **人間判断と修正を行う**：既存仕様上の明確な問題はMakerが修正する。仕様・重要なUXに関する提案は人間の判断を待つ。修正後は影響に応じて再検証・再レビューする。
7. **人間が採用を判断する**：人間が完了条件、検証、レビュー、未解決事項を確認して採用を判断する。PRがある工程では人間が最終mergeを行い、AIは自動mergeを含めて実行しない。

設計・Wireframe・Mock・実装を連続して扱う場合の想定フローは次のとおり。工程によって不要なステップは省略できるが、仕様の決定と最終mergeを人間が担う原則は維持する。

```text
人間 + ChatGPT等による設計・壁打ち
  → 設計ドキュメント
  → Design Review Issue → 別AI Review → 人間判断
  → Wireframe Issue → Wireframe生成 → 別AI Review → 人間判断
  → 引き渡し可能ならMock Issueを作成
  → Mock Issue → 作業branch → Mock実装
  → 必要に応じてImplementation Issue → 作業branch → 実装
  → Pull Request → 別AI Review → 人間判断 → 必要なら修正
  → 人間がmerge
```

## 5. 判断待ちの停止・再開

設計書の不備・矛盾や、AIだけでは判断できない事項を発見しても、その事項のための新規Issueは作成しない。まず元Issueへ次の情報を記録し、次工程へ進めるかどうかでBlockingとNon-blockingに分類する。

```text
判断待ち：論点の短い説明
根拠：設計書のパス・節・commit、Issueコメント等
不明点／矛盾：何が決まっていないか
選択肢と影響：各案の仕様・UX・実装への影響。推奨案は提案と明記
停止する範囲：判断に依存する作業
継続できる範囲：判断に依存しない作業
再開条件：人間に決めてもらう内容
```

AIは判断に依存する作業を停止し、独立して進められる調査・修正・検証は継続できる。沈黙、時間経過、レビュー未返信を承認とみなさない。PRを先に作成する場合は判断待ちを明示し、未完了の成果はDraft等で区別する。

- **Blocking**：成果物を確定できず次工程へ引き渡せない事項。元Issueへ判断待ちとして記録し、人間の判断と必要な設計書修正が完了してから該当作業を再開する。
- **Non-blocking**：要検討事項は残るが、現在工程の成果物を確定して次工程へ引き渡せる事項。元Issueへ記録し、人間の確認を得たうえで後続Issueの引き継ぎ事項にも含められる。

すべての要検討事項が解決済みであることは、Issue完了や工程引き渡しの一律の条件ではない。現在工程の成果物が生成され、レビューを経て、残る事項を明示した状態で次工程を開始できるかを判断基準とする。

再開時は、人間の決定と対象範囲をIssue上で確認し、参照commit以降の設計変更・他の作業の更新も確認する。必要な設計書更新、作業再開、検証を行い、判断待ちが解消したことと決定へのリンクをIssue・PRへ記録する。新しい矛盾が見つかった場合は該当部分を再び判断待ちとする。

GitHubへの接続・権限等で記録できない場合は、成果物と投稿予定の内容を失わない形で保存し、未投稿であることを人間へ伝える。接続回復後に記録してから、判断が必要な作業を再開する。ローカル記録を人間の承認の代わりにしない。

## 6. 工程の完了と後続Issueの作成

新規の後続Issueは、問題を発見した時点ではなく、現在工程から次工程へ成果物を引き渡す時点で作成する。次の条件をすべて満たすことを作成条件とする。

- 現在工程で必要な成果物が生成されている。
- Maker以外のAIによるレビューが完了している。別AIを利用できない場合は、第2節に従ってその制約と確認状況が記録されている。
- 人間によるレビューが完了している。
- 残るBlocking事項がなく、AIと人間の双方が「次工程へ引き渡し可能」と判断している。

Non-blockingな要検討事項が残っていても、上記を満たせば後続Issueを作成できる。既存Issueを確認して重複を避け、元Issueと後続Issueを相互に関連付ける。後続Issueには、少なくとも次を明記し、工程間の引き継ぎとして機能させる。

- 前工程Issue。
- 入力成果物と、その参照先。
- 次工程で参照する設計書。
- Non-blockingな要検討事項を含む引き継ぎ事項。ない場合はその旨。
- 次工程の完了条件。

Issueを作成しただけで、その着手・優先順位・納期まで確定したことにはしない。元Issueの完了条件に必要な作業を後続へ移す場合は、単なる引き継ぎではなく範囲変更として人間に確認する。未完了事項を別Issueへ移しただけで完了と報告しない。後続工程がない場合は「後続Issueなし」と記録でき、形式を満たすためだけにIssueを作らない。

## 7. Git・branch・PRの運用

当面はGitHub Flowを採用し、developブランチは設けない。Gitリポジトリの変更を伴う工程では、AIはmainへ直接変更・commit・pushせず、Issue単位の作業branchからPRを経由して統合する。無関係な既存変更を取り込まない。PRは全Issue共通の完了条件ではない。Wireframeのように外部artifact等が成果物となりGitリポジトリを変更しない工程では、PRを必須とせず、成果物へのリンク、レビュー結果、判断、引き継ぎ事項をIssueへ記録する。

### 作業場所の分離

AIがGitリポジトリを変更する場合は、原則としてIssue単位のbranchに対応するGit worktreeを用意し、そのworktree内だけで作業する。人間がIDE等で利用している通常のcheckoutをAI作業に共用せず、AIは通常のcheckout上でbranchを切り替えない。これにより、branchの切り替え、未コミットの変更、未追跡ファイル、複数Issueの作業が同じ作業場所で混在することを防ぐ。

作業開始前に、使用するworktreeの現在branchと、未コミット・未追跡ファイルを確認する。別作業の変更がある場合は編集・移動・削除・commitへ含めず、新しいworktreeへ分離する。既に共有checkoutで作業を開始していた場合も、安全に分離できる時点でIssue用worktreeへ移り、共有checkoutのbranchや既存変更を元に戻す操作は人間の確認なしに行わない。

worktreeを利用できない環境では、独立したclone等、同等に作業場所を分離できる方法を利用する。それもできない場合は、作業を始める前に制約と混在の可能性を人間へ伝え、作業方法の判断を待つ。人間による環境準備やGit操作の代行が必要になった場合は、第2節のHuman Intervention Logへ記録する。

PRのmerge後または作業中止後は、未送信の成果物や必要な記録が残っていないことを確認してから、不要になったworktreeと作業branchを整理する。削除は成果物を失わないことを確認したうえで行い、AIが判断できない場合は人間へ確認する。

commitは変更の目的が分かる内容とし、PRには次を記載する。

- 対象Issue、解決する問題と変更後の動作・運用。
- 変更した成果物と主要な判断理由、参照した設計資料・基準commit。
- 実施した検証と結果。未実施の確認や制約はその理由。
- Maker／Reviewerの担当とレビュー対象commit、レビュー結果または待ち状況。
- 判断待ち・既知の問題・後続Issue。ない場合もその旨を記載する。

文書変更ではIssueの完了条件、既存資料との整合性、リンクや差分を確認する。実装変更では変更に応じたテスト・ビルド・画面操作等を確認する。未実施の検証を成功と書かない。

Reviewerの確認やAIによる作業完了報告は、人間による採用の代わりにはならない。PR作成済み・レビュー済み・人間の採用待ち・merge済みを区別して記録する。Issueを閉じる連携を使う場合も、対象の完了条件を満たすPRであることを確認する。

## 8. 既存方針との関係と運用の見直し

[各種設計資料の作成方針](../各種設計資料作成方針.md)は、設計資料・Wireframe・Mockの工程とComponent採番等の個別方針を定める。本書はIssue・判断・レビュー・Gitによる協働の基本運用を定め、個別方針を置き換えない。[フロントエンド技術方針](../フロントエンド技術方針.md)等の対象分野の資料も併せて確認する。

AIへの入力と出力の記録は[docs/aiの方針](../ai/README.md)を参照する。Issue・PRには判断や成果を辿るための要点とリンクを残す。資料間に不整合があれば、第5節の判断待ちとして扱う。

Issue #5では、この文書自体を作業branchで作成し、PRと別AIレビューを試す。実験で見つかった運用上の課題はIssue・PRへ記録し、既存方針の明確化で済むものは本書へ反映する。新たな運用判断が必要なものは人間へ返す。採用後も、必要に応じてIssueとPRを通じて本書を見直す。

## 9. Decision Log

重要な意思決定とその背景は `docs/decisions/` に記録する。

### 参照ルール

- 現在有効な仕様は各種定義書を正とする。
- 通常の作業では、Decision Logを事前にすべて参照する必要はない。
- 以下の場合に限り、関連するDecision Logを参照する。
    - 定義書だけでは判断理由が不明な場合
    - Issue / PR から関連するDecisionが指定されている場合
    - 過去の判断との整合性を確認する必要がある場合
    - 既存仕様を変更・再検討する場合
- Decision Logと現在の定義に差異がある場合、現在の定義を優先する。
- Decision Logを参照しても判断できない場合は、推測で補完せず確認する。

### 記録ルール

以下のような判断は、必要に応じてDecision Logとして記録する。

- 後続作業で判断背景が必要になる可能性がある
- 複数の選択肢から明示的に方針を決定した
- 将来再検討する可能性がある
- AI・人間間の引き継ぎで背景が失われる可能性がある

すべての会話・判断を記録する必要はない。
