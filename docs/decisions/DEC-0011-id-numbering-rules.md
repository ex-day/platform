# DEC-0011: 画面・コンポーネント・機能のIDの採番ルールと、早期採番の学び

## Status

Accepted

## Date

2026-09-25

## Context

ex-dayでは、設計の初期段階から画面（S）・コンポーネント（C）・機能（F）にIDを付けてきた。AIとのやり取りや、Issue・PR・DECの中で画面や部品を短く正確に指し示すためであり、実際にその目的は果たしてきた。

一方、DEC-0005〜DEC-0010で、ドメインの考え方（Contributionを会話の中の発言として扱う、Discoveryを会話の器とする、会話の理解の層を分ける、投稿後に解析する、会話の重複を歓迎する等）が大きく変わった。その結果、画面・コンポーネントの単位そのものが入れ替わることになった。

- 廃止：S04（知識・疑問登録／編集）、S11（知識・疑問登録確認画面）、C21（Contribution CTA）、C22（場所入力）、C24（時期・期間入力）
- 役割の見直しが保留中：S05・S06・S09、C14・C16〜C18（#68）
- 名前の変更：C26（Contribution Thread → みんなの声）ほか
- 新規：新規投稿のモーダル（C27の見込み）、投稿後の会話の解析等の機能（F）

既存の運用では、C13を廃止した際に「ID保持・再利用禁止」として一覧に残しており、新しい番号はAIが提案し人間がレビューで確定することとしていた（各種設計資料作成方針）。しかし、ここまで大規模に廃止・変更・追加が重なることは想定しておらず、一覧の中で現行と廃止が混在し、IDが覚えにくくなる懸念が生じた。

また、この変更の経緯は、「AIと設計を進める場合、先に決めるべきもの（ドメインの考え方）を決める前に画面の単位を固めると、後で大きく入れ替わる」という学びとして残す価値がある。この経緯は、Gitの履歴に残っているという理由で記録を省略せず、判断として明示的に残す。

## Decision

### 1. IDは変えない・再利用しない

- 一度付けたIDは、名前や役割が変わっても変更しない。
- 廃止したIDは欠番とし、別の画面・コンポーネント・機能に再利用しない（C13の運用を一般化する）。
- 過去のDEC・Issue・PRに残る参照（「S04」「C26」等）が、将来も同じものを指し続けるようにするため。

### 2. 変更の種類ごとの扱い

| 変更の種類 | 扱い |
|---|---|
| 廃止 | IDは残し、一覧に「（廃止）」と、廃止の理由と参照先（関係するDEC・Issue）を記載する。定義ファイルは削除せず、冒頭に廃止した旨を書く |
| 名前・役割の変更 | IDはそのまま。ファイル名のID以降の部分（スラッグ）と、定義の中身を変える（例：`C26-contribution-thread.md` → `C26-post-thread.md`） |
| 新規 | 各種類の次の番号を使う。番号はAIが提案し、人間がレビューで確定する（既存ルールを維持） |
| 判断待ち | 判断が出るまで触らない（例：S05・S06・S09、C14・C16〜C18は #68） |

### 3. 一覧は「現行」と「廃止」を分ける

- 画面一覧（screen-list.md）・コンポーネント一覧（component-list.md）・機能一覧（function-list.md）は、上に現行のものだけを並べ、廃止したものは下の「廃止済み」の欄に移す。
- 普段参照するのは現行の欄とし、欠番があっても読みやすくする。

### 4. 参照は「ID＋名前」で書く

- 文書・Issue・PR・DECで画面・コンポーネント・機能を参照するときは、「C26（みんなの声）」のように、IDと名前を併記する。
- IDは変わらない目印、名前は人が覚えるためのもの、と役割を分ける。これにより、番号を覚えていなくても読めるようにする。

### 5. 機能一覧（function-list.md）を新設する

- 機能（F）は、これまでF01（discovery-sections）の定義だけがあり、一覧がなかった。`docs/function-list.md`を新設し、画面・コンポーネント一覧と同じ形式・同じルールで管理する。

### 6. 学び：ドメインが固まる前に付けたIDは、変わる前提で扱う

- 早い段階でIDを付けること自体は、AIとのやり取りを正確にするために有効であり、今後も続ける。
- ただし、ドメインの考え方が固まる前に付けた画面・コンポーネントのIDは、単位ごと入れ替わる可能性がある前提で扱う。そのために、上記1〜4のルールで、変わっても過去の参照が壊れず、現在の一覧が読みやすい状態を保つ。
- 大きなドメインの判断（DEC）を行ったときは、画面・コンポーネント・機能の一覧への影響を、Consequencesで確認する。

## Reason

- IDを振り直すと、DEC・Issue・PR・Wireframe・Mockのレビュー記録に残る参照がすべて別のものを指すようになり、経緯が読めなくなる。
- 欠番を一覧に混ぜたままにすると、現行の画面・部品が分かりにくくなる。現行と廃止を分ければ、経緯を残しつつ読みやすさを保てる。
- IDと名前を併記すれば、IDの覚えにくさを補える。
- この経緯はGitの履歴からも辿れるが、履歴は「何が変わったか」は示しても「なぜそうなったか」「次にどうすべきか」は示さない。学びとして判断を明示的に残す。

## Alternatives

- **IDをすべて振り直して詰める案**：過去の参照が壊れるため採用しない。
- **廃止したIDを新しい画面・部品に再利用する案**：過去の参照が別物を指すため採用しない。
- **IDを使わず、名前だけで参照する案**：名前は変わり得るうえ、AIとのやり取りで指し示す対象が曖昧になるため採用しない。
- **経緯はGitの履歴に任せ、記録しない案**：理由と学びが残らないため採用しない。

## Consequences

- 各種設計資料作成方針の採番のルールに、本Decisionの1〜5を反映する。
- screen-list.md・component-list.mdを、現行と廃止済みの欄に分ける。
- function-list.mdを新設する。
- #67（画面・コンポーネント・モックへの反映）は、本Decisionのルールに従って廃止・名前の変更・新規の追加を行う。
- 以降のDECのConsequencesでは、画面・コンポーネント・機能の一覧への影響を確認する。
