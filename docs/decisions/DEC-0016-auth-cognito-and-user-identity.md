# DEC-0016: 認証は Amazon Cognito Essentials を使い、ログイン方法のつなぎは ex-day 側で持つ

## Status

Proposed（方針は人間が 2026-11-01 に決定。本文は Claude が作成し、レビュー待ち）

## Date

2026-11-01

## Context

#75 で、認証サービスを選ぶ条件を次のとおりにした（人の判断）。

- 認証のエンジン（ID の発行、トークンの署名など）は自前で作らない。標準の OIDC のライブラリでつなぐ
- 認証サービスが何であれ、後から変えられる作りにする
- パスワードを持たない。パスキーへの対応は必須
- 将来の API の公開を見込む。先に要るのは、外部の事業者がデータを登録する仕組み（M2M）。利用者の代わりにほかのアプリが使う形（同意の画面つき）は、必要になった段階で足す

候補を Auth0 と Cognito に絞って比べ（`docs/infra/auth-service-comparison.md`）、費用を見積もり（`docs/infra/cost-model.md`）、Cognito を実際に試した（`docs/infra/cognito-trial.md`、ex-day/poc#38）。

- 費用：Auth0 は無料が 25,000 MAU までと広いが、超えると有料の段（30,000 MAU で月 $2,100）へ移る。アプリを出すと利用者のほぼ全員が MAU になるので、この崖が早く来る。Cognito Essentials は 10,000 MAU まで無料、超えた分は 1 MAU あたり $0.015。M2M も、Cognito はトークン発行1回 $0.00225 で段差がなく、Auth0 は Free・Essentials で月 1,000 トークンまで
- パスワードなし：Cognito の managed login の登録の画面はパスワードを求める（公式の仕様）。登録だけ ex-day の画面で受け、サーバーから `SignUp` をパスワードなしで呼ぶと、managed login でメールのコードでログイン → パスキーの登録 → 次からパスキーかメールのコード、まで通った。登録の確認のメールは、ユーザープールの自動の検証・確認を外すと止まり、メールは1通になった
- Google：`google_<Google の sub>`、`identities` で上流の識別子を受け取れた
- 標準のライブラリ：Spring Security の OAuth2 Client でそのままつながり、トークンはサーバー側のセッションに置けた（ブラウザの cookie は JSESSIONID だけ）。Cognito 専用に書いたのは、登録（`SignUp`）、パスキーの登録のページへの転送、ログアウトの3か所で、どれもトークンを扱わない

## Decision

### 1. 認証サービスは Amazon Cognito（Essentials）

- ログインは managed login（ログインの画面は Cognito のもの。日本語で出す）。標準の OIDC（認可コード＋PKCE）でつなぐ
- ログインの処理とトークンはサーバー側で持ち、ブラウザには HttpOnly の cookie でセッションの印だけを渡す（#75 の要件1）
- ex-day が Cognito に求める OIDC のスコープは `openid` を基本にする。`email`・`profile` は、使う理由ができるまで求めない（決定5）。Cognito が Google などから受け取るスコープ（Cognito の IdP の設定）とは別に考える
- 外部の事業者からのデータ登録は、提供先ごとの App Client とスコープ（M2M）で作る。実際に作るときに確かめる
- クラウドは AWS を前提にする。部品の選び方は #129 で決める

### 2. MVP のログイン方法は Google とメール（パスキー・メールのコード）

- メールの人は、ex-day の登録の画面でメールアドレスだけを受け、パスワードなしで登録する。ログインはパスキーか、メールに届くコード
- パスキーは、登録してログインしたあとに勧める（Cognito のパスキーの登録のページへ送る）。パスキーをなくした人や作れない端末の人は、メールのコードで入る
- Apple は、iOS アプリを出すとき（Apple の開発者登録をするとき）に足す。LINE・X は利用の様子を見て決める（#75 の論点1）

### 3. 同じメールアドレスでも、ログイン方法は自動でつながない

- 同じメールアドレスで別のログイン方法から来ても、自動では同じユーザーにしない。ほかのサービスのメールアドレスを信じてつなぐと、乗っ取りの入口になりうるため（人の判断：「つなぎ込みはユーザーのアクションを伴わないと怖い」）
- メールアドレスは、同じ人かどうかの判定にも、ログイン方法をつなぐ鍵にも使わない（Apple の非公開のメールアドレスのように、同じ人でも違うメールアドレスになることもある）
- **ログイン方法をつなぐ**：本人が今の User でログインしたまま、足したいログイン方法でも認証し直し、そのログイン方法がまだどの User にもつながっていなければ、その User に UserIdentity を足す。S08 から行う形にする（後から作る）
- **アカウントの統合**：足したいログイン方法が、すでに別の User（User B）につながっている場合は、上のつなぎではなく、User B の Post・Reaction・プロフィール・状態などの扱いを伴う統合になる。自動で付け替えない。統合の手続きは別に設計する（Deferred）
- **アカウントの有無を漏らさない**：ログインの前に「このメールアドレスは Google で登録済みです」のように案内すると、第三者がメールアドレスから、アカウントがあるか・どのログイン方法を使っているかを調べられる。ログインの前は、登録済みかどうかで応答を変えない（ex-day の登録の画面でも、登録済みのメールアドレスかどうかを画面で区別せず、同じようにメールのコードでのログインへ進める）。登録済みであることやログイン方法を伝えるのは、メールのコードなどでそのメールアドレスの持ち主であることを確かめたあとに限る。具体的な流れと文言は Deferred

### 4. ログイン方法のつなぎは ex-day の DB（UserIdentity）で持つ

- Cognito の側では、ログイン方法ごとのユーザーは別々のままにし、Cognito の機能でつながない
- ex-day の User に、UserIdentity を 1..* でつなぐ（論理設計 4.1。#76 で決めた構成のまま）
- UserIdentity に持つもの：
  - 認証サービスの識別子（発行元と `sub`）。ログインのときは、これで UserIdentity を引く
  - ログイン方法の種類（Google、メールなど）
  - 上流の識別子（Google の `sub` など。`identities` から）。認証サービスを乗り換えたときに、同じ Google のアカウントで同じ ex-day のユーザーに戻すため（#75 の要件5）。メールの人には上流がない
  - つないだ時点
- 1つのログイン方法が、2人以上の User につながらないようにする。物理設計で、（発行元, `sub`）と（ログイン方法の種類, 上流の識別子）に一意の制約を置く
- ex-day のユーザー（User・UserIdentity）は、初回のログインのときに作り、ニックネームの設定（S07）へ送る

### 5. メールアドレスは Cognito を保管元とし、ex-day には残さない

- メールアドレスの保管元は Cognito だけにする。ex-day は、次のどこにもメールアドレスを残さない
  - 業務データ（DB）
  - アプリのログ、アクセスログ、監査ログ
  - エラーの監視・性能の監視（APM）
  - 分析の基盤
  - 一時ファイル、認証以外のバックアップ
- ただし、ex-day のサーバー（BFF）がメールアドレスを一時的に扱う場面はある（登録の画面、`login_hint`、Cognito への問い合わせ、運営からの連絡）。その場合は必要な範囲だけで扱い、ログ・エラーの記録・監視に出すときは伏せる（マスクする）。リクエストの本文・クエリをそのままログに出さない
- ID トークンにメールアドレスを入れないよう、ex-day が求めるスコープは `openid` を基本にする（決定1）
- 理由：使い道がまだない情報は持たない。個人情報の漏洩の影響を小さくする（人の判断）
- 通知が要るようになったら、メールではなくアプリ（プッシュ通知）で届ける方向で考える（人の考え）
- 運営からの連絡（規約の変更、アカウントの問題）が要るときは、その都度 Cognito から引く形を考える。ex-day に写さない
- プライバシーポリシーには、認証サービス（Cognito）にメールアドレスを預けることを書く

### 6. 認証サービスを乗り換えるときの対応づけ

- Google・Apple などでログインする人は、UserIdentity に持つ上流の識別子（Google の `sub` など）で、乗り換え先のユーザーと ex-day の User を対応づける。メールアドレスは使わない
- メールでログインする人（Cognito のユーザー）は、上流の識別子がないので、Cognito からメールアドレスを書き出して乗り換え先へ移し、乗り換え先の識別子と ex-day の UserIdentity を対応づける。書き出したメールアドレスは移行の作業の中だけで扱い、ex-day に残さない
- パスキーは移せないものとして考える。乗り換えたあとは、メールのコードやソーシャルログインで入り、パスキーを登録し直してもらう（`docs/infra/auth-service-comparison.md`）

## Reason

- 費用：利用者が増えても、MAU・M2M のどちらにも料金の崖がない。アプリを出しても予測しやすい
- パスキーとパスワードなしを、標準のライブラリのまま実現できることを試して確かめた。以前のように画面を全部自前にして標準のライブラリを使えなくなる形にならない
- 先に要る API の公開（M2M）に、そのまま対応できる。Auth0 の強み（同意の画面と取り消し）は、利用者の代わりにほかのアプリが使う形のもので、今は要らない
- ログイン方法のつなぎとユーザーの識別子を ex-day 側で持つので、Cognito を乗り換えても、ex-day のユーザーと投稿・Reaction は変わらない（#75 の要件3）

## Alternatives

- **Auth0**：無料の範囲が広く、同意の画面・取り消しがそろう。パスワードなしの登録もできる（ただし Early Access）。25,000 MAU を超えたときの料金の崖、M2M の上限で採らない。利用者の代わりにほかのアプリが使う形が中心になったら、改めて比べる
- **ログインの画面を全部自前で作り、Cognito の API を直接呼ぶ**：見た目は自由になるが、標準の OIDC のライブラリが使えず、認証の処理を自前で書く範囲が広がる（#75 の要件2 に反する）。登録の画面だけを自前にする形にとどめる
- **同じメールアドレスを自動でつなぐ**：使い勝手はよいが、上の決定3の理由で採らない
- **Cognito の機能でログイン方法をつなぐ**（`AdminLinkProviderForUser`）：Cognito に寄ったつなぎになり、乗り換えにくくなる
- **メールアドレスを ex-day に写して持つ**：通知や連絡には便利だが、使い道が決まるまで持たない
- **メールアドレスで同じ人かを判定する・移行の鍵にする**：上の決定3・6の理由で採らない
- そのほかの認証サービス（Clerk、Entra External ID、Firebase など）を外した理由は `docs/infra/auth-service-comparison.md`

## Consequences

### Domain・Logical Entity

- 論理設計 4.1 の UserIdentity の中身を、決定4のとおりにする
- User・UserProfile にメールアドレスを持たない（決定5）
- 物理設計：UserIdentity の（発行元, `sub`）と（ログイン方法の種類, 上流の識別子）に一意の制約（決定4）

### UI・機能

- S07（新規ユーザー登録）：メールの人の登録の画面（メールアドレスだけ）と、初回ログインのあとのニックネームの設定
- C08（ログイン）：「Google で続ける」「メールで続ける」。Google は ex-day のボタンから Cognito の画面を飛ばして直接送る。メールは managed login
- S08（ユーザー情報更新）：パスキーの追加（Cognito のパスキーの登録のページへ送る）、ログイン方法をつなぐ（後から）、退会
- 同じメールアドレスが別の方法で登録済みのときの案内

### 運用・設定

- ログ・エラーの監視・分析の基盤を入れるときは、メールアドレスが出ないこと（伏せること）を確かめる（決定5）
- Cognito：選択ベースのサインイン（パスキー＋メールのワンタイムパスワード）、App Client の `ALLOW_USER_AUTH`、自動の検証・確認を外す、Google の属性の対応（`email`、`email_verified`）
- 独自ドメイン（例：`auth.ex-day.jp`）で動かす。パスキーはドメインに紐づくため、最初から独自ドメインにする
- メールは SES で独自ドメインから送り、件名・本文を日本語にする
- 本番のユーザープールは東京（ap-northeast-1）に作る

## Deferred / Open Issues

- 外部の事業者からのデータ登録（M2M）の作り：提供先ごとの App Client・スコープ・トークンの有効期限。実際に作るときに確かめる
- ログインの持続時間（ex-day のセッションの長さ、Cognito のトークン更新の期限）。値は設定で持ち、MAU の数え方と安全のつり合いで決める（#75）
- 登録の画面のボット対策（量の制限、CAPTCHA）。#35 と合わせて決める
- 本人の操作でログイン方法をつなぐ機能（S08）の作り
- 同じメールアドレスが登録済みのときの流れと文言（決定3：ログインの前は応答を変えず、持ち主であることを確かめたあとに限って伝える）
- アカウントの統合の手続き（決定3：足したいログイン方法が、すでに別の User につながっている場合）
- メールアドレスをログ・監視で伏せる仕組み（決定5）の具体（ログの書式、エラーの監視の設定）
- 退会のとき：Cognito のユーザーの削除と、ex-day の User の状態・投稿の扱い（#76）
- Apple を足すときの論点（メールを非公開にする機能、鍵の作り直し）
- 利用者の代わりにほかのアプリが使う形（同意の画面・取り消し）を足すとき：Cognito では ex-day 側で作る（`docs/infra/auth-service-comparison.md`）

## Revisit Conditions

- 利用者の代わりにほかのアプリが使う形が、事業の中心になったとき（Auth0 などと比べ直す）
- Cognito の料金・機能が大きく変わったとき（managed login の登録の画面がパスワードなしに対応した、など）
- 通知のためにメールアドレスが要るようになったとき（決定5）
