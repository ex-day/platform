# DEC-0019: ex-day が一番やりたいのは、Wiki や Google でも見つけにくい地域の細かい発見を集めて体験へつなげることとし、初期は寄り道と場所のデータで体験を支える

## Status

Proposed（方針は人間が 2026-11-01〜03 に platform#134・#135 で決定。本文は Claude が作成し、レビュー待ち）

## Date

2026-11-03

## Context

ex-day は、場所・時間・興味を起点に「知らなかった何か」と出会うためのサービスとして企画した。もとは古い写真・地図と今の風景を比べる構想で、古い写真・地図を集めること自体がネックになると考え、「隙間時間を埋める発見」の企画と合体させた経緯がある。

PoC と画面の議論を重ねるうちに、扱いたいことが増えた。

- 寄り道（到達圏）：Discovery がなくても、時間の帯の地図を見ているだけで面白いと分かった（ex-day/poc#40・#42、platform#134）。帰り道・往復・片道を「そこで何分過ごせるか」で同じ形に扱えると分かった
- 地域の記憶：漁師の子どもがおやつに食べていた青柳の干物、川崎駅の外にあった跨線橋で行商人が魚を売っていた話など
- マニアの目線：都内一の急坂、日本一短い国道のような番付。まだ知られていないものをデータで掘り起こせそう（標高データ × 道路で勾配を推定する等）
- 企画：おすすめの散歩コース、ゆっくり花見ができる場所のまとめ、ユーザー自身が作る番付（DEC-0021）

人の判断（2026-11-02）：ex-day は、当初考えていたよりだいぶ大きくなり、単なる発見のためのサービスというより、やりたいことが全部入ったプラットフォームになっている。規模を縮小する必要はないが、体験してほしいものの順位を改めて付けるところに来ている。

一方、これまでのドメイン設計は、地域の記憶（A）や今昔（C）を Discovery として扱い、それを体験の入口にしていた。初期は Discovery のデータがないため、入口が空になる。PoC で寄り道（B）のためのデータ（場所）が必要になり、場所と Discovery の関係が設計に入っていない。

## Decision（案）

### 1. 一番やりたいこと

**Wiki や Google でも見つけにくい、地域の細かい発見を集め、その発見を体験できるところへつなげる。**

- 例：漁師の子どものおやつだった青柳の干物、川崎駅の昔の跨線橋と行商人、鶴見の急坂と「雪の日はタクシーでも上れない」話
- 地元の人にとっては当たり前のことが、よその人（その分野が好きな人、マニア）から見ると「そうなの？」と驚く発見になる。その出会いを作る
- 人の興味はさまざまなので、食べ物・坂・道・歴史など、特定の分野に絞らない

### 2. 体験の構造

ex-day の体験を、次の記号で呼ぶ（platform#134 の議論で使った記号）。

| 記号 | 体験 |
|---|---|
| A | 地域の記憶・発見に出会う |
| B | 隙間時間で寄り道する（そこで何分過ごせるか） |
| C | 今昔を見比べる |
| D | 記憶・発見を体験しに行く |
| E | 会話で育てる（投稿・返信・解析） |
| F | 問いに答える（AI が会話から取り出した問い、声のない場所への問いかけ） |

関係は次のとおりとする。

- **A や C を集めて D につなげる。その過程が E である**
- **F は、E の結果として、また E に参加してもらうための入口として、AI が抽出した追加の問いを Discovery（や場所）に表示するもの**
- **初期は A や C のデータがないため、B を中心に、体験できるデータ（場所。DEC-0020）を用意する**。番付・まとめなどの企画（DEC-0021）も、データの少ない初期を支える

### 3. 本筋の使い方

- 本筋は、スマホで「いま」を見る使い方とする（起点＝現在地。platform#134 の 2026-11-01 のコメント）
- PC で予定を立てる使い方も同じ画面で扱う。予定の保存・共有は、ログインや予定の持ち方に関わるので後で決める

### 4. 後に回すもの

- 予定の保存・共有（上記）
- 地域への還元（長期の目標。今は具体化しない）

## Reason

- テーマの芯（地域の細かい発見）は、ほかのサービスにない。寄り道は、その発見へ行くための道具であり、初日からデータなしで価値が伝わる
- A や C を体験の入口にすると、データの少ない初期に入口が空になる。B と場所のデータで入口を支え、A・C は育てるもの、と分けると矛盾がない
- 規模を縮小しない代わりに、体験の構造（何が目的で、何が過程・入口・足場か）を決めておけば、機能が増えても判断がぶれにくい

## Alternatives

- **規模を縮小し、寄り道だけ（または発見だけ）に絞る**：人の判断で採らない。地域の発見がなければ寄り道は普通の地図サービスに近づき、寄り道がなければ初期に体験を作れない
- **A・C を初期から運営が大量に登録して入口にする**：運営が登録する Discovery（#57）は見本として使うが、量で入口を支えるのは運営の負担が大きく、地域の細かい発見の質も保ちにくい

## Consequences

- 場所を Discovery と独立した先にあるものとして置き、会話を器にする（DEC-0020）
- 企画を独立したものとして置く（DEC-0021）
- TOP の構成を、初日と育ったあとで中身の重みが移る形にする（DEC-0022）
- 要件（`ex-day_requirements.md`）、MVP の範囲（`ex-day_mvp_scope.md`）、ドメインモデル、論理エンティティ設計に、この構造との食い違いがある。洗い出しと直し方は platform#135 で行い、#132（ドメイン設計）へ引き継ぐ

## Deferred / Open Questions

- ex-day の価値の言い方（例：「地元の人の当たり前と、よその人の『そうなの？』が出会う場所」）は候補のまま。対外的な文言は別に決める
- A・C・D のうち、MVP でどこまで画面として作るか（C の今昔の見比べの見せ方など）

## Revisit Conditions

- 運用を始めて、初期の利用者が実際にどの体験（B・企画・A）から入っているかが分かったとき
- 会話が集まらず、E の循環が回らないとき
