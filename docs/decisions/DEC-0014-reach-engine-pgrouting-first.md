# DEC-0014: 寄り道の到達圏は MVP では pgRouting で計算し、R5 への移行は費用見合いで別途判断する

## Status

Proposed（方針は人間が 2026-10-10 に決定。本文は Claude が作成し、レビュー待ち）

## Date

2026-10-10

## Context

DEC-0013（下書き）で、寄り道の提案を MVP に入れることにした。そのための「行ける駅・場所の一覧」と「移動時間」を、何で計算するかを ex-day/poc で比べた。

| | pgRouting | OpenTripPlanner 2.11 | R5（r5py） |
|---|---|---|---|
| 検証 | #5・#6・#23・#27（PR #21・#22・#24・#29） | #7（PR #25）、#26（PR #28） | #26（PR #28） |
| 行ける駅の一覧 | 約0.6秒（＋歩きの事前計算） | 一対多の API が無い（等時間線は 2.5 まで）。駅ごとの問い合わせで全駅 約4,400回 | 行き・帰りで 0.6〜0.7秒 |
| 場所への時間 | 駅までの時間＋駅から場所の歩き（事前計算） | — | 場所 6,323件へ 2.0秒。代表の駅・歩きの事前計算が要らない |
| 置き場所・メモリ | 既存の Postgres の中 | 専用サーバー（関東で約6GB） | Python と同じプロセスの Java（関東で約4.5GB） |

わかったこと：

- 時刻表（利用条件の厳しい ODPT など）を使わず、N02 と表定速度から作った仮の GTFS で、OTP も R5 も動く
- pgRouting は、駅をまたいで歩く乗換を入れず、乗換を10分の固定にしているので、R5 と比べて行ける駅を1〜2割少なく出す（「行けない」側に寄せる方針どおり）
- 寄り道の提案の質は、pgRouting 側を直した（#27）あとは R5 に近い。上位10件の重なりは平均7件、降りる駅の一致は 79%。残る違いの多くは駅の代表点（ホームの重心）で、pgRouting でも直せる
- 費用（参考）：pgRouting は追加無し。R5 は関東で月 約1〜2万円（実測の約4.5GB から、AWS 東京のオンデマンド）。全国は測っていない

比較の詳細は poc の `reach/otp/README.md`、判断の表は platform の DA表の下書き（`DA-reach-engine.draft.md`）。

## Decision（案）

### 1. MVP の到達圏は pgRouting で計算する

- 行ける駅の一覧（`reach.reachable`）と、駅から場所への歩き（`station_spot_walk`、N13）を使う
- 既存の Postgres の中で動き、追加の固定費がかからない
- poc #27 の直し（遠回りに歩きの往復を入れる、出発駅・帰着駅も最寄りの駅に使う）を前提にする

### 2. OpenTripPlanner は使わない

- OTP 2.11 には一対多の API が無く、行ける駅・場所の一覧を数秒で出せない

### 3. R5 への移行は、費用見合いで別途判断する

この DEC では決めない。費用と収支（PV・収益の見込み）は変わりうるので、移るかを考える時点で、全国版のメモリを測り、そのときの料金と収支で判断する（事業収支計画の側）。

判断のときに、費用とあわせて見る材料：

- **歩き**：歩く道を OSM にしたい（N13 に細い道・参道が無く、遠回りに出る場所が問題になった）
- **ほかの交通**：バスなど、駅以外の交通を足したい（公開されている GTFS を入れる）
- **駅の代表点**：駅の改札・出入口や、駅をまたぐ徒歩乗換を、手で持ち続けるのがつらくなった

移るときは、R5 の交通網を作る処理（OSM・仮 GTFS の更新ごと）と、帰りの近似（帰着駅 → 場所の一対多）を、実際のデータで確かめ直す。

## Consequences

- MVP では、駅の代表点（ホームの重心）による割り当てのずれが残る（例：東京駅の中の場所が、駅から歩き16分と出る）。改札・出入口を持たせる直しは、MVP の中で行うか後回しにするかを別に決める
- 歩きは N13 のまま。細い道が無いため、一部の場所は遠回りに出る
- 駅をまたぐ徒歩乗換をしないので、行ける駅は R5 より1〜2割少なく出る（「行けない」側に寄せる方針どおり）
- R5 に移るときに、提案の仕組み（駅経由 → 場所へ直接）が変わる。API の形（行ける場所の一覧と、時間の目安を返す）は、どちらでも同じになるようにしておく

## Alternatives

- **最初から R5**：代表の駅・歩きの事前計算が要らず、降りる駅も自然。ただし MVP から固定費がかかり、Java のプロセスと交通網の作り直しを運用することになる
- **OTP**：一対多が無く、到達圏の計算には使えない（2.5 までの等時間線の API は保守されていない）
- **時刻表（ODPT など）を使う**：利用条件の多くがチャレンジ向けで、ex-day では使えない。「だいたい○○分」でよい前提とも合わない
