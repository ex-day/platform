# DEC-0009: 会話の理解（話題・発見の仮説・わかってきたこと）の層と、タグの採用を定める

## Status

Accepted（Decision 11の名前は仮称とし、上位文書への反映時に最終決定する）

## Date

2026-09-25

## Context

DEC-0007で、Discoveryの補完・派生を、Post単体ではなく会話の「文脈のまとまり」を単位として判断することとした。一方、次の事項がEntityのあり方に依存して先送り・判断待ちになっていた。

- DEC-0007 Deferred：文脈のまとまりをEntityとして永続化するか、Postとの関係
- DEC-0008 Deferred：会話から読み取られた結果（わかってきたこと／Finding）を独立したドメインとするか、Contributionという語を「寄与」の意味で残すか
- #58 判断待ち：ContributionDiscovery、Contribution Subject、ContributionOriginの新しい名前
- PR #62のレビュー：論理Entity設計に残るPost↔Subjectの直接の関係を維持するか

また、ユーザーがPostに付ける明示的な印（タグ）は、これまでex-dayで検討されていなかった。

Issue #63で、汽車道（散歩ルートから貨物線・氷川丸へ話題が移る会話）と浜松町（「古いビルの入口はなぜ一段高い？」という問いから、水害説・〇〇説が出る会話）の例を流しながら検討した。検討の経過は #63 の途中経過1〜8に記録している。

## Decision

### 1. 3つの層に分ける

| 層 | 含むもの | 性質 |
|---|---|---|
| 人間が作ったもの | Post、Reaction、Media、Post間の参照（返信等）、表示するタグ | AIの解釈で書き換えない |
| ex-dayが会話から理解しているもの | 話題、発見の仮説、わかってきたこと、内部で持つタグ | ex-dayの見立て。新しいPostや再解析で更新・分割・統合・失効してよい |
| ex-dayとして採用した構造 | Discovery、Subject、Place、Value、DiscoveryRelation、判断記録、提案 | 「確定」は真実の保証ではなく、ex-dayのドメインモデルとして採用したことを意味する |

**2つの層をつなぐルール：** 判断（提案の確定・却下、派生等）の時点で、根拠となったPost（と、それを支えたわかってきたこと）を判断記録の側に写し取って固める。見立ての層のIDを参照するだけにはしない。これにより、見立てが後で組み直されても、判断の理由は失われない。

### 2. 話題（旧称：文脈）をex-dayが管理・保存する

- 話題は「どのPostの範囲で、何について話しているか」を表す、ex-dayの見立てである。Postそのものではない。
- 新しいPostのたびに過去の全Postを解析するとコストが破綻するため、ex-dayが話題とその要約を保存する。新しいPostの解析は「既存の話題の要約＋新しいPost」を主な入力とする。DEC-0007 Deferredの「文脈のまとまりを永続化するか」への答えは「永続化する（見立ての層として）」である。
- 話題は後のPostで意味が変わる（「そうなの？」が後から鉄道史の話と分かる等）ため、形成・更新・分岐・再構成してよい。組み直しの記録は要らない。
- 1つのPostは複数の話題に属してよい。話題は、複数のDiscoveryのPostを参照できる（Decision 8）。
- Post間の参照（返信等）は、話題の推定で優先して使う（DEC-0007 決定8）。

### 3. 話題は、発見の仮説（擬似Discovery）を持つ

- 各話題は、Discoveryと同じ形（場所・Subject・価値）を持つ擬似的なDiscoveryとして中身を持つ。これを「発見の仮説」と呼ぶ。
- 1つの話題に、解釈の異なる複数の仮説があってよい（例：浜松町の会話から、水害に備えた街のつくりという仮説と、昔あった〇〇の名残という仮説）。DEC-0005 決定9（矛盾する解釈を無理に一つにまとめない）を構造にしたもの。
- 仮説の数は、確からしさの高いものから数個までに絞る。
- 会話が進むと仮説は絞られ、支えを失った仮説は失効する。
- 発見の仮説は見立ての層の概念であり、単独の中核Entityとはしない。

### 4. わかってきたこと（Finding）は、仮説の中身として育つ

- わかってきたことは、会話から「何がわかってきたか」を表す。話題（何について話しているか）とは区別する。
- 種類は**説**と**価値**の2つとする。
  - 説：「水害対策では」「汽車道は旧貨物線の一部だった」等。観察（「入口が一段高い」）を含む。資料（出典）の裏付けがあるものを知識として扱う。
  - 価値：「夕方、夕焼けが綺麗」「高低差の理由を一緒に考える」等。
- 問いはわかってきたことに含めない。問いはPostであり、問いを起点とした成立前のDiscovery（器）の話題になる。まだわかっていないことは、話題の要約の一部として表す。疑問起点の価値（「謎を一緒に考える」）は、わかってきたことの価値に含む。
- わかってきたことは1つのEntityとし、種類は属性として持つ。種類どうしの関係（この説はこの問いに答える等）は、最初は持たない。
- わかってきたことはユーザーに見せる（S03のC25「わかってきたこと」）。

**同一性のルール：** 再解析で表現が変わったとき、「すでに反応した人が、変わった後の文を見ても同じ反応をするか」で判断する。するなら同じものの更新（Reactionを引き継ぐ）、しないなら別の新しいもの。

| 変化 | 扱い |
|---|---|
| 言い換え、詳しくなる、条件が絞られる | 更新（Reactionを引き継ぐ） |
| 主張が変わる、対立する説が出る | 別の新しいもの。元の説も残して並べる |
| 同じものだと分かる | 統合（Reactionを合算し、同じ人の重複は1つにまとめる） |
| 2つの主張が混ざっていた | 分割（元の方にReactionを残す） |
| 支えがなくなった | 失効（消さずに残す） |

版の履歴と、Reactionがどの版に付けられたかを保持する。

### 5. Post↔Subjectの直接の関係は持たない

- 単体では話題を持たないPostや、複数の話題にまたがるPostがあるため、SubjectをPostに直接持たせない。
- Subjectの候補は発見の仮説が持ち、採用されたらDiscoveryのSubjectになる。
- Post単位の埋め込み・語の抽出は、解析の内部データ（キャッシュ）として扱ってよい。
- ユーザーが付けるタグは、Postに直接持たせてよい（Decision 10）。

### 6. 「寄与」ではなく「出所」とする

- わかってきたことは話題（会話全体）を解析して得るものであり、「誰が寄与したか」を個人に割り振ることは正確にはできない。
- Postとわかってきたことの関係は、「どの会話から分かったか」という出所（根拠）の関係とする。
- 個人を特定できるのは資料の提供であり、資料（Media）自体が提供者・出典を持つ（DEC-0005 決定8）。
- ドメインに「寄与（Contribution）」という概念は置かない。S09は「自分の発言が役立った」ではなく、「自分が参加した会話から、こんなことがわかってきた」という参加の手応えとして見せる。

### 7. 提案と、候補にする判断材料

**提案：** 仮説に付く判定（補完・類似・同一・派生）は見立てであり、会話が進めば変わってよい。判定が基準を超えたら、事実の層に**提案**を出す。提案は対象の側が状態（提案中→確定／却下／失効）を持つ（例：関係の提案はDiscovery AとBの組が持つ）。却下は組についての事実として残り、同じ提案を繰り返さない関門になる。

**突き合わせの単位と行き先：** 比べる単位は発見の仮説である。仮説はDiscoveryと同じ形を持つため、「仮説とDiscovery」「仮説どうし」を同じ物差しで比べられる。

| 突き合わせの結果 | 提案 |
|---|---|
| 元のDiscoveryと類似 | 元のDiscoveryへの補完 |
| 別の既存Discoveryと同一（価値の一致まで見る） | 統合、または新しいValueの追加 |
| 別の既存Discoveryと類似 | 関連 |
| どれとも一致しない | 派生 |

突き合わせのきっかけは、仮説の変化・他のDiscoveryの更新・定期的なまとめての突き合わせ（ベクター検索等）とする。

**候補にする判断材料（数値の閾値は #61 で決める）：**

- 2つの段階：「わかってきたこととして見せる」（低い基準）と、「確定候補・派生候補として判断に回す」（高い基準）
- 3つの軸：中身の成熟（場所・価値の特定、同じ方向のわかってきたことの数）、人の支え（参加者の数、価値へのReaction、返信での参照、タグ）、時間の安定（再解析をまたいで残るか、話が続くか）
- 候補にしない条件：却下済みの組み合わせ、安全性の問題（#35）、知識として扱う場合の未解決の対立する説
- **1人の参加者の1つの発言だけからは、確定候補にも派生候補にもしない。** 現時点での例外は運営が登録するDiscovery（#57）のみとし、将来の事業者によるDiscovery等に備え、例外は登録主体の種類と信頼性によって広げられる形にする（具体的なルールは #46）。

採用（確定）の判断・運用は後続で検討する。

### 8. 派生が確定したときの流れ

1. 新しいDiscoveryが成立前（`UNESTABLISHED`）で生まれる（DEC-0007 決定6）。中身は派生と判定された仮説から引き継ぐが、採用済みではなく候補のまま持つ。
2. 元のDiscoveryとの間に派生の関係を作る。
3. 判断記録に、確定時点の根拠のPostを固めて残す。
4. **話題を派生先へコピーし、派生先の最初の話題にする。Postはコピーせず、元の場所に残して参照する。** 派生先の最初の話題が、成立の経緯（元の会話の参照）と続きの会話を一続きに持つ。コピー後、元の話題と派生先の話題は別々に育つ。

- 続きの会話は派生先で行うよう誘導するが、強制しない。誘導の見せ方（元の側の案内、返信時の提案、派生先の冒頭での経緯の表示等）は画面設計で扱う。
- 元の場所で同じ話の続きが投稿された場合、Postは元のDiscoveryに属したまま、派生先の話題にも参照として加える。これにより話は分散しない。
- Postが属する器は、投稿された場所の1つだけとする。他のDiscoveryとは参照（根拠・出所・話題への所属）でつながる。

### 9. Reactionの対象

| 対象 | Reactionの意味 | 注意 |
|---|---|---|
| Post | 発言への共感 | ― |
| 価値（わかってきたこと・候補・採用後のValue） | 「わかる」「行ってみたい」 | 確からしさ・推薦の材料 |
| 説（裏付けのないもの） | 「そうかも」 | 正しさの証拠にはしない。票の多い説を正解のように見せない（「Reactionの数を事実の正しさに置き換えない」既存原則） |
| 説（裏付けのある知識） | 付けない | 確からしさは資料・出典で決まる |
| Subject・Condition単独 | 付けない | 意味をなさない |

問いへの「自分も気になる」は、問いを投げたPost（またはDiscovery）に付ける。

### 10. タグを採用する

**採用の理由：**

- 探すためのキーワードを低コストで、本人の意図どおりに付けられる。
- 価値がまだない段階のDiscoveryを、TOP等で露出できる（DEC-0006：成立前のDiscoveryは推薦ではなく露出する）。
- 自然な文の中で付けられ、投稿の入力負担を増やさない（DEC-0004・DEC-0005）。
- 返信等の参照と同じく、人が与える構造情報として話題の解析に使える。
- Subjectの候補の最も安い入口になる（DEC-0007 決定9）。

**表示するタグと内部で持つタグを分ける：**

| | 表示するタグ | 内部で持つタグ |
|---|---|---|
| 中身 | ユーザーが書いたまま | 表記の揺れを吸収し、Subjectに対応付けたもの |
| 層 | 人間が作ったもの（Postに付く） | ex-dayが会話から理解しているもの |

- タグはPostに付ける。Discoveryのタグは属するPostのタグを集めて求める。運営が登録するDiscovery（#57）には、運営が付けたタグを直接持たせてよい。
- 必須にしない。判断ではなく、重み付けされた入力として扱う（DEC-0007 決定10）。
- タグで見せる単位はPostではなくDiscoveryとする（DEC-0008 決定4：SNS的な振る舞いを採らない）。
- 入力はPostと同じ欄で行う。モバイルでの入力の手間は画面設計で解消する。

### 11. 名前（仮）

名前はすべて仮称とし、上位文書への反映時に最終決定する。既存の設計の用語と衝突しないようにする。

| 概念 | 仮の名前 | 避けた名前と理由 |
|---|---|---|
| 話題（旧称：文脈） | Topic | Context：ドメイン設計で「Discovery Context」「SearchContext」（探すときの文脈）に使っている |
| 発見の仮説（擬似Discovery） | DiscoveryHypothesis | ― |
| わかってきたこと | Finding | ― |
| 提案 | Proposal | ― |
| 出所（Postとわかってきたことの関係） | 関係名として表す（例：Findingの根拠Post） | Source・Evidence：既存のEntity（資料の出典、根拠）として使っている |
| 表示するタグ／内部で持つタグ | PostTag／TagMapping | ― |

**#58 から引き継いだ名前：**

| 現行名 | 扱い（案） |
|---|---|
| ContributionDiscovery | PostとDiscoveryの関係として整理し直す。器としての所属（Postが投稿された場所、1つ）と、参照（話題への所属、わかってきたことの根拠）に分かれる。寄与の意味では残さない（Decision 6） |
| Contribution Subject | 廃止（Decision 5） |
| ContributionOrigin | Postが何を起点に生じたか（別のPostへの応答、外部の資料の参照、Discovery上の問い等）を表す。Post間の参照（DEC-0007 決定8）と大きく重なるため、Post間の参照（仮称：PostReference）に統合し、起点の種類を属性として持つ方向で検討する |

## Reason

- 過去の全Postを毎回解析する方式は、会話が長くなるほどコストが増え、話題の判定そのものを諦めることになりかねない。話題を保存すれば、「要約＋新しいPost」で解析できる。
- 話題は後のPostで意味が変わる見立てであり、確定した事実と同じ層に置くと、組み直すたびに判断記録や派生の経緯まで揺れる。層を分け、判断時点で根拠を固めることで両立できる。
- 実際の会話では、1つの話題から複数のわかってきたことが生まれ、1つのわかってきたことが複数の話題にまたがり、わかってきたことから出る構造は個別に採用・却下される。「何について話しているか」「何がわかってきたか」「それを構造にすると何か」を分ける必要がある。
- 話題の中身をDiscoveryと同じ形（仮説）で持つと、比べる単位と物差しがそろい、候補の種類を分けずに1つの判定（補完・類似・同一・派生）で扱える。
- 会話全体の産物を個人の寄与に割り振ると、AIの解釈に依存した根拠の弱い帰属になり、投稿の圧（DEC-0008で懸念）も生む。
- 知識の確からしさは反応の数では決まらず、価値への共感とは性質が違う。既存の「Reactionの数を事実の正しさに置き換えない」原則に合わせる必要がある。
- 派生の際にPostを複製すると編集・削除・出所の管理が崩れる。話題（見立て）だけを複製すれば、経緯と続きの会話を派生先で一続きに持てる。
- タグは、低コスト・本人の意図・入力負担の小ささの点で、AI解析を補う人の構造情報として有効である。

## Alternatives

- **話題を保存せず、毎回全Postを解析する案**：コストが会話の長さに比例して増えるため採用しない。
- **話題を確定した事実の層に置く案**：組み直しのたびに判断記録や派生の経緯が揺れるため採用しない。
- **投稿時点で話題への振り分けを固定する案**：後のPostで前のPostの意味が変わるため採用しない。
- **Post↔Subjectの直接の関係を維持する案**：単体で話題を持たないPostや、複数の話題にまたがるPostを扱えないため採用しない。
- **わかってきたことを話題の要約と同一視する案**：「何について話しているか」と「何がわかってきたか」を混同し、1つの話題から複数のわかってきたことが生まれる場合を扱えないため採用しない。
- **候補を種類（Value・Subject・関係・派生等）ごとに別々に持つ案**：同じまとまりの行き先の違いを別物として扱うことになり、判断の仕組みが増えるため採用しない。
- **1つの話題に1つの解釈だけを持つ案**：対立する説・解釈を並べられないため採用しない。
- **問いをわかってきたことに含める案**：問いは「何について話しているか」の側にあり、Postと器で表せるため採用しない。
- **わかってきたことの種類を細かく分ける（問い・観察・仮説・知識・価値）案**：重くなるため、説と価値の2つに絞る。
- **寄与（Contribution）を個人に割り振って持つ案**：正確に割り振れず、投稿の圧を生むため採用しない。
- **知識・説にも価値と同じReactionを付ける案**：反応の数を正しさと誤認させるため採用しない。
- **派生時にPostを複製・移動する案**：管理が崩れ、元の話題の文脈も壊れるため採用しない。
- **派生時に続きの会話の移動を強制する案**：会話が逸れることを抑制しない方針（DEC-0007 決定7）に反するため採用しない。
- **タグを採用しない案**：価値がまだない段階のDiscoveryの露出や、低コストのキーワード付けの手段を失うため採用しない。
- **タグ専用の入力欄を設ける案**：入力の手間が増えるため採用しない。
- **話題の名前をContextとする案**：探すときの文脈（Discovery Context、SearchContext）と衝突するため採用しない。

## Consequences

### Domain

- 3つの層と、層をつなぐ「判断時点で根拠を固める」ルールを記載する。
- 話題・発見の仮説・わかってきたことを「ex-dayが会話から理解しているもの」の層の概念として記載する。中核Entityとは区別する。
- Subjectの定義（Post Subjectの役割）から、Postへの直接の付与を外す。
- 派生の流れ（話題のコピー、Postの参照、誘導）を、成長・派生の記述に追加する。
- Reactionの対象と意味（Decision 9）を記載する。「Reactionの数を事実の正しさに置き換えない」原則との関係を明記する。
- タグ（表示するタグ・内部で持つタグ）を記載する。

### Logical Entity

- Post↔Subjectの直接の関係（旧Contribution Subject）を削除する。
- ContributionDiscoveryを、器としての所属と参照に整理し直す（名前は上位文書への反映時に決定）。
- ContributionOriginをPost間の参照に統合する方向で整理する。
- 話題、発見の仮説、わかってきたこと、提案、表示するタグ・内部で持つタグを追加する（見立ての層か事実の層かを明記する）。
- わかってきたことに、版の履歴とReactionの対象の版を持たせる。
- Reactionの対象を、Post・Discoveryに加え、わかってきたこと（価値・説）・Valueへ広げる。
- 提案に、状態（提案中→確定／却下／失効）と判断記録へのつながりを持たせる。DiscoveryRelationの候補段階（DEC-0007 決定10）はこれに含める。
- 判断記録に、確定時点の根拠のPost・わかってきたことを固めて持たせる。

### UI

- C25（わかってきたこと）は、説と価値を表示し、種類ごとのReaction（Decision 9）を扱う。
- 派生の誘導（元の側の案内、返信時の提案、派生先の冒頭での経緯の表示）をS03で設計する。
- タグの入力（Postと同じ欄、モバイルでの入力支援）と、タグによるDiscoveryの露出を設計する。
- S09を「自分が参加した会話から、わかってきたこと」として再構成する。

### PoC（#61）

- 話題・発見の仮説・わかってきたことの考え方と、派生の流れが実際の会話で成り立つかを検証する。
- 1つの話題に出る仮説の数、候補にする判断材料の数値の閾値、突き合わせの頻度とコストを検証する。

## Revisit Conditions

- PoC（#61）で、話題・発見の仮説・わかってきたことの3段階が実際の会話で成り立たない、またはコストが見合わないことが明らかになった場合
- 1つの話題に出る仮説が多すぎて、絞り込みが機能しない場合
- わかってきたことの同一性のルールで、Reactionの引き継ぎが実用上うまく働かない場合
- タグが、表記の揺れやスパムによって、露出・解析の品質を下げていることが確認された場合
- 事業者等の新しい登録主体を扱う際に、候補にする判断材料の例外の枠組みが合わない場合
