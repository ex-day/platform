# DEC-0022: TOP は企画と発見で何のサービスかを伝え、小さな地図から全画面の寄り道（`/detour`）へつなぎ、中身のある枠だけを出す

## Context

これまで TOP（S01）は、「この時期のおすすめ」などの Discovery の提案を中心にしていた。Discovery が体験価値の高い時間（時期・時間帯の条件）を持つことを前提にしていた。

DEC-0019〜0021 で、次のようにした。

- 初期は Discovery が少ない。寄り道（B）と場所のデータ、企画で体験を支える
- 場所は Discovery と独立して先にある。Discovery は場所や地域に関する具体的な発見・体験価値で、時期の条件は Discovery が持つ
- 企画（コース・番付・まとめ・記憶）を、運営とユーザーが作る

platform#134 で、寄り道の画面を検索の結果（S02）と分け、ヘッダーの検索窓の横に「寄り道」のリンクを置く形にしていた（S12 の想定）。

人の考え（2026-11-03）：TOP を地図そのものにするのは、別の視点ならありだが、何のサービスか分かりにくくなる。初期状態でも地図は出すが、PC では大きく出さず、余白に「こんなデータ作りませんか？」という企画を出す。地図を押すと全画面の地図になる（トグルのような形）。

## Decision（案）

### 1. TOP の形

- **PC**：真ん中に企画と発見（何のサービスかを伝える）、余白に小さな地図（ここから行ける範囲）。地図を押すと全画面の寄り道の画面になり、戻ると TOP に戻る
- **スマホ**：一番上に地図のカード（S01 のミニ地図のカード）、その下に企画と発見のカード。地図のカードを押すと全画面
- 全画面の地図は、寄り道の画面（S12 の想定）と同じもの。入口は、ヘッダーの「寄り道」、TOP の小さな地図、S03 の「ここから行ける」

### 2. TOP の枠

| 枠 | 中身 | 必要なデータ |
|---|---|---|
| 企画 | いま募集中の企画（運営・ユーザー）。「こんな番付、作ってみませんか？」 | 企画 |
| いま、この時期 | 時期・時間帯の条件が今に合う Discovery | Discovery |
| 近くの発見 | 近くの Discovery。場所を見出しにして出す（「小机城址：春は地元の人しか来ない桜の穴場」） | Discovery |
| ここから | 「ここから30分で行ける範囲」の小さな地図。寄り道の入口 | 場所 |
| 番付 | データから出した推定の候補（「推定・鶴見区の急坂」） | 場所＋計算 |
| ex-day の発見（見本） | 運営が登録した Discovery（#57）。近くになければ、始める地域のもの | Discovery（運営） |
| 声を待っている | 「この場所の昔を、知っていますか？」と、近くの声のない場所 | 場所＋問い |

- **中身のある枠だけを出す**。空の枠や「0件」は出さない。枠の切り替えの仕組みは持たず、データの量に合わせて重みが自然に移る
  - 初日：企画、ここから、番付、見本、声を待っているが中心
  - 育ったあと：いま・この時期と、近くの発見が前に出て、企画は帯に小さくなる
- 時期の情報は Discovery の条件から出す。場所のデータの時期の情報（祭りの開催日、「桜の名所」の分類など）は、出来事として後で考える

### 3. Discovery が少ないときの出し方

- 「いま、この時期」は範囲を広げて探す：近く → 同じ区・市 → 全国から1〜2件（「今の時期ならこんな発見も」）→ なければ枠ごと出さない
- 少なさを隠さず、余白を数字で見せる（「このあたり：場所 [N]・声のある発見 [N]」）
- 始める地域の外にいる人には、「このあたりはまだ発見が少ない」と書いたうえで、近くの番付と問いかけを前に出し、いちばん近い発見を寄り道の入口として出す

### 4. 全画面の地図から戻ったときに、TOP の状態を保つ

基本方針：

- スクロール位置と、読み込んだカードを保つ。読み直しても、あとで見ようと思ったものが見つからなくならないようにする
- TOP の並びは、一定の間（例：同じセッション、その日のうち）は変えない
- メモリを使いすぎない：地図（重い描画）を同時にいくつも動かさない。TOP のカードを際限なく増やさない
- 「あとで見る」の保存は、ログインが要るので後で決める

実装の選択肢（決定ではない。実装で確かめて選ぶ）：

- Next.js（App Router）の intercepting routes で、TOP から開いたときは TOP を裏に残したまま地図を上に重ね、URL を直接開いたときは単独のページにする
- TOP の小さな地図は、地図ライブラリ（WebGL）ではなく、帯の形を SVG などで描く。本物の地図は全画面の1つだけにする
- TOP のカードは無限スクロールにせず、件数に上限を設ける（例：50件、その先は「もっと見る」）。画像は見えたところで読み込む
- 並びを固定するために、日付などを種にした並びを使う

### 5. 寄り道の画面の URL

```
/detour?from=<場所のID>&to=<場所のID>&t=180
```

- 駅・場所は名前ではなく ID で指定する（同じ名前の駅がある。S03 と同じ理由）。名前はページのタイトルと共有の表示（OGP）に出す
- 終点：`to` を省くと「ここに戻る」（往復。既定）、`to=<ID>` で「そこに着く」（帰り道）、`to=none` で「そこで終わる」（片道）
- `t` は使える時間（分）。時刻では聞かない（時刻での検索はしない。DEC-0014）
- 現在地から始めるとき：現在地の座標は、なるべく URL に残さない。URL に入った座標は、共有したリンクだけでなく、ブラウザの履歴、サーバー・CDN・解析のログ、外部のサイトへ移るときの参照元（Referer）にも残り得るため
  - 基本は、現在地を最寄りの駅・場所の ID に置き換えて URL にする。座標が要るときは、URL ではなく画面の中の状態として持つ
  - URL に座標を入れる場合（例：`from=@緯度,経度`）は、丸めて精度を落とす。共有用のリンクでは駅・場所の ID に置き換える。ログでは座標を記録しないか丸める。外部へのリンクには参照元を送らない設定（Referrer-Policy）を使う
  - 具体的な持ち方は実装で決める
- そのほかの条件（並べ方など）は `sort=` などで足す

### 6. 既定を地図にする設定

- Web のうちは `/detour` のブックマークで足りる。アプリを作るまでに、利用者の設定として持てるようにする

## Reason

- 企画と発見を真ん中に置くと、初めて来た人にも何のサービスかが伝わる。地図だけでは伝わりにくい
- 小さな地図から全画面へつなぐと、データがなくても面白い寄り道（ex-day/poc#40・#42）を、TOP から1回で触れる
- 中身のある枠だけを出す決まりにしておけば、初日と育ったあとで画面を作り分けずに済む
- 戻ったときに状態が消えると、あとで見ようとしたものが見つからなくなる。地図を1つに絞り、件数に上限を設ければ、メモリの心配を抑えて状態を保てる

## Alternatives

- **TOP を地図そのものにする**：何のサービスか伝わりにくい。スマホでは地図の操作とページのスクロールがぶつかりやすい
- **TOP を企画だけにする**：企画のない地域では出すものがない。寄り道の入口が遠くなる
- **初日と育ったあとで TOP を切り替える仕組みを持つ**：切り替えの基準と運用が要る。中身のある枠だけを出す決まりで足りる
- **URL を `/reach` にする**：到達圏は「片道で行ける範囲」の意味が強い。往復や帰り道も扱うので `/detour`（寄り道）にした（人の判断）

## Consequences

- 画面一覧：S01（TOP）を、企画と発見・小さな地図の形に書き直す。寄り道の画面（S12 の想定）を `/detour` で置く。場所のページ・企画のページを足す（DEC-0020・0021）
- C01（共通ヘッダー）：検索窓の横の「寄り道」リンクを `/detour` にする
- C06（検索条件）：利用可能時間は詳細の絞り込みへ移す（platform#134 の整理を引き継ぐ）
- API：TOP の枠ごとの中身を返す。並びを一定の間固定にするための仕組み
- TOP の小さな地図を軽く描くための、帯の形を返す API（SVG などで描く場合）
- 現在地の座標の扱い（URL・履歴・ログ・参照元）を、ログの方針と合わせて決める

## Deferred / Open Questions

- 枠の並び順と、各枠の件数
- TOP の並びを固定する期間（セッション、1日）
- 「あとで見る」の保存
- 場所の時期の情報（祭り、名所の分類）を出来事として扱うか
- 既定を地図にする設定の持ち方（アプリを作るまでに）

## Revisit Conditions

- 初めて来た人が、何のサービスか分からずに離れていると分かったとき
- 全画面の地図から戻ったときの状態の保持で、性能やメモリの問題が出たとき
