# DEC-0018: 会話の解析（F02）は、差分の取り出しと1日1回のまとめ直しを安いモデルで回し、表示の前の関所と予算の2つの枠で守る

## Status

Accepted（方針は人間が 2026-10-31〜11-01 に platform#127 で決定。本文は Claude が作成し、PR #133 のレビュー（送る前の費用の予約、解析とモデレーションの Workspace の分離、関所の費用の予約、抜き取りを止めない、段階3 をパイプライン単位に、先送り分のまとめ、API 側との照合の頻度）と人の確認を経て 2026-11-01 に Accepted）

## Date

2026-11-01

## Context

DEC-0015 で、会話の解析の構造を「Post → 主張 → わかってきたこと（説・価値）」とし、問いを独立した概念にし、除外の規則を決めた。DEC-0012 は AI による解析の原則（見立ては後から直せる、ただし除外は例外）を決めた。本 DEC は、その解析を**どう回すか**（単位・タイミング・モデル・品質管理・費用の上限・記録）を決める。platform#127 の手順1〜5 の判断をまとめたもの。

材料：

- ex-day/poc#34（PR ex-day/poc#35）：2段（主張 → わかってきたこと・問い）で取り出せる。除外は Sonnet 5.5・Haiku 5.5・GPT-5.6 Luna とも漏れ0（2本・12件、各1回）。Haiku は拾う量が多いが確かさを落として言い切る癖がある
- ex-day/poc#36（PR ex-day/poc#37）：日ごとに届く投稿を、新しい Post の分だけ主張を取り出す形で回しても、拾える量は会話全体のときとほぼ同じ（拾いたい知見 19.5 → 20.5 ／ 24）。返信の鎖を付けると「あの辺」の指す先も届く。2段目を差分の出力にすると、除外の漏れ（0 → 2）・除きすぎ・余計な問いが増え、状態の管理が複雑になる
- 単位あたりの原価（platform#127 手順4）：1日1,000投稿・Discovery 150件で、Haiku 5.5 標準なら月 約$46（1,000PV あたり 約2.5円、投稿率1%）、Sonnet 5.5 標準なら月 約$430
- 費用と収益（`docs/infra/cost-model.md`）、動かす場所（DEC-0017：定期処理は ECS のタスク、設定は環境変数、DB の接続を絞る）

前提（人の判断、ex-day/poc#34）：精度は最初から高くなくてよい（見立てとして出し、後から直す）。ただし除外は、表示した時点で害になるので後から直せばよい、とはいかない。当面は安いモデルで回し、利益が出てから上位モデルも考える。赤字が大きくなるのは避ける。

## Decision

### 1. 標準の経路

| 段 | いつ | 単位 | 入力 | 出力 |
|---|---|---|---|---|
| 0. 投稿 | すぐ | Post | ― | Post を保存。成立は解析を待たない（DEC-0005 決定7） |
| 1. 主張の取り出し | 夜のバッチ（1日1回） | **新しい Post だけ**（差分） | 新しい Post ＋ 文脈（返信の鎖（深さの上限つき）、直前の数件、器の Discovery の名前と場所） | 主張（根拠の Post の id、確かさの言い方を残す）、除外の状態と理由 |
| 2. まとめ直し | 1 のあと（1日1回） | Discovery | Discovery の場所 ＋ **有効な主張すべて**（除外済みは除く） | わかってきたこと・問いを、全体としてまとめ直す（差分の出力にしない） |
| 3. 表示の前の関所 | 2 のあと | 新しくできた・変わったわかってきたこと・問い | 2 の出力 | 表示してよいか（決定3） |
| 4. 表示 | 3 のあと | ― | ― | C25 などに出す |

- 1段目は新しい Post の分だけなので、会話全体を毎回送らない。文脈の初めの値は、返信の鎖の深さ8・直前5件（ex-day/poc#36 の値）。指す先の漏れを見て直す（設定で持つ）
- 1段目のタイミングは、MVP では夜のバッチとする。投稿のときに回す形（投稿のときのチェック（#35）と入力を共通にする）は、#35 で投稿のときに LLM を使うと決めたとき、または似た Discovery の案内（F03）に主張を使うときに改めて決める。その場合も、安全の判定と主張の取り出しは別の呼び出しにする（責務を混ぜない）
- 2段目は、新しい Post があった Discovery と、根拠の Post が削除・非公開になった Discovery だけを回す
- 2段目を全体のまとめ直しにすると、わかってきたことの id は毎回つけ直される。DEC-0009 決定4 の同一性のルール（Reaction を引き継ぐ更新か、別の新しいものか）を守るため、前回のわかってきたこととの対応づけを ex-day 側で行う。根拠の主張の重なりで対応づける
- 将来、会話がとても長い・更新がとても多い Discovery だけ、2段目を差分に切り替えることを考える
- Anthropic のバッチの API（半額）を使う場合は、処理を「依頼を送る」と「結果を取りに行き、確かめて反映する」の2つに分け、依頼と結果の対応・状態は DB に残す（1つの処理が結果を待たない）

### 2. モデルは段ごとに設定で持ち、固定しない

- モデルは、段ごと（1段目、2段目、関所の判定、上位の見直し）に設定で持つ。当面の標準は Haiku 5.5、上位は Sonnet 5.5
- 新しいモデルが出たり料金が変わったりしたら、その段だけ**評価用の一式**で確かめ直し、場合によって切り替える。評価用の一式は ex-day/poc#34・#36 の会話・正解・照らし合わせの指示（`context/extract/expected/`・`safety/`・`prompts/judge_synth_v2.md`・`judge_safety.md`）から始め、本番の会話から例を足していく
- 切り替えの判断に見る数字：除外の漏れ（**0 でなければ切り替えない**）、拾いたい知見・問い、確かさの消失の数、費用
- 標準のモデルを上位（Sonnet など）に上げる条件：上位で回したときの見込みの費用が、広告収入の5%以下に収まる月が3か月続いたら検討する。切り替える前に評価用の一式で確かめ、除外の漏れが0であることを条件にする

### 3. 品質管理と再チェック

**誤りの種類と扱い**

| 誤り | 害が出る時点 | 扱い |
|---|---|---|
| 除外の漏れ（危険・私人・店の評価などが出る） | 表示した時点 | 表示の前の関所で毎回止める |
| 除きすぎ | 表示されないだけ | 除外の理由ごとの件数から、別の経路で見直す |
| 確かさの消失・言いすぎ | 見立てとして表示される | AI なしで拾い、上位モデルで見直す |
| 見逃し | なし | 次の解析・定期の見直しで足す（DEC-0012 決定7） |
| 誤った関連付け・統合 | 構造に影響 | 提案の段階で慎重に扱う（#46） |
| 処理の失敗 | 反映が遅れる | 結果を機械的に確かめ、次のバッチでやり直す |

**表示の前の関所（毎回）**

- 1次は AI なし：除外の言葉の一覧（立入禁止・フェンス・裏口・線路を横切る、店名＋評価の言葉、人を指す言い方など）に当たるか
- 当たったものだけ上位モデルで判定する。**判定が出るまで、そのわかってきたこと・問いは表示しない**（保留）。Post 自体は保留にしない（Post の公開・非公開は #35）
- 関所の処理が失敗したら、表示しない側に倒す
- 費用の上限に近づいても関所は省かない（決定4）

**再チェックの対象の拾い方（多くは AI なし）**

| しるし | 拾い方 | 行き先 |
|---|---|---|
| 確かさの消失 | 根拠の主張に「気がする」「らしい」「かも」「聞いた」などがあるのに、わかってきたことの文にない | 上位モデル |
| 根拠が薄い | 根拠が主張1件・投稿者1人だけ | 表示はしてよい。採用の候補にはしない（DEC-0009 決定7） |
| 根拠の切れ | 根拠の Post が削除・非公開 | 次の2段目でまとめ直す |
| 利用者の反応 | 「違うのでは」・通報 | 上位モデル、必要なら人 |
| 大きな変化 | 前回との対応づけで、大きく変わった・失効した | 上位モデル |
| 除外の偏り | 除外の理由ごとの件数（「頼みごと」「感想」で落ちたものなど） | 別の経路で抜き取り確認 |
| ランダムな抜き取り | 見逃しの割合を知るため | 週1回、上位モデルで数十件。そのうち一部を運営が見る |
| 採用の候補 | Value などに採用する前 | **必ず**上位モデルか人（DEC-0009 決定7） |

- タイミング：表示の前（毎回）、出来事のとき（「違うのでは」・通報・採用の候補）、定期（週1回）、モデル・指示を変えたとき（前の版と抜き取りで比べる）
- 処理の失敗：形、主張の根拠が実際に渡した範囲にあるか、有効なわかってきたことが除外済みの主張を参照していないかを機械的に確かめる。通らなければ反映せず、次のバッチでやり直す。何度も失敗するものは記録して人へ
- 人の確認の場所：管理画面はいったん作らない（権限などを考える必要が出るため）。一覧（ファイルなど）や、汎用の AI のポータルのような仕組みで足りないかを含め、#37 と合わせて別に検討する

### 4. 予算は枠に分けて持ち、API へ送る前に費用を予約し、通常の枠を使い切る前に段階的に縮退する

**2重の上限と、API 側の分離**

- ex-day の設定の「システムの予算」で縮退を始め、各社の管理画面の「API 側の上限」を最後の安全網にする（システムの予算の120%）
- **解析と、投稿のときのモデレーションは、API の側でも分ける**。Anthropic では、F02 の解析専用の Workspace・API の鍵・支出の上限（$78）と、投稿のときのモデレーション専用の Workspace・API の鍵・別の上限を持つ。同じ Workspace・鍵・上限を共有すると、解析が上限に当たったときにモデレーションも拒否されるため。Default Workspace には支出の上限を置けないので、専用の Workspace を作る。組織全体の上限にも、モデレーションの分の余裕を残す（https://platform.claude.com/docs/en/manage-claude/workspaces ）

**枠**

| 枠 | 当初の値 | 使い道 |
|---|---|---|
| 通常の枠 | $58.5（予算の90%） | 1段目・2段目、定期の見直し、抜き取り。使い切った時点で解析を止める |
| 安全処理の枠 | $5 | 関所、出来事のとき（通報・「違うのでは」）の確認 |
| ずれの吸収の枠 | $1.5 | ex-day の計算と API 側の集計のずれ |
| システムの予算（合計） | **$65**（約1万円） | ― |
| API 側の上限（解析の Workspace） | $78 | 最後の安全網 |

- 安全処理の枠とずれの吸収の枠は、残りを分けて持つ（安全処理以外で使い切らないように）。分け方（$5・$1.5）は当初の値で、設定で変えられる（人の確認、2026-11-01）

**API へ送る前に、費用を予約する（費用の台帳）**

解析のあとに使った額を数えるだけでは、複数の処理やバッチの依頼が同時に「まだ予算内」と判断して送ると、終わったときに予算を超える。バッチの API は、送ったあとすぐに処理が始まり、取り消しても処理済みの分は残る。そこで、API へ送る前に、DB の上で一度に（ほかの処理と競合しないよう、ロックをかけて）次を確保する。

> 使える額 ＝ 予算 − 使った額 − 送った分の最大の額 − 安全処理の枠の予約

- 送った分の最大の額は、入力の実際のトークン数と、出力の上限（max_tokens）、モデル、バッチの割引などの料金の条件から見積もり、終わったら実際の額で精算する
- 費用の台帳は、使った額（spent）、送って結果待ちの最大の額（committed）、精算で戻った額（released）を分けて持つ。送った・処理中・やり直し待ちのものも予算に含める
- やり直しのための重複防止のキー（idempotency key）と、バッチの API の依頼ごとの id（custom_id）を持ち、同じ依頼を二重に数えない・送らない
- 1回の依頼の入力のトークン数・出力の上限、1つのバッチの件数・最大の額に上限を置く
- 料金の条件（モデル、価格表の版、バッチ・キャッシュなどの割引）の版を記録する
- **2段目を始める前に、その出力を関所に通す最大の費用も、安全処理の枠から予約する**。関所の費用が足りないときは、その2段目を始めない（作っても表示できない候補を積み上げない）

**縮退の段階**

| 段階 | 当初の値（使った額＋予約） | 止める・減らすもの | 続けるもの |
|---|---|---|---|
| 0. 通常 | 〜$30 | ― | すべて |
| 1. 注意 | $30 | 運営に知らせる。ランダムな抜き取りを**減らす**（週数十件 → 週数件。最低の件数は残し、危険の種類を優先する） | ほかはすべて |
| 2. 縮退 | $50 | 定期の見直しを止める。主張の多い Discovery の更新の間隔をあける | 出来事のときの上位の経路、関所、最低の抜き取り |
| 3. 最小 | $55 | **Discovery 単位で、「1段目 → 2段目 → 関所」まで終えられる仕事だけを、優先度の高い順に始める**（優先度：新しい Post の数、反応、更新が止まっている日数）。1段目だけを全件続けることはしない | 関所、最低の抜き取り |
| 4. 解析を止める | $58.5（通常の枠の上限） | AI の解析をすべて止める | Post の投稿・表示、安全処理の枠での関所・確認 |

- 当初の値は月 約$6（1日10投稿）の見込みに対する安全網で、主に処理の暴走・バグで費用が膨らむのを止める
- ランダムな抜き取りは、未知の除外の漏れ・見逃しを見つけるための計器なので、完全には止めない（除外を確かめた会話はまだ2本・12件・各1回のため）
- 閾値は、金額か、通常の枠に対する割合（当初の値で約51%・85%・95%）のどちらでも設定できる。値はすべて設定で変えられる
- **収益が出だしたら、これらの値を見直す。見直しが入らない場合は、システムの予算を「前月の収入の5%（ただし最低 $65）」とし、段階の閾値と枠は割合で追随させる**（人の判断）
- 段階は、使った額と予約の合計に加え、月末までの見込み（ここまでのペース）でも上げる。**月の中では段階は上がるだけにし、下げるのは月が変わったとき（リセット）か、人の操作による**
- **API 側との照合**：すぐの予算の判断は ex-day の費用の台帳で行う。Anthropic の使用量・費用の API（Usage and Cost API。データはおおむね5分で反映）で、バッチが動いている間は数分〜1時間ごとに照合し、ずれを見つける（https://platform.claude.com/docs/en/manage-claude/usage-cost-api ）。ずれが大きいときは運営に知らせ、段階を上げる

**月が変わったときの先送り分**

- 先送りした日ごとの処理を、古い順にすべて再生しない。2段目は有効な主張すべてから全体をまとめ直すので、**Discovery ごとに未処理を1件にまとめ、最新の主張すべてから一度だけまとめ直す**
- 新しい処理と、先送り分の片づけに、予算の比率を割り当てる（新しい投稿の反映が、先送り分のせいで再び遅れないように）

**変えない約束**

- 関所は省かない。回せないときは表示しない側に倒す
- Post の投稿と表示は、どの段階でも止めない
- 投稿のときのモデレーション（#35）は、解析とは別の予算・別の Workspace にし、解析の予算・上限が尽きても止めない

**画面と記録**

- 縮退の段階3以降で反映が遅れている Discovery では、わかってきたことのそばに「新しい投稿は、まだ反映されていません」のように控えめに出す。予算や縮退のことは利用者に見せない（C25）
- 運用で記録して見直す：各段階に入った日とその月の残りの日数、先送りした処理の量と片づくまでの日数、予約と実際の額の差、システムの計算と API 側の集計のずれ

### 5. 解析ごとに版と費用を記録する

- 解析の実行ごとに、モデルの正確な版、推論の設定、指示（プロンプト）の版、入出力のトークン数、計算した費用を残す（DEC-0015 決定4 の解析の版）。わかってきたこと・主張・問いは、どの実行で作られたかをたどれるようにする
- 設定の変更を記録する（誰が、いつ、どの値をどう変えたか）。費用や結果が変わったときに原因をたどれるようにする

### 6. 変えても問題のない値は設定にし、再起動なしで反映する

- **変えても安全を損なわない値は、すべて設定で変えられるようにする**（人の判断、2026-11-01）。例：予算、枠の配分（通常・安全処理・ずれの吸収）、段階の閾値、抜き取りの量と最低の件数、段階3 の優先度の重み、先送り分と新しい処理の予算の比率、1回の依頼・1つのバッチの上限、API 側との照合の間隔、文脈の範囲、段ごとのモデル、上位の経路へ回す条件
- 変えてはいけないもの（設定にしない）：「関所を省かない」「Post の投稿・表示を止めない」「モデレーションを解析と別にする」などの、決定4 の変えない約束
- 設定をどこ（ファイル・DB・環境変数・Parameter Store）に置くかは、実装の設計で決める（人の判断）


| 設定 | 反映 |
|---|---|
| 予算・枠の割合・段階の閾値、料金の単価、除外の言葉の一覧、1回の依頼・1つのバッチの上限 | すぐ（次の判断から。すでに予約・送った分は変えない） |
| 段ごとのモデル・推論の設定、指示の版、文脈の範囲 | 次のバッチから（1回のバッチの途中では変えない。モデル・指示が混ざらないように） |
| 抜き取りの量・頻度、上位の経路へ回す条件 | 次の定期の処理から |
| API の鍵・接続先（解析とモデレーションで別の Workspace・鍵） | 起動のときに読む（定期の処理は毎回起動するので、次の起動から） |
| バッチを回す時刻 | 定期実行の仕組み（EventBridge Scheduler）の設定 |
| API 側の支出の上限 | 各社の管理画面（ex-day の外） |

- 解析の処理は、毎回起動して終わったら消える処理にする（DEC-0017：EventBridge Scheduler から ECS のタスクを起動。API と同じコンテナイメージ）。起動のたびに設定を読むので、再起動という考え方がほぼなくなる。運営が手で「今すぐ回す」を呼んでも同じ処理が起動する
- ずっと動き続けるサーバー（API）で AI の設定を使う場合は、設定を短い間隔で読み直す作りにする
- 解析の処理は、画面・API を圧迫しないよう、DB の接続の数を絞る（DEC-0017 決定7）

### 7. 運用で追う数字

- 除外の漏れ（目標0）、関所で保留にした件数
- 上位モデルへ回した割合、再チェックで直した割合（訂正率）、「違うのでは」の割合
- 処理の失敗・やり直しの件数、反映までの時間
- 円／新規投稿、円／更新した Discovery、円／1,000PV、使った額と予算の段階
- PV／投稿、投稿／Discovery／日、主張の数の分布

## Reason

- 差分で主張を取り出しても拾える量は変わらず、返信の鎖で指す先も届く（ex-day/poc#36）。主張は保存してあるので（DEC-0015 決定2）、2段目は会話ではなく短い主張を渡せばよい
- 2段目を全体のまとめ直しにすると、差分の出力より除外の漏れ・除きすぎ・余計な問いが少なく、状態の管理も簡単。費用は Haiku・バッチで月 約$15（1日1,000投稿の概算）と小さい
- 安いモデル（Haiku）の標準なら、AI の費用は 1,000PV あたり数円で、広告収入の数%以下。上位モデルは、関所・再チェックの対象・抜き取りに絞って使う
- 除外は表示した時点で害になるので、関所は毎回・費用によらず通し、通らないものは出さない
- 予算を枠に分け、送る前に費用を予約することで、同時に動いても天井を守れ、解析を止めても関所・通報の確認は回せる。止める前に段階的に減らすことで、急に止まらない
- 解析とモデレーションを API の側でも分けることで、解析の上限がモデレーションに波及しない

## Alternatives

- **投稿ごとに Sonnet で解析する**：1,000PV あたり 約360円（投稿率1%）で、広告の目安を超える
- **2段目を差分の出力にする**：費用は下がるが、除外の漏れ・除きすぎ・余計な問いが増え、わかってきたこと・問いの追加・更新・失効と主張の除外の整合を取り続ける状態の管理が複雑になる（ex-day/poc#36）
- **1段目を投稿のときに回す**：主張がすぐできる。バッチの割引がなくなるが差は小さい。#35・F03 の判断を待つ（決定1）
- **話題（Topic）を段に入れる**：DEC-0015 決定3 で外した
- **モデルを固定する**：新しいモデル・料金の変化に追随できない
- **予算の 100% で解析を止める**：関所・通報の確認の分が残らない
- **使った額を解析のあとに数えるだけにする**：同時に動く処理・バッチの依頼で、予算を超える
- **解析とモデレーションで同じ Workspace・鍵を使う**：解析の上限でモデレーションも止まる
- **縮退でランダムな抜き取りを止める**：未知の除外の漏れを見つける手段がなくなる
- **解析を Lambda で回す**：DEC-0017 の Alternatives

## Consequences

### UI・機能

- F02（`docs/ui/functions/F02-conversation-analysis.md`）を、DEC-0015 と本 DEC に合わせて書き直す（話題の形成・更新を外し、主張の取り出し・まとめ直し・関所・再チェック・予算を書く）
- C25（わかってきたこと）：関所で保留中のものは表示しない。縮退で反映が遅れているときの控えめな表示

### Domain・Logical Entity（後続の作業：#132）

- DEC-0015 の Consequences（話題を外す、主張・問いを足す、わかってきたことの属性）に加えて、解析の実行（版・トークン数・費用）、バッチの依頼の状態（重複防止のキー、custom_id）、費用の台帳（使った額・予約・精算、枠ごと、料金の条件の版）、予算の段階、先送りした処理（Discovery ごとに1件）、設定の変更の記録、関所の判定（保留・結果）の持ち方を、ドメイン設計・論理設計に足す

### 運用

- Anthropic に、F02 の解析専用と、投稿のときのモデレーション専用の Workspace・API の鍵・支出の上限を作る（決定4）

- 評価用の一式を用意し、モデル・指示を変えるたびに使う。戦史・災害・刑場跡などの例を足す（platform#127 の後続の作業：歴史の話は残し、危険な入り方だけを除くか）
- 管理画面を作らない間の、人の確認のやり方（#37）
