# DEC-0023: 投稿した人に場所の入力を求めず、場所が分からないときは共有を誘う

## Status

Proposed（方針は人間が 2026-11-14 に platform#132 の議論で決定。本文は Claude が作成。PR #139 のレビュー（DEC-0005 の読み替え注記・DEC-0020 決定3 との食い違い）を受けて DEC にした。PR #139 の再レビューで、誘う条件を「採用した場所がないとき」にし、候補の有無で答え方を分けた。人の確認を経て Accepted にしてから PR #139 をマージする）

## Date

2026-11-14

## Context

DEC-0020 決定3 は、投稿のときに「どこの話？」とだけ聞き、粒度は問わず、選ばずに話し始めてもよいとした。DEC-0005 の DEC-0020 読み替え注記も「投稿のときに『どこの話？』を聞くが、任意で、選ばなくてもよい」としている。

人の考え（2026-11-14）：

- 初期の MVP では場所を指定させるつもりだったが、ワイヤーフレームを作ってみると、想像以上にユーザーの手間がかかりそうだった。それで文脈から場所を取れないかという方向に進んだ経緯がある。そこへ戻りたくない
- このサービスは、ユーザーに参加してもらわなければ成立しない。コミュニティの機能は薄いが、ソーシャルな部分はしっかりある。その参加の入り口の負担を重くしたくない
- ただし場所は大事。場所が分からない投稿は、場所未定として持ち、あとから候補を見られるようにすればよい。場所未定だと届く機会が減ることがはっきりしていれば、ユーザーは分かる範囲で入れてくれる可能性がある

投稿の入力欄に「どこの話？」を置くと、任意であっても、投稿のたびに考える項目が1つ増える。また、会話の解析はバッチで回す（DEC-0018）ため、解析の結果を待ってから場所を聞くことはできない。

## Decision

### 1. 投稿した人に場所の入力を求めない

- 投稿の入力欄に、場所の入力・選択の項目を置かない。場所が分からなくても投稿は必ず通り、場所未定の会話として持つ
- DEC-0020 決定3 の「投稿のときは『どこの話？』とだけ聞き」を、本 DEC の2・3に置き換える。粒度を問わないこと、場所を選ばずに話し始めてよいこと、話の中身から場所の候補を出して人が採用すること、あとから細かい場所に付け替えられることは変えない

### 2. 場所は入口と言葉から決める

- 場所のページ・Discovery のページ・企画の項目から「話す」で始めた会話は、入口から場所が決まる（会話の始まりの時点で、その場所を投稿した人が採用したものとして扱う。持ち方は論理エンティティ設計 4.3節）
- 投稿の直後に、LLM を使わない軽い判定（地名の辞書との照合。#82）で本文から場所の候補を出す。会話の解析（バッチ）で後から読み取った候補も加わる
- スマホでは現在地から近い場所を候補に出せる。ただし現在地を会話の場所とはみなさない

### 3. 場所が決まっていないときは、共有を誘う

- 入口などで場所がすでに決まっている（採用した場所がある）投稿には、誘わない
- 採用した場所がない投稿には、投稿の直後に、投稿した人へ場所の共有を誘う（「場所を共有すると、近くの人や同じ地域に興味のある人に届きやすくなります」のように）
- 答えは任意。投稿の直後の照合などで**候補があれば**、候補を並べてワンタップで確かめるだけにする。**候補がなければ**、地図で指す・現在地の近くから選ぶ。どちらも文字を打たせない
- 誘うのは、1つの投稿につき1回まで。断られたら、その投稿ではもう出さない
- 誘いは「自分の話」にも残し、あとから場所を足せる。解析で後から読み取った候補もそこで確かめられる

### 4. 場所未定でも不利に扱わず、届く機会の差は隠さない

- 場所未定だと届く機会が減ることは、投稿した人に隠さず伝える
- 共有しないことを理由に投稿を不利に扱わない。場所未定の会話は、候補の場所のページ、TOP の「探しています」、投稿した人の「自分の話」の道で届ける（ドメインモデル 3.4節）
- 場所が分からないことは、周りの人が「ここでは？」と答える参加のきっかけにもなる

## Reason

- 参加の入り口の負担を、場所の入力1つ分でも軽くする。場所が分からない投稿でも、入口・言葉・周りの人から場所が集まる
- 入力欄の項目は、任意でも「埋めるべきもの」に見える。投稿の後に、理由（届きやすくなる）を添えて誘う方が、同じ手間でも受け取り方が軽い
- 会話の解析はバッチなので、投稿の瞬間の判定は軽い照合で行い、解析の結果は後から「自分の話」で確かめられるようにする

## Alternatives

- **投稿の入力欄に「どこの話？」を置く（任意）**（DEC-0020 決定3）：場所がはっきりした投稿は早く場所が決まるが、投稿のたびに考える項目が増える。ワイヤーフレームで手間が大きいと分かった道に戻る
- **場所を必須にする**：参加の入り口が重くなる。場所が分からない投稿（古写真、昔の記憶）を受けられない
- **解析の結果を待ってから場所を聞く**：解析はバッチなので、投稿した人は画面にいないことが多い

## Consequences

- ドメインモデル 3.4節の会話の始まり方・入口の表・9.1節のシナリオを、本 DEC に合わせる（PR #139）
- 論理エンティティ設計に、投稿ごとの場所の共有の誘いの記録を持つ（1回までを守るため。PR #139）
- 画面（C27 新しい話を始める）に「どこの話？」の入力欄を足さない。DEC-0020 の画面の Consequences「投稿（C27）に『どこの話？』を足す」は、本 DEC の誘いに置き換える
- 地名の辞書（#82）に、投稿の直後の軽い判定の役割が加わる。MVP は地域を絞り、最初からすべてやらない（#82 のコメント）

## Deferred / Open Questions

- 誘いの文言と見せ方（画面の設計）
- 候補の出し方の細部（照合で拾った候補が弱いときに、候補として並べるか、候補なしとして扱うか）
- 返信（2件目以降の Post）で場所が分かる場合の扱い。誘いは会話を始めた Post にだけ出すか

## Revisit Conditions

- 場所未定の会話が多く、届け方の道（候補の場所のページ、TOP、自分の話）だけでは誰にも届かない会話が目立つ場合
- 誘いに答える人が少なく、投稿の入力欄に任意の項目を置く方がよいと分かった場合
