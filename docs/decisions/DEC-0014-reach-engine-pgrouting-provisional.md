# DEC-0014: 寄り道の到達圏は pgRouting で暫定採用し、リリース前の結合テスト開始までに R5 を含めて最終判断する

## Status

Proposed（方針は人間が 2026-10-10 に決定。本文は Claude が作成し、レビュー待ち）。2026-10-12 に、全国版の R5 の PoC（poc #30・PR #33）と入口の PoC（#31・PR #32）の結果を足し、最終判断の条件を改めた

## Date

2026-10-10（2026-10-12 改訂）

## Context

DEC-0013 で、寄り道の提案を MVP に入れることにした。そのための「行ける駅・場所の一覧」と「移動時間」を、何で計算するかを ex-day/poc で比べた。

| | pgRouting | OpenTripPlanner 2.11 | R5（r5py） |
|---|---|---|---|
| 検証 | #5・#6・#23・#27（PR #21・#22・#24・#29） | #7（PR #25）、#26（PR #28） | #26（PR #28） |
| 行ける駅の一覧 | 約0.6秒（＋歩きの事前計算） | 一対多の API が無い（等時間線は 2.5 まで）。駅ごとの問い合わせで全駅 約4,400回 | 行き・帰りで 0.6〜0.7秒 |
| 場所への時間 | 駅までの時間＋駅から場所の歩き（事前計算） | — | 場所 6,323件へ 2.0秒。代表の駅・歩きの事前計算が要らない |
| 置き場所・メモリ | 既存の Postgres の中 | 専用サーバー（関東で約6GB） | Python と同じプロセスの Java（関東で約4.5GB） |

わかったこと：

- 時刻表（利用条件の厳しい ODPT など）を使わず、N02 と表定速度から作った仮の GTFS で、OTP も R5 も動く
- pgRouting は、駅をまたいで歩く乗換を入れず、乗換を10分の固定にしているので、R5 と比べて行ける駅を1〜2割少なく出す（「行けない」側に寄せる方針どおり）
- 寄り道の提案の質は、pgRouting 側を直した（#27）あとは R5 に近い。上位10件の重なりは平均7件、降りる駅の一致は 79%。残る違いの多くは駅の代表点（ホームの重心）
- Discovery は駅ではなく場所（点または範囲）に結び付く。駅を中心に到達圏を計算する pgRouting より、OSM の歩く道も使って実際の目的地まで届く R5 のほうが、ドメインの上では自然
- ただし、範囲のある Discovery（公園・湖など）の入口・到達点の決め方は、R5 でも別に要る
- 費用（参考。どれも構成で変わる暫定の値）：pgRouting は追加無し。R5 は関東で月 約1〜2万円（実測の約4.5GB から）。全国は下の poc #30 の結果。月 約7万円は OTP の全国の試算（以前の概算で R5 と混同していたので訂正）

全国版の R5（poc #30・PR #33）：

- **手を加えていない R5 では、日本を1つの交通網にできない**。R5 本体の入力の検証で、外接する四角の面積が 97.5万km² までに制限されている（日本の OSM は約676万km²、本州・四国・九州だけでも約137万km²）。フォークすれば変えられるが、標準の R5・r5py では変えられない
- 重なりのある3地域（北海道、東＝東北〜近畿、西＝近畿〜九州）なら作れた。作るときの最大は東で RSS 約9.7GB・329秒。保存した交通網を読んだあとの Java ヒープは東 3.0GB・西 2.3GB・北海道 0.4GB。地域をまたぐ移動（東京 → 博多など）と離島は、そのままでは扱えない
- 1件で CPU を約2.2個分使い、同時4件のあたりで1秒あたりの件数が頭打ちになる（東、12コアの Mac で 1.5〜1.9件）。同時に計算する数を絞って待たせる前提
- 費用（計算のサーバーだけ）：3地域を常に動かして月 約1.5万円（r7g.large）〜3万円（r7g.xlarge）。ALB・ログ・冗長化・転送は別

入口・駅の出入口（poc #31・PR #32）：

- 範囲のある場所の到達点（入口・道との交わり・範囲の端）は、pgRouting でも R5 でも同じように効く。位置の持ち方は DEC-0013 決定5で、計算の仕組みに依らずに決めた
- 駅のまわりの歩きのずれ（東京駅の中の場所が駅から歩き16分）は、駅の代表点ではなく、N13 に駅の中・駅前の歩ける道が無いことが原因。OSM の道で歩けば直る見込み（R5 では出入口から歩くと、組の1割強で3分以上短くなった）
- pgRouting と R5 の差には、仕組みの差だけでなく道路データの差（N13 と OSM）が入っている（PR #33 のレビュー）

比較の詳細は poc の `reach/otp/README.md`、判断の表は DA表の下書き（platform の `Claude outputs/DA-reach-engine.draft.md`）。

## Decision（案）

### 1. 到達圏は、今は pgRouting を暫定採用して実装・検証を進める

- 行ける駅の一覧（`reach.reachable`）と、駅から場所への歩き（`station_spot_walk`、N13）を使う
- poc #27 の直し（遠回りに歩きの往復を入れる、出発駅・帰着駅も最寄りの駅に使う）を前提にする
- 「MVP で確定採用」ではない

### 2. API と Discovery の位置情報のモデルは、計算の仕組みに依らない形にする

- API は「行ける場所の一覧と、時間の目安（行き・帰り・遠回り・余裕）」を返す。駅を経由するか、場所へ直接届くかは、API の外に出さない
- Discovery の位置は、代表点・範囲・到達点・行き方で持つ（DEC-0013 決定5。2026-10-12 に決めた）。行き方（「○○駅から徒歩○分」）があるときは、駅から先を計算せずにその分数を使う（DEC-0013 決定3）
- 到達点と行き方は手段（徒歩・車・バス）を持ち、API も手段を引数に足せる形にする（今は鉄道＋徒歩だけ）
- これにより、最終判断を先に延ばしても、実装を止めずに進められる

### 3. リリース前の結合テストを始めるまでに、R5 を含めて最終判断する

- 判断の観点：機能（場所へ直接届く、OSM の歩き、ほかの交通を足せる）、品質（提案・降りる駅の自然さ）、運用負荷（交通網の作り直し、メモリの管理、データの更新）、固定費
- 全国版の R5 の PoC は済んだ（poc #30・PR #33）。判断の前に、次を行う（PR #126 のレビュー）
  - **同じ道路データでの比較**：都市部・郊外・広い施設から30〜50件を選び、同じ OSM のスナップショットと同じ到達点で、pgRouting（歩きを OSM にしたもの）と R5 を比べる。公式のアクセス（DEC-0013 決定3）との一致、作る時間、性能を見る
  - **データ更新の運用試験**：OSM の更新 → 作り直し → 切り戻しを一度通す
- MVP の暫定の形としては、「N02 由来の鉄道の到達圏＋OSM の歩きのネットワークを PostGIS・pgRouting で前もって計算し、公式の行き方があればそれを優先する」が有力（PR #126 のレビュー）。歩きを N13 から OSM に替えることは、上の比較で確かめる

### 4. OpenTripPlanner は使わない

- OTP 2.11 には一対多の API が無く、行ける駅・場所の一覧を数秒で出せない

## Consequences

- 暫定採用の間は、駅の代表点（ホームの重心）による割り当てのずれが残る（例：東京駅の中の場所が、駅から歩き16分と出る）。歩きは N13 のまま
- 駅をまたぐ徒歩乗換をしないので、行ける駅は R5 より1〜2割少なく出る（「行けない」側に寄せる方針どおり）
- R5 に切り替える場合、提案の仕組み（駅経由 → 場所へ直接）が変わる。API と位置情報のモデルを計算の仕組みに依らない形にしておくことで、変更を API の内側に閉じ込める

## Deferred / 後続

- ~~全国版の R5 の PoC~~：済み（poc #30・PR #33。結果は Context）。本番に採る前の後続：
  - 3つの交通網を同じ JVM に載せた状態のメモリと、同時の検索
  - 東京リージョンの 2・4 vCPU の Graviton の実機での測り直し
  - 一定の間隔で検索が来るときの p50・p95・p99、GC、待ちの長さ
  - 地域をまたぐ移動の代わり（回廊の交通網を足す、pgRouting の結果を返す、など）
  - 交通網の更新と切り戻しの手順（R5・r5py の版と作った交通網をそろえる）
- **範囲のある Discovery の入口・到達点**：OSM の部分は poc #31（PR #32）で確かめ、位置の持ち方は DEC-0013 決定5で決めた。公式の施設のサイトからの行き方の取り出し（#31 の 3）と ODbL は残る。利用者による「行き方」の登録（DEC-0013）を MVP でどこまで要るとするかは、その結果で判断する
- **駅の代表点を改札・出入口にする**（pgRouting のままの場合。poc #24 の後続）：N13 の上では効かない（駅のまわりの歩ける道が無いため。poc #31）。歩きを OSM にする比較（決定3）と合わせて確かめる
- 比べるときの留意点（poc PR #28 のレビュー）：R5 の帰りの近似（帰着駅 → 場所）は仮 GTFS の条件での結果、R5 の候補の判定は一律20分の余裕を足した参考値、仮 GTFS は直通を分けて乗換を生みうる

## Alternatives

- **MVP で pgRouting を確定採用し、R5 は費用見合いで後から判断する**：固定費は最小だが、Discovery が場所に結び付くことと、駅中心の計算のずれを、リリース後まで持ち越す
- **最初から R5**：場所へ直接届き、代表の駅・歩きの事前計算が要らない。ただし、全国を1つの交通網にできず地域に分ける必要があり（地域をまたぐ移動は別の手当て）、常に動く Java のサーバー（3地域で月1.5〜3万円）と、同時アクセスの制限（同時4件のあたりで頭打ち）が要る（poc #30）
- **経路探索を自前で作る**：ex-day が自前で作る価値があるのは、行き・帰り・滞在・余裕・遠回りを合わせた到達圏のサービス、行き方の順番、出どころ・鮮度・確かさの管理のほう。道路の最短経路の探索そのものは、pgRouting で足りないと測れてからでよい（PR #126 のレビュー）
- **Valhalla**：車・徒歩は得意だが、鉄道・バスの乗り継ぎの一対多が使えないので、寄り道の中心に合わない
- **OTP**：一対多が無く、到達圏の計算には使えない（2.5 までの等時間線の API は保守されていない）
- **時刻表（ODPT など）を使う**：利用条件の多くがチャレンジ向けで、ex-day では使えない。「だいたい○○分」でよい前提とも合わない
