# DEC-0003: S04/S11とContribution AI解析の責務境界

## Status

Accepted（方針として合意。Function定義・Issue化は未着手）

## Context

Issue #18（S04 Wireframe）の1st pass比較（案A：現行定義どおりの単一フォーム／案B：本文優先＋場所・時期の折りたたみ）で、現行S04定義どおりに全項目を並べると初期表示が重く、入力負荷が投稿のモチベーションを下げうることを確認した。

一方で、場所・時間等の入力を単に折りたたむだけでは、「未入力のままS11へ進んだ場合、その情報をどこで・どう補うか」という課題が残った（S04-contribution-save.mdの検討事項「入力負荷、時間入力をS11へ寄せるか、中間補完を挟むか、AIとの対話式入力にするか」に対応）。

この課題を検討する中で、以下の論点が連鎖的に出た。

- AI解析をどのタイミングで発火させるか（入力中／フォーカス喪失時／確認へ進む時）
- AIによる推定と、DEC-0002が避けた「観測事実からDiscovery/Valueへの一般化」の混同リスク
- S04内でAIが対話的に入力へ介入すること（「AIに聞きながら入力する」）が、投稿者の所有感・投稿動機に与える影響
- ex-day_requirements.md 13〜15章・22章に既に記述されている、疑問／知識それぞれの投稿動機の違い

これらを踏まえ、S04・AI解析・S11の責務分担について合意した内容を本Decisionに記録する。

## Decision

1. **S04**は「気軽に投稿できる場所」に留める。本文または資料の少なくとも一方があれば「確認へ進む」ことができる。場所・時間等の詳細は、ユーザーが明示したい場合の任意入力として残すが、S04内でAIとの自動対話・自動解析は行わない。
2. Contributionの解析は、「確認へ進む」ボタン押下のみをトリガーとする独立した**Function**（`docs/ui/functions/`、既存F01-discovery-sections.mdの形式を踏襲。仮称：contribution-analysis）として切り出す。
3. 画面遷移は「解析してから渡す」方式ではなく、**「受け取って解析する」方式**を採る。S04はFunctionの完了を待たずにS11へ遷移し、S11が受け取ったContributionを元にFunctionを呼び出し、結果を表示する。
4. **S11**は「AI解析結果を確認する画面」に役割を変える。確度が高い候補は選択済み状態で提示し、確度が低くDiscovery/Value形成に必要な項目のみユーザーに確認を求める。
5. Functionが返すのは、あくまで「そのContributionについて言える候補」までとする。複数Contributionの積み上げを要するDiscovery/Valueの確定条件への一般化は、Function・S11のいずれの責務にも含めない。
6. 「AIに聞きながら入力する」ようなS04入力中の対話的アシストは、デフォルトの自動フローに含めない。将来的に扱うとしても、ユーザーが明示的に選択するオプション機能として別途検討する。

## Reason

- 入力負荷の検証（Issue #18 1st pass）で、単一フォームは初期表示のフィールド数が多く重いことを確認した。折りたたみだけでは「未入力分をどこで補うか」が残るため、AIによる解析結果の確認へ置き換える方向性を検討した。
- 発火タイミングを本文欄のフォーカス喪失や入力中にすると、頻度が高すぎて費用対効果が悪い（同一内容にほぼ近い解析が何度も走る）。「確認へ進む」を唯一のトリガーにすることで、発火回数が投稿1件につき1回に定まり、解析対象も最終的な入力内容になるため無駄が出ない。
- 「解析してから渡す」方式だと、解析完了までの待ち時間をS04かS04/S11間の新しい画面状態のどちらかが背負う必要があり、S04を軽く保つ方針と矛盾する。「受け取って解析する」方式なら、S04→S11の遷移は即座に行い、解析中の状態はS11自身の初期ローディングとして扱える。S11から「入力内容を修正する」で戻って再度確認へ進んだ場合の再実行や、解析失敗時のフォールバックも、S11という1画面の責務に閉じ込められる。
- Contributionの解析をFunctionとして切り出すことで、S11の責務は「いつ呼ぶか・どう見せるか・失敗時どうするか」というUI/オーケストレーションに絞られ、解析ロジックの契約（入力・出力・確度の扱い）はFunction側の関心事として独立する。既存の案D（S11事後チェックフロー）にある「類似検索＋AI」との関係（同一Functionの再利用か別Functionか）も、Function単位で明示的に検討できるようになる。
- 単一のContributionが示す情報をそのままDiscovery/Valueの確定条件に格上げすると、DEC-0002が避けた一般化の問題を再導入してしまう。「このContributionについて言える候補」と「Discovery/Valueの確定情報」を明確に分離する必要がある。
- S04入力中にAIが対話的に介入すると、投稿者が「自分の言葉で語った」という所有感が薄れ、投稿動機を損なうおそれがある（ex-day_requirements.md 13〜15章が前提とする「疑問／知識」それぞれの投稿動機とも関連）。AIの関与はユーザーの入力が一段落した後（確認へ進む以降）に限定する方が安全。

## Alternatives

- **案A**：現行S04定義どおりの単一フォーム（Issue #18 1st pass比較のベースライン）。入力負荷が高く不採用。
- **解析してから渡す方式**：S04→解析Function→S11、解析完了を待ってからS11へ遷移する案。待ち時間の責務・再実行・失敗時フォールバックが画面をまたいで曖昧になるため不採用。
- **S04内でAIとの対話的入力をデフォルト動線にする案**（「AIに聞きながら入力する」）：発火頻度・コストの問題に加え、投稿動機（所有感）を損なうおそれがあるため、デフォルトでは不採用。将来的なオプション機能としては排除しない。

## Consequences

- S11は初期表示時にローディング状態（解析中）を持つ必要がある。S11 Wireframe再開時（Issue #40）にこの前提を反映する。
- Contribution解析を担うFunctionを新規定義する必要がある（`docs/ui/functions/`）。現状Function（F0x）には、Component（C0x）のような採番・レビュー手順が明文化されていないため、あわせて運用ルールの整備が必要になる可能性がある。
- Issue #1（pgvector技術検証）の結果が、既存Discovery候補の確度に直結するため、Function実装は段階的（本文解析→資料メタデータ→既存Discoveryとのベクター照合）に進めることが望ましい。

## Deferred / Open Questions

- Contribution解析Functionの入出力契約の詳細（確度の階層定義、対象範囲の段階分け）
- 解析失敗・利用不可時のフォールバックUIの詳細設計
- 1つのContributionから複数のDiscovery/Value候補が生まれるケース（例：小机城址の公園/中世の城）のS11での提示方法
- 複数Contributionの積み上げからDiscovery/Valueの確定条件を形成するプロセスの所在（S11の外、運営レビュー、案Dの事後チェックフローとの関係等）
- 案Dの事後チェックにおける「類似検索＋AI」と、本Decisionの解析Functionの関係（同一Functionの再利用か、別Functionか）
- Contributionそのものをメインコンテンツとして扱う方向性（投稿動機を高める別の切り口。本Decisionのスコープ外、別途検討）

## Revisit Conditions

- Issue #1（pgvector技術検証）の結果が判明した場合
- S11 Wireframe（Issue #40）またはFunction定義の設計時に、本Decisionの前提と矛盾する制約が見つかった場合
- 「AIに聞きながら入力する」機能を実際に検討する場合
