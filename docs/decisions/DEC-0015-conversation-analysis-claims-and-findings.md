# DEC-0015: 会話の解析を「主張 → わかってきたこと」の順にし、話題を必須の段から外す

## Status

Proposed（方針は人間が 2026-10-31 に決定（platform#127 の手順1）。本文は Claude が作成し、レビュー待ち）

## Date

2026-10-31

## Context

DEC-0009 で、会話の理解を「Post → 話題（Topic）→ 発見の仮説 → わかってきたこと」の順に育つ見立ての層として定めた。話題を保存し、「既存の話題の要約＋新しい Post」を主な入力とすることで、過去の全 Post を毎回解析する費用を避ける、という判断だった（DEC-0009 決定2）。

その後の PoC で、次のことが分かった。

- 会話の Post を話題に振り分ける方法（ex-day/poc#8・#14）：ルールとベクトルでは振り分けられず、AI に会話の全文を渡すと振り分けられる。10件ずつ順に渡すと下がる（数字は DEC-0012 の Context）。
- 会話から、わかってきたことを根拠の Post の id 付きで取り出す方法（ex-day/poc#34、PR ex-day/poc#35。出典：ex-day/poc の `context/extract/README.md` 途中経過1〜7）：
  - 1段目で、発言ごとの**主張**（自己完結した1つの主張）を、根拠の Post の id 付きで取り出す。2段目で、主張を束ねて**わかってきたこと**と、**答えが付けば確かになる問い**を書く。この2段の形で、拾いたいわかってきたことは Claude Sonnet 5.5 で 12／13・11／11（会話2本、AI による照らし合わせ）
  - 主張の根拠が、人の付けた正解の話題をまたいだのは99件中1件だった。**話題に分けることを、取り出しの前提にしなくてよい**
  - 出してはいけないもの（危険な情報、店の評価、私人についての情報、同意なく頼むような話、会話の中で否定された推測）は、2段目で落とせた（Sonnet 5.5・Haiku 5.5・GPT-5.6 Luna とも、会話2本・12件中0件の漏れ）
  - どれも各条件1回で、揺れは測っていない

DEC-0012（下書き）は、「わかってきたことを先に取り出し、話題は後からできるものとする案」を、この PoC のあとで判断するとして先送りしていた。本 DEC で、その判断をする。

人間の判断は platform#127 のコメント（2026-10-31。手順1の D-1〜D-5）と、ex-day/poc#34 のコメント（除外の規則など）に記録している。

## Decision

### 1. 解析の順番を「Post → 主張 → わかってきたこと」にする

| 段 | 中身 | 根拠 |
|---|---|---|
| 主張（Claim、仮称） | 1つの Post、または問いと答えのような数件の Post から読み取れる、自己完結した1つの主張 | 根拠の Post の id |
| わかってきたこと（Finding） | 主張を場所・対象ごとに束ね、その場所について何がわかるかを書いたもの | 束ねた主張の id（たどれば Post まで戻れる） |

- 主張は、見立ての層（DEC-0009 決定1）の内部の概念とし、画面には出さない。
- わかってきたことは、これまでどおり画面に出す（C25）。

### 2. 主張を保存する

- 主張は、見立ての層として保存する。Post・返信・資料を原本とし、主張は原本から作り直せるもの（DEC-0012 決定6）として扱う。
- 保存を基本の方針とする。AI で取り出し直す費用と保存の費用は実測して見直し、費用に応じて、主張の履歴や保存する量を調整する。
- 保存の費用は小さい見込み（1日1,000投稿で1日 約0.3MB、1年で100MB前後）。保存しないと、解析のたびに会話全体から主張を取り出し直すことになる（Haiku 5.5 でも Discovery 1つ・1回あたり 約$0.006。ex-day/poc の `context/extract/cost.py` の近似）。
- 保存した主張は、次に使う。
  - 差分の解析：新しい Post の分だけ主張を取り出す（解析の単位・タイミングは platform#127 で決める）
  - 再チェックの対象を AI なしで拾う：主張にあった「気がする」「らしい」が、わかってきたことで消えた、など（platform#127）
  - 根拠のたどり：わかってきたこと → 主張 → Post
  - モデルや指示を変えたときの比べ：同じ会話で、前の版の主張・わかってきたことと並べる

### 3. 話題（Topic）を必須の段にせず、いったん概念から外す

- 話題は、AI の費用を抑えつつ価値・疑問の抽出の精度を上げるための試行錯誤の中で置いた段であり、最後の PoC（ex-day/poc#34）では使っていない。必須の段にしない。いったん、見立ての層の概念から外す。
- 将来、画面の整理、検索、長い会話の要約などに必要になった場合は、話題を、保存した主張・わかってきたことから作り直せる派生の情報として生成・保存してよい。ただし、わかってきたことが成り立つかを左右する必須の段にはしない（Alternatives、Revisit Conditions）。
- 人間が作った返信（Post 間の参照）や会話のまとまりと、AI が作る話題は、別のものとして扱う。
- 発見の仮説（DiscoveryHypothesis）は、話題ではなく、わかってきたことを場所・対象などで束ねるときにできるものとする。突き合わせ（DEC-0009 決定7）の単位として使う。保持の方法は論理 Entity 設計で決める。

### 4. わかってきたことの種類は、説・価値の2つのまま

- 種類は DEC-0009 決定4 どおり**説**と**価値**の2つとする。種類を増やすのは最後の手段にする。
- PoC で「事実」として分けたもの（「天金は今もある」「赤灯台の堤防は立入禁止」など、会話で述べられた場所・店・道についての情報）は、説（観察）に含める。わかってきたことは、支えが厚くなっても ex-day が事実と認定した情報ではない（DEC-0012 決定4）。
- 確かさの違いは、種類を増やすのではなく、属性で扱う：根拠（どの主張・Post に支えられているか、支えの厚さ）と、表現（「気がする」「らしい」「〜だという」などの確かさの言い方を残すか）。確度の数字を AI に返させないこと（DEC-0012 決定5）は変えない。
- わかってきたことに、次の属性を持たせる（人間の判断は ex-day/poc#34 の人の確認、`context/extract/results/synth/human_review.json`）。
  - 今もそうかが未確認であること（「昔あった」「あったよね」だけで、今もあるかが分からないもの）。なくなったと言い切らない
  - 関連する場所：器の Discovery の場所とは別の場所についてのわかってきたこと（例：鶴見の会話に出た川崎・野毛）。ほかの Discovery との突き合わせや、似た Discovery の案内（F03）の材料にする
  - 解析の版：モデルの正確な版、推論の設定、指示の版、入出力のトークン数（DEC-0012 の Consequences、PR ex-day/poc#35 のレビュー）

### 5. 問い（まだわかっていないこと）を、独立した概念にする

- AI が立てる「答えが付けば、そのわかってきたことが確かになる問い」を、独立した概念とする（仮称：問い、OpenQuestion）。問いを生み出したわかってきたこととの関係を持つ。
- 保存の持ち方と、画面での見せ方は分けて考える。
  - データの持ち方：問いは、必要に応じて**複数の**わかってきたことと関係を持てる形にする。回答済み・未回答の状態、問いの中身の変更も、後から扱える余地を残す
  - 当面の解析の規則：1つのわかってきたことから作る問いは、1つまで（下記）
- 会話の中で出て、答えのない問いは、これまでどおり Post である（DEC-0009 決定4）。AI が立てた問いと区別し、会話で出た問いには、その Post を参照させる。
- 問いは、わかってきたことには含めない（DEC-0009 決定4 のまま）。DEC-0009 決定4 の「まだわかっていないことは、話題の要約の一部として表す」は、話題を外すため、本決定で置き換える。
- 画面では、わかってきたことの中に「これが分かるとさらに確かになること」として出すことも、Discovery に「こんな情報を求めています」として出すこともできるようにする。どちらにするかは、見せ方の判断として UI で別に決める。
- 当面の解析の規則として、1つのわかってきたことから作る問いは1つまで（いちばん確かめたいもの）とする（PoC の v3 の指示）。データの持ち方（複数と関係を持てる）とは分ける。

### 6. 除外の規則

次のものは、わかってきたことにも問いにもしない。会話に書かれていても、主張として取り出されていても、2段目で落とす（人間の判断は ex-day/poc#34 のコメント）。

| 除外するもの | 理由・補足 |
|---|---|
| 危険な情報（立入禁止の場所への入り方、危ない近道など） | 本人だけでなく、場所の管理者や、何かあったときに対応する人にも迷惑がかかる。**絶対に**知見にしない。「立入禁止である」こと自体は書いてよい |
| 店の評価（良い・悪い、安い・高い、おいしい・まずい） | 店の評価は ex-day でする必要がない。店については存在と特徴（何の店か、どこにあるか、何を売っているか）だけを残す |
| 私人についての情報（投稿者、店主、近所の人、事故にあった人など） | 同意なく個人を出さない。名前の入った店名・地名は、場所の名前として書いてよい。歴史上の人物や記録に残る人は、場所の歴史の一部として書いてよい（主語は場所） |
| 公開されると店や第三者が困るかもしれない情報（店が表に出していない頼みごとを聞いてくれる、など） | 同意なく、他者に何かを求めることになる |
| 撤回・訂正された説、問いの形で出て否定された推測 | 例：投稿者自身が「勘違いだった」と訂正した説。「大塚神社って、大塚さんって人が建てたの？」→「違うよ」（PoC の除外の会話）。**別の人から反対意見が出ただけの説は除外しない**（下記） |
| 人によって受け止めが違う注意や感想（運転の注意など） | 知見にしない |

- **反対意見と対立する説は、除外と区別する。** 別の参加者が反対しただけの説は、元の説を落とさない。両方を残し、対立する関係として扱う（DEC-0012 の「支持する／反する関係」、2026-10-06 の人の判断「反対の意見は、同じ話の中の反対意見として扱う」）。対立する説をつなぐ関係の持ち方は Deferred。
- 除外は「見立てに入れるか」の責務である。わかってきたことから除外したこと自体は、Post の公開・非公開を決めない。Post の可視性は、#35 のモデレーションで別に判断する。
- **除外した主張が、差分の解析で戻らないようにする。** 除外するものも一度は主張として取り出されるため、主張を保存して次の解析に使うと、除外したものが将来のわかってきたこと・問いに戻るおそれがある。そこで、次を論理設計・F02 の要件とする。
  - 主張に、除外の状態と理由を持たせる
  - 除外した主張は、通常のわかってきたこと・問いを作る入力に戻さない
  - 除外の見直し（除きすぎの確認など）が要るときは、通常の経路と分けた経路で行う
- 除外は、表示した時点で害になるため、「後から直せばよい」とは扱わない（DEC-0012 の「後から直せる」の例外）。表示の前に毎回確かめる方法は platform#127 で決める。

### 7. ほかの呼び名は問いにせず、会話に出たら別名の候補として持つ

- 道や場所のほかの呼び名を、AI が問いとして立てることはしない。
- 会話の中で、同じ場所が別の言い方で呼ばれていたら（略称、地元の呼び方）、別名の候補として持つ。持ち方は、内部で持つタグ（TagMapping、DEC-0009 決定10）または地名の辞書（#82）と合わせて決める。
- 別名は、どの場所の別名か、どのあたりで通じる呼び方かをあわせて持つ必要がある（例：「2国」は品川〜横浜あたりで第二京浜＝国道1号を指す）。

### 8. 派生の流れの読み替え

- DEC-0009 決定8 の「話題を派生先へコピーし、派生先の最初の話題にする」は、「派生の根拠となったわかってきたこと・主張・Post の集まりを、派生先から参照する」に読み替える。Post はコピーせず参照する点は変えない。
- DEC-0007 決定1（補完・派生は Post 単体でなく文脈のまとまりを単位に判断する）は、趣旨（Post 単体では判断しない、1人の1つの発言だけでは候補にしない）を維持し、単位を「わかってきたことの束と、その根拠」に読み替える。
- 器の Discovery から遠いわかってきたことを、どう派生の候補にするかは、引き続き検討する（Deferred）。

## Reason

- PoC で、話題に分けずに主張から直接わかってきたことを作れると分かった。話題を必須の段にすると、話題の振り分け（AI でも完全にはできない）の誤りが、その先のわかってきたことに持ち込まれる。
- 主張を保存すると、根拠の Post をたどれる形を保ったまま、差分の解析ができる。保存の費用は、取り出し直す費用よりずっと小さい。
- わかってきたことの種類を増やすと、画面・Reaction・判断材料のすべてに影響する。観察を説に含めれば、今の DEC-0009 の枠組みで扱える。
- 問いの見せ方は決まっておらず、変わる可能性がある。独立した概念にしておけば、見せ方が変わっても、データの持ち方を変えずに済む。
- 除外の失敗は、見逃しや誤りと違い、表示した時点で人に害が及ぶ。見立ての誤りと同じ「後から直す」扱いにできない。

## Alternatives

- **話題を必須の段として残す案**：PoC で取り出しの前提にしなくてよいと分かり、話題の振り分けの誤りを持ち込むため採用しない。ただし、次の場合には、話題を（必須ではない形で）戻すことを検討する（Revisit Conditions）。
  - 会話を区切って見せたい（長い会話の目次、話の流れの表示など）
  - 話の流れを、派生や「続きの投稿への注記」（C26）の材料にしたい
- **主張を保存せず、解析のたびに取り出し直す案**：費用が大きく、差分の解析もできないため採用しない。
- **わかってきたことの種類に「事実」または「観察」を足す案**：種類を増やすのは最後の手段にする（人間の判断）。「事実」という名前は、ex-day が認定したように見える（DEC-0012 決定4）。
- **問いを、わかってきたことの属性として持つ案**：見せ方が「Discovery として情報を募集する」形に変わったとき、持ち方を変える必要が出るため採用しない。
- **まだわかっていないことを、話題の要約の一部として表す案（DEC-0009 決定4）**：話題を外すため採用しない。
- **除外を、ほかの誤りと同じく「後から直す」扱いにする案**：表示した時点で害になるため採用しない。
- **反対意見が出た説を除外する案**：対立する見解を表せなくなり、DEC-0012 の「支持する／反する関係」とも合わないため採用しない。除外するのは、撤回・訂正された説と、問いの形で出て否定された推測に限る。
- **除外した主張を保存せず、毎回捨てる案**：除外の理由を後から確かめられず、除きすぎの見直しもできないため採用しない。保存したうえで、通常の入力に戻さない。

## Consequences

### DEC-0009 との関係

DEC-0009 の本文は書き換えない。本 DEC で次のように変える。

| DEC-0009 | 本 DEC での扱い |
|---|---|
| 決定1（3つの層、判断時点で根拠を固める） | 変えない。主張は見立ての層に入る |
| 決定2（話題を保存し、「要約＋新しい Post」を主な入力にする） | **置き換える**（決定1〜3）。入力の形は platform#127 で決める |
| 決定3（話題が発見の仮説を持つ） | **置き換える**（決定3）。発見の仮説は、わかってきたことを束ねるときにできる |
| 決定4（わかってきたこと） | 種類（説・価値）、同一性のルール、版の履歴は変えない。「まだわかっていないことは話題の要約の一部」を置き換える（決定5） |
| 決定5・6・7・9・10 | 変えない |
| 決定8（派生のとき話題をコピー） | **読み替える**（決定8） |
| 決定11（名前） | 話題（Topic）を外す。主張（Claim）・問い（OpenQuestion）を仮称として足す |

### Domain・Logical Entity

- ドメイン設計 2.1節（3つの層の表と図）、3.5節（話題・発見の仮説・わかってきたこと）を直す。話題を外し、主張と問いを足す。
- 論理設計 6A節：Topic を外す。Claim（除外の状態・理由を持つ）・OpenQuestion（複数の Finding と関係を持てる、回答の状態を持てる）を足す。Finding に、根拠の主張、今もそうかの状態、関連する場所、解析の版を足す。DiscoveryHypothesis の多重度を見直す。
- 4.6節（派生が確定したときの流れ）を、決定8 に合わせて直す。

### UI・機能

- F02（投稿後の会話の解析）：関連概要・アクションから話題の形成・更新を外し、主張の取り出しと、わかってきたこと・問いの作成・更新に置き換える。解析の単位・タイミング・モデルの分担・費用の上限・品質管理は platform#127 で決めて書く。
- C26（みんなの声）の「続きの投稿への注記」は、派生先の話題を使って求める作りになっている。話題を外すため、求め方を見直す（Deferred）。
- C25（わかってきたこと）：表示は説・価値のまま。問いの見せ方は別に決める。
- 画面・コンポーネント・機能の一覧（S・C・F）への影響：ID の追加・廃止・名前の変更はない（DEC-0011 決定6 の確認）。

## Deferred / Open Issues

- 派生の方法（器の Discovery から遠いわかってきたことを、どう派生の候補にするか）
- 発見の仮説の保持の方法（わかってきたことの束をいつ作り、保存するか）
- C26 の「続きの投稿への注記」の求め方
- 問いの画面での見せ方と、回答済み・未回答の扱い
- 別名の候補の持ち方（#82 と合わせる）
- 対立する説をつなぐ関係（DEC-0012 の Deferred から引き継ぐ）
- 主張・わかってきたことの名前の最終決定（DEC-0009 決定11 と合わせる）
- 解析の単位・タイミング・モデルの分担・費用の上限・品質管理（platform#127）

## Revisit Conditions

- 会話を区切って見せたい、話の流れを派生や「続きの投稿への注記」の材料にしたい、という要求が出た場合（話題を必須ではない形で戻すことを検討する）
- 主張を保存する費用・運用の負担が、取り出し直す費用を上回ることが分かった場合
- 説・価値の2つでは、画面や判断材料で扱いきれない種類のわかってきたことが多く出た場合
- 除外の規則で、出してはいけないものが表示される、または除きすぎで価値のあるわかってきたことが大きく減る場合
