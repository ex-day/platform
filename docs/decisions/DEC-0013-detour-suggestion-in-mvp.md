# DEC-0013: 寄り道の提案を MVP に入れ、Discovery への行き方をあとから足せるようにする

## Status

Proposed（方針は人間が 2026-10-09 に決定。本文は Claude が作成し、レビュー待ち）

## Date

2026-10-09

## Context

MVP スコープ（`ex-day_mvp_scope.md` 13節）では、次を MVP 対象外・将来拡張としていた。

- 天候・移動手段・空き時間等を考慮した Discovery
- 出張・旅行等での寄り道提案
- 高度なナビゲーション・経路提案

要求仕様の Scenario 01（出張帰りに新しい体験を探す）も、MVP の代表シナリオには入れていなかった。

ex-day/poc の Issue #5・#6 で、寄り道の提案が作れるかを確かめた（PR #21・#22）。

- 時刻表を使わず、国土数値情報 N02 と路線ごとの表定速度で、「残り時間のうちに寄り道できる駅」を出せた。1回の問い合わせは約0.6秒（#5）
- その駅のまわりの場所と、ユーザーの興味を突き合わせ、遠回りの小さい順に並べると、帰り道の途中で降りるだけの場所（例：新大阪から新横浜への帰りに小田原城）が上に来て、寄り道らしい提案になった（#6）
- 提案の質を決めるのは、到達圏の計算ではなく Discovery の中身だった。わかってきたこと（説・価値）を持つ Discovery は興味とよく結び付き、名前しかない場所は外れが多かった（#6）
- 駅から場所までは直線距離（800m〜2km）で代わりに測った。実際には、施設ごとにバス・タクシー・おすすめの行き方がある。どの駅を代表にするか、誰がどう整備するかは未決だった（#6、PR #22 のレビュー）

## Decision（案）

### 1. 寄り道の提案を MVP に入れる

「今いる場所（出発地）と、帰る場所・帰りの期限から、途中で寄れる Discovery を出す」を MVP に入れる。ほかの地図・観光サービスとの、はっきりした違いになるため。

- 移動時間は、時刻表を使わず、平均の表定速度で「だいたい○○分」として出す。乗り継ぎの詳細は乗換案内のサービスに任せ、リンクで渡す
- 誤差は「行けない」側に寄せる
- 並べ方は、興味との近さに加えて、遠回りの小さいものを上にする。余裕の少なすぎるものは出さない
- 寄り道の提案のために、Discovery の中身（わかってきたこと、とくに価値）が「そこで何ができるか・何が感じられるか」が分かる形で育つことを重視する（F02 への要求）

### 2. Discovery への「行き方」を、あとから誰でも足せるようにする

Discovery に、行き方（どの路線のどの駅から、何で、何分）を持たせる。

- 書き方：「○○線○○駅からバス○分」のような形。駅、手段（徒歩・バス・タクシー等）、所要時間（分）、ひとこと（任意。例：「本数が少ないので注意」「坂がきつい」）
- 駅は、「川崎」のように入れると、駅の候補（路線名・事業者つき。例：JR 川崎、京急川崎）が出て、そこから選ぶ形にする。路線は選んだ駅から決まるので、利用者が路線を書く必要はない。選んだ駅は駅マスタの station_id で持つ
- **投稿のときの必須にはしない。** 投稿の入力の負担を増やさない（DEC-0004・DEC-0005）。行ったことのある人、気がついた人が、あとから S03（Discovery 詳細）で足す
- **直すのではなく、足していく。** 1件ずつ、登録した人のものとして残す（MVP スコープの「編集ではなく知識を追加する」）。人が登録したものは AI の解釈で書き換えない（DEC-0009 決定1の「人間が作ったもの」の層）
- 登録した本人は、自分の行き方を直せる・消せる
- 他の人の行き方には、「この行き方で行けた」「今は違うかも」で応えられる。違う行き方を知っている人は、別の1件として足す
- 悪質なものは、既存の「暫定公開＋事後チェック」の通報の流れに乗せる

### 3. 行き方がなければ、自動で代わりを出す

行き方は、なくても寄り道の提案は動く。

| 出どころ | 扱い |
|---|---|
| 運営が登録（初期の Discovery。#57） | 確かさが高い |
| ユーザーの登録（S03） | 「行けた」の数と新しさで、見せる順を決める |
| 会話から取り出したもの（F02） | 「寄せられている情報」として、支えの厚さで扱う（DEC-0012） |
| 自動（場所から近い駅、直線距離） | 何もないときの目安。「目安」と分かるように見せる |

どれを代表として提案に使うかの具体的なルールは、後続で決める。

### 4. ex-day の駅マスタを持つ

行き方も、寄り道の提案も、駅を ex-day 独自の変わらない番号（station_id）で指す。

- 中身は国土数値情報 N02 から作る。N02 の駅コード・グループコードは年度版で変わりうるので、年度ごとの対応表で station_id に名寄せする
- 到達圏の計算と ex-day 本体の間は、station_id でやり取りする。経路計算の内部の番号は外に出さない

## Reason

- 寄り道の提案は、ex-day の「場所・時間を起点に、知らなかった何かと出会う」をそのまま形にしたもので、ほかのサービスとの違いを示しやすい
- PoC で、時刻表なしの粗い計算でも、実用の速さで、寄り道らしい提案が出せることが分かった
- 行き方は、行った人がいちばんよく知っている。会話に出ないことも多いので、行った人が書き残せる場所があると集まりやすい。「苦労した」情報は、寄り道を考える人にとって役に立つ
- 直す形にすると、荒らしや書き換え合戦の手当てが要る。足していく形なら、登録は人のものとして残り、どれを見せるかは ex-day がまとめて決められる。わかってきたことの「支えの厚さ」と同じ考え方で扱える
- 行き方がなくても自動の目安で動くので、初期に人手がなくても始められる

## Alternatives

- **寄り道の提案を MVP の後にする案**：ほかのサービスとの違いを、最初から示せないため採用しない
- **時刻表を使って正確に出す案**：出発時刻が決まらない探し方（来週の予定など）で候補が漏れ、手間も大きいため採用しない。時刻表を使うなら、行き先を決めたあとの S03 の行程の側（リンクで済ませてよい）
- **行き方を投稿のときの必須にする案**：投稿の負担が増えるため採用しない
- **行き方を1つの欄にして、誰でも書き換えられるようにする案（Wiki のような形）**：荒らし・書き換え合戦の手当てが要り、「編集ではなく知識を追加する」に反するため採用しない
- **運営だけが行き方を整備する案**：Discovery が増えると追いつかないため採用しない（初期の Discovery では使う）
- **自動の目安だけにする案**：施設ごとのバス・タクシー・おすすめの行き方を表せないため採用しない（何もないときの代わりとして使う）
- **国土数値情報のコードをそのまま駅の番号にする案**：年度版で変わりうるため採用しない

## Consequences

### MVP スコープ（`ex-day_mvp_scope.md`）

- 13節の「出張・旅行等での寄り道提案」を MVP 対象外から外す。「天候・移動手段・空き時間等を考慮した Discovery」のうち、移動時間・空き時間は寄り道の提案として MVP に入る（天候は対象外のまま）。「高度なナビゲーション・経路提案」は対象外のまま（リンクで渡す）
- 15節の代表シナリオに、Scenario 01 を加えるか検討する

### Domain・Logical Entity

- Discovery の「行き方」を足す。出どころ（運営／ユーザー／会話／自動）と、層（人が登録したもの／見立て／採用した構造）を明記する
- 駅マスタ（station_id）を足す
- 行き方への反応（「行けた」「今は違うかも」）を、Reaction の対象として扱うかを決める

### UI

- S03（Discovery 詳細）に、行き方の表示と登録を足す。新しいコンポーネントになる見込み（番号は人間がレビューで決める。DEC-0011）
- 寄り道の条件（出発地、帰る場所、帰りの期限、滞在時間）を入れる画面・コンポーネント。S01・S02 のどこに置くかは画面設計で決める
- 駅の指定は、入力した文字から候補（路線名・事業者つき）を出して選ぶ形、または現在地から近い駅を出す形（同じ名前の駅があるため）。行き方の登録と、寄り道の条件の入力で、同じ部品を使う
- 画面・コンポーネント・機能の一覧への影響：新しいコンポーネントと、寄り道の提案の機能（F）が増える見込み（DEC-0011 決定6の確認）

### F02

- 会話から行き方（どの駅から、何で、何分）を取り出すことを、Finding を取り出す PoC の対象に加える
- わかってきたこと（とくに価値）を、「そこで何ができるか・何が感じられるか」が分かる形で取り出す

## Deferred / Open Issues

- 複数の行き方があるとき、どれを代表として提案に使うか（出どころの優先順、「行けた」の数、新しさ）
- 自動の目安の決め方（PoC #6 は駅から直線で800m〜2km。#23 で道のり（N13）にし、片道10分＋余裕・上限25分にした。駅の代表点はホームの重心のままで、改札・出入口にするのは後続）
- 到達圏の API が返す余裕の意味（場所で使える時間の合計か、滞在時間を引いた残りか）。PoC では、滞在時間を「駅を出て戻るまでを含む寄り道の枠」として扱っている（PR #24 のレビュー）
- 行き方の項目の細かさ（バス停の名前、運行の本数などを持つか）
- 寄り道の提案の精度（長距離の特急、新快速、乗換の時間、終電）。計算の仕組みは DEC-0014
- 湖・川・散歩道のような広がりのある場所の扱い（範囲で持つ）
- 駅マスタの作り方と、年度ごとの名寄せの運用

- 利用者による「行き方」の登録を MVP でどこまで要るとするか。範囲のある Discovery の入口・到達点に、公式の施設のサイトや OSM の入口の情報を使えるかの検証の結果で判断する（DEC-0014 の Deferred）

## Revisit Conditions

- 行き方がほとんど集まらず、自動の目安だけでは提案の質が足りない場合
- 行き方の登録で、荒らしや誤りが運用で抑えきれない場合
- 粗い移動時間の誤差が大きく、「行けると言われたのに間に合わない」が多い場合
