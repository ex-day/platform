## Context

MVP スコープ（`ex-day_mvp_scope.md` 13節）では、次を MVP 対象外・将来拡張としていた。

- 天候・移動手段・空き時間等を考慮した Discovery
- 出張・旅行等での寄り道提案
- 高度なナビゲーション・経路提案

要求仕様の Scenario 01（出張帰りに新しい体験を探す）も、MVP の代表シナリオには入れていなかった。

ex-day/poc の Issue #5・#6 で、寄り道の提案が作れるかを確かめた（PR #21・#22）。

- 時刻表を使わず、国土数値情報 N02 と路線ごとの表定速度で、「残り時間のうちに寄り道できる駅」を出せた。1回の問い合わせは約0.6秒（#5）
- その駅のまわりの場所と、ユーザーの興味を突き合わせ、遠回りの小さい順に並べると、帰り道の途中で降りるだけの場所（例：新大阪から新横浜への帰りに小田原城）が上に来て、寄り道らしい提案になった（#6）
- 提案の質を決めるのは、到達圏の計算ではなく Discovery の中身だった。わかってきたこと（説・価値）を持つ Discovery は興味とよく結び付き、名前しかない場所は外れが多かった（#6）
- 駅から場所までは直線距離（800m〜2km）で代わりに測った。実際には、施設ごとにバス・タクシー・おすすめの行き方がある。どの駅を代表にするか、誰がどう整備するかは未決だった（#6、PR #22 のレビュー）

## Decision

### 1. 寄り道の提案を MVP に入れる

「起点（場所）と使える時間、終点から、寄れる場所と、その上の Discovery を出す」を MVP に入れる（画面は S12 `/detour`。DEC-0022）。ほかの地図・観光サービスとの、はっきりした違いになるため。

- **条件**：起点（場所）、使える時間（分）、終点（なし＝片道／起点に戻る＝往復／別の場所＝帰り道）。時刻では聞かない（MVP スコープ 4節。2026-11-19 に、以前の「帰る場所・帰りの期限」から改めた）
- **対象**：寄れる場所と、その上の Discovery（DEC-0020 決定11）。Discovery のない場所も「声のない場所」として出す
- **結果**：寄れる場所ごとに「そこで何分過ごせるか」（寄れる時間＝使える時間 −（起点からそこまで）−（そこから終点まで））を出し（終点ごとに：往復は「そこから起点まで」、帰り道は「そこから終点の場所まで」を引く。片道（終点なし）は最後の項を 0 とし、寄れる場所で旅程を終える（2026-11-19、PR #162 のレビュー））、寄り道先のまとまり（「○○のあたり」）で束ねる（S12）
- 移動時間は、時刻表を使わず、平均の表定速度で「だいたい○○分」として出す。乗り継ぎの詳細は乗換案内のサービスに任せ、リンクで渡す
- 誤差は「行けない」側に寄せる
- 並べ方の種類（過ごせる時間の長い順、発見の多い順など）は S12 で決める。PoC（poc #6）の「興味との近さに加えて、遠回りの小さいものを上にする」は、その候補の一つとして引き継ぐ。寄れる時間の少なすぎるものは出さない（下限は F06 の設計で決める（#161））
- 寄り道の提案のために、Discovery の中身（わかってきたこと、とくに価値）が「そこで何ができるか・何が感じられるか」が分かる形で育つことを重視する（F02 への要求）

### 2. 場所への「行き方」は、あとから足せるデータの形にする

**MVP で決めること**：場所に、行き方（どの路線のどの駅から、何で、何分）を、あとから何件でも足せるデータの形で持たせる。

- 項目：駅（駅マスタの station_id）、主な手段（徒歩・バス・タクシー等）、所要時間（分）、着く先（施設、または到達点。決定5）、ひとこと（任意）、元の書き方（任意。例：「○○駅からバス10分、○○停留所下車、徒歩5分」）、出どころ・確かめた状態（下）、層（人が登録したもの／見立て／採用した構造。DEC-0009）
- **所要時間は、駅を出てから着く先に着くまでの合計**にする。MVP では「主な手段＋合計の分数」に丸めて持つ。例：「駅からバス10分、○○停留所下車、徒歩5分」は、主な手段バス・合計15分。バス停の名前や区間ごとの分数は、元の書き方として残し、区間を分けて持つのは後続（Deferred）
- **出どころと、確かめた状態を分けて持つ**（PR #126 のレビュー）。公式サイトは信頼できても、AI で取り出したものは、別の施設・駅・分数を結び付けている可能性があるため
  - 出どころ：運営／公式（施設のサイト）／ユーザー／会話／自動計算
  - 確かめた状態：人が確かめた／機械で取り出した・未確認
  - 出典の URL、取得日・確かめた日
  - 状態：有効／無効（古い・誤り）／取り出しの失敗
- **直すのではなく、足していく形**：1件ずつ、登録したもの（人・取得元）ごとに残す（MVP スコープの「編集ではなく知識を追加する」）。人が登録したものは AI の解釈で書き換えない（DEC-0009 決定1の「人間が作ったもの」の層）
- **投稿のときの必須にはしない**：投稿の入力の負担を増やさない（DEC-0004・DEC-0005）
- 行き方を持つ先は Discovery ではなく場所とする（DEC-0020 決定1。Discovery は場所との関係で位置を持つ。DEC-0020 決定6）
- **MVP の最初の段階**：DB V2 の「行き方の代表の駅」（`place.access_station_place_id`。1つ）で始める。上の項目を何件でも足せる行き方の表は、F06 の設計で決める（#161）

**MVP で決めないこと**：利用者が行き方を登録・編集・反応する UI を MVP に含めるか、含める場合の範囲は、公式の施設のサイト・OSM 等からの自動の取得と、入口・到達点の PoC（DEC-0014 の Deferred）の結果を踏まえて決める。

UI を採用する場合の方針（今の案）：

- 行ったことのある人、気がついた人が、あとから S13（場所のページ）で足す
- 駅は、「川崎」のように入れると、駅の候補（路線名・事業者つき。例：JR 川崎、京急川崎）が出て、そこから選ぶ形にする。路線は選んだ駅から決まる
- 登録した本人は、自分の行き方を直せる・消せる
- 他の人の行き方には、「この行き方で行けた」「今は違うかも」で応えられる。違う行き方を知っている人は、別の1件として足す
- 悪質なものは、既存の「暫定公開＋事後チェック」の通報の流れに乗せる

### 3. 行き方を使う順番と、行き方がないときの自動の代わり

行き方は、なくても寄り道の提案は動く。あるときは、駅からの時間を計算せずに、行き方の分数をそのまま使う（駅までの時間は到達圏の計算、駅から先は行き方）。どの計算の仕組みでも同じように使える（DEC-0014 決定2）。

**公式の情報を積極的に使う。** 施設の公式サイトの「○○駅から徒歩○分」「○○駅からバス○分」は、確かさが高く、安く取れる。AI で取り出したもの（人が確かめる前のもの）も、施設・駅・手段・分数が一意に取れたものは提案に使ってよい。

使う順番（同じ場所・同じ駅に複数あるとき）：

| 順 | 出どころ | 扱い |
|---|---|---|
| 1 | 運営が登録（初期の Discovery。#57）、公式で人が確かめたもの | 確か |
| 2 | 公式で、機械で取り出した・未確認のもの | 提案に使う。ただし、施設・駅・手段・分数が一意に取れたものだけ。取り出しに失敗したとき・あいまいなときの扱いは、公式サイトからの取り出しの PoC（poc #31 の 3）で決める |
| 3 | ユーザーの登録（S13。UI を採用する場合） | 「行けた」の数と新しさで、見せる順を決める |
| 4 | 会話から取り出したもの（F02） | 「寄せられている情報」として、支えの厚さで扱う（DEC-0012） |
| 5 | 自動（到達点、または場所から近い駅と道のり） | 何もないときの目安。「目安」と分かるように見せる |

分数の扱い（「行けない」側に寄せる。決定1）：

- **行き方の分数と自動の計算が大きく食い違うときは、長いほうを使う。ただし、比べるのは起点と終点が同じとき（同じ駅グループから、同じ施設・到達点まで）に限る。** ホーム・改札・駅の出口・施設の入口が違う数字は、そのまま比べられない（PR #126 のレビュー）。公式の「徒歩○分」は、改札からか出口からか、1分を何mで数えたかが施設によって違う。食い違いは記録し、公式の誤りや古い情報を見つける手がかりにする
- **バスは、待ちの目安（おおよそ15分）を足して使う。** 公式の「バス○分」は待ち時間を含まないことが多く、本数も分からないため。乗換の時間も細かくは見ていない（決定1）ので、同じ粗さで余裕を持たせる。**この15分は、取得した事実ではなく計算の決まり（補正値）なので、行き方には書き込まず、別の設定として持ち、あとから変えられるようにする**（PR #126 のレビュー。設定の置き場所は F06 の設計で決める（#161））
- **画面では、バス・乗換を含む時間は「目安」と見せ、待ち時間を含む正確な行き方は乗換案内のサービスで調べるよう案内する**（リンクで渡す。決定1）

### 4. 駅は、利用者から見える場所と、到達圏の計算の中の番号の両方で持つ

- **利用者から見える駅は、場所（種類が駅）とする**（DEC-0020 決定1。DB V2）。起点・行き方の代表の駅・URL の識別子は、場所の識別子で指す
- **到達圏の計算の中では、ex-day 独自の変わらない番号（station_id）を持つ**。中身は国土数値情報 N02 から作る。N02 の駅コード・グループコードは年度版で変わりうるので、年度ごとの対応表で station_id に名寄せする
- station_id と場所（駅）を対応づける。到達圏の計算と ex-day 本体の間は、場所の識別子（または station_id）でやり取りし、経路計算の内部の番号は外に出さない
- 対応の表と、年度ごとの名寄せの運用は、F06 の設計で決める（#161）

### 5. 場所の位置は、代表点・範囲・到達点・行き方で持つ

行き方（決定2）と、位置の情報を分けて持つ。位置を持つ先は Discovery ではなく場所とする（DEC-0020 決定1。Discovery の位置は、場所との関係（役割・順番）で表す。DEC-0020 決定6）。poc #31（PR #32）で、範囲のある場所の入口・到達点を OSM から取れるかを確かめた結果による。

| 持つもの | 数 | 中身 | 出どころの例 |
|---|---|---|---|
| 代表点 | 1 | 地図に出す位置 | 運営・投稿・Wikidata |
| 範囲 | 0〜1 | 公園・湖・境内など、広がりのある場所の形。1つの形は、複数の OSM の物（北と西に分かれた湖など）をまとめた MultiPolygon でよい。もとにした OSM の ID は複数持つ | OSM |
| 到達点 | 0以上 | たどり着く地点。種類（確かな入口／推定の到達点）と、手段（徒歩・車・バス）を持つ | OSM の入口の印（確かな入口）、OSM の歩ける道と範囲の境界の交わり・範囲の端（推定）、公式、投稿 |
| 行き方 | 0以上 | 駅 → 場所の、手段と分数（決定2） | 公式・運営・投稿・会話・自動 |

- **行き方**は「この駅からなら何分」という、寄り道の計算にそのまま使える答え。**到達点**は「どこに着くか」という地点で、行き方が無いときに自動で時間を出す材料
- 到達点と行き方は、**手段**を持つ。今は鉄道＋徒歩だけだが、将来のバス（到達点は停留所）・車（到達点は駐車場）も同じ形で受ける
- **推定の到達点は、確かな入口と分けて扱う**（poc PR #32 のレビュー）。道との交わりには、フェンスで仕切られた道や外周に沿う道も入るため
- 範囲は、同じ Wikidata の ID に複数の OSM の範囲があるとき、最も広い1つだけを採らない（poc PR #32 のレビュー）。まとめて1つの範囲にし、もとの ID を残す
- バスの行き方の「着く先」は、降りた停留所ではなく施設（または到達点）にする。停留所から先の歩きは、行き方の合計の分数に含める（決定2）
- どれも、到達圏の計算の仕組み（DEC-0014）に依らない。pgRouting でも R5 でも、到達点を行き先にして時間を出せる
- **MVP の最初の段階**：DB V2 の場所は、形（地点・エリア・経路）を1つ持つ（`place.spatial_type`・`geom`）。代表点・到達点・範囲の元の OSM の ID の持ち方は、F06 の設計で決める（#161）

## Reason

- 寄り道の提案は、ex-day の「場所・時間を起点に、知らなかった何かと出会う」をそのまま形にしたもので、ほかのサービスとの違いを示しやすい
- PoC で、時刻表なしの粗い計算でも、実用の速さで、寄り道らしい提案が出せることが分かった
- 行き方は、行った人がいちばんよく知っている。会話に出ないことも多いので、あとから足せるデータの形にしておけば、登録の UI・公式サイト・OSM 等、どの出どころでも同じ形で受けられる。どの出どころを MVP で使うかは、検証の結果で決められる
- 直す形にすると、荒らしや書き換え合戦の手当てが要る。足していく形なら、登録は人のものとして残り、どれを見せるかは ex-day がまとめて決められる。わかってきたことの「支えの厚さ」と同じ考え方で扱える
- 行き方がなくても自動の目安で動くので、初期に人手がなくても始められる

## Alternatives

- **寄り道の提案を MVP の後にする案**：ほかのサービスとの違いを、最初から示せないため採用しない
- **時刻表を使って正確に出す案**：出発時刻が決まらない探し方（来週の予定など）で候補が漏れ、手間も大きいため採用しない。時刻表を使うなら、行き先を決めたあとの S03 の行程の側（リンクで済ませてよい）
- **行き方を投稿のときの必須にする案**：投稿の負担が増えるため採用しない
- **行き方を1つの欄にして、誰でも書き換えられるようにする案（Wiki のような形）**：荒らし・書き換え合戦の手当てが要り、「編集ではなく知識を追加する」に反するため採用しない
- **運営だけが行き方を整備する案**：Discovery が増えると追いつかないため採用しない（初期の Discovery では使う）
- **自動の目安だけにする案**：施設ごとのバス・タクシー・おすすめの行き方を表せないため採用しない（何もないときの代わりとして使う）
- **国土数値情報のコードをそのまま駅の番号にする案**：年度版で変わりうるため採用しない

## Consequences

### MVP スコープ（`ex-day_mvp_scope.md`）

- 寄り道を MVP に入れた（反映済み。MVP スコープ 4節。代表のシナリオ「3時間の寄り道」も入った）。天候を考えた提案、高度なナビゲーション・経路提案は対象外のまま（リンクで渡す）
- 4節の判断待ち「DEC-0013・DEC-0014 の Accepted の扱い」は、2026-11-19 に Accepted にした（本 DEC と DEC-0014）

### Domain・Logical Entity

- 論理設計の Place に「行き方」がある（反映済み。論理設計 4.2節）。DB V2 は行き方の代表の駅（`place.access_station_place_id`）だけを持つ
- （F06 の設計で決める（#161））場所の「行き方」を、何件でも足せる形で持つ。出どころ（運営／ユーザー／会話／公式サイト・OSM 等からの取得／自動）と、層（人が登録したもの／見立て／採用した構造）を明記する
- （F06 の設計で決める（#161））到達圏の計算の中の駅の番号（station_id）と、場所（駅）との対応
- （F06 の設計で決める（#161））場所の位置を、代表点・範囲・到達点・行き方で持つ（決定5）。到達点と行き方は手段を持つ。到達点は種類（確かな入口／推定の到達点）を持つ。行き方は、主な手段・合計の分数・着く先・元の書き方、出どころ・確かめた状態・出典の URL・取得日・確かめた日・状態（有効／無効／取り出しの失敗）、自動の計算との食い違いを持てる。範囲は MultiPolygon と、もとにした OSM の ID（複数）を持つ。バスの待ちの目安は行き方とは別の設定
- （UI を採用する場合の後続候補）行き方への反応（「行けた」「今は違うかも」）を、Reaction の対象として扱うかを決める

### UI

- 寄り道の画面は S12（`/detour`。DEC-0022 決定5）。条件は起点・使える時間・終点（反映済み）。計算は F06（寄り道の到達圏）
- （MVP で確定）S13（場所のページ）に、行き方の表示を足す（自動の目安を含む）。S12 の寄れる場所のカードにも行き方を出す
- （UI を採用する場合の後続候補）S13 に、行き方の登録・編集・反応を足す。新しいコンポーネントになる見込み（番号は人間がレビューで決める。DEC-0011）
- （MVP で確定）起点の指定は、入力した文字から駅・場所の候補（駅は路線名・事業者つき）を出して選ぶ形、または現在地から近い駅に置き換える形（同じ名前の駅があるため。座標は URL に出さない。DEC-0022 決定5）。行き方の登録の UI を採用する場合は、同じ部品を使う

## Revisit Conditions

- 行き方がほとんど集まらず、自動の目安だけでは提案の質が足りない場合
- 行き方の登録で、荒らしや誤りが運用で抑えきれない場合
- 粗い移動時間の誤差が大きく、「行けると言われたのに間に合わない」が多い場合
