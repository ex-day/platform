# DEC-0012: AIによる会話の解析の原則を定める（不確かさを許し、後から直せる設計にする）

## Status

Proposed（方針は人間が 2026-10-06〜07 に決定。2026-10-31 に、わかってきたことの取り出しの PoC（ex-day/poc#34）の結果を Context に足し、先送りしていた論点を DEC-0015 で決めた。本文は Claude が作成し、レビュー待ち）

## Date

2026-10-07（2026-10-31 改訂）

## Context

DEC-0009で、会話の理解を「話題 → 発見の仮説 → わかってきたこと」の層として定めた。その後、ex-day/poc の Issue #8・#14 で、会話のPostを話題に振り分ける方法を確かめた（PR #15〜#20）。

数字は「まとまりのF」（1に近いほど、人が付けた正解と同じ分け方）。ex-day/poc の main（commit 11db335）の結果ファイルと照合した。

AIを使わない方法（7本・209件。出典：`context/README.md`、`context/results/first_pass_v2_ruri-v3-30m.md`）：

| 方法 | 返信先あり | 返信先なし |
|---|---|---|
| 返信先＋ベクトル＋保留のルール | 0.60 | 0.39 |
| ベクトルで、話題の始まりと続きを見分ける | AUC 0.41 | ― |
| ベクトルで、分岐した返信と分岐していない返信を見分ける | AUC 0.36 | ― |

AIに振り分けさせる方法（人が書いた会話3本・76件、「会話の流れ」の指示。出典：`context/ai_split/results/score.md`）：

| 渡し方 | モデル | 返信先あり | 返信先なし |
|---|---|---|---|
| 会話の全文を一度に渡す | GPT-5.6 Sol | 0.96 | 0.92 |
| 会話の全文を一度に渡す | Claude Sonnet | 0.87 | 0.84 |
| 10件ずつ順に渡す | GPT-5.6 Sol | 0.80 | 0.79 |
| 10件ずつ順に渡す | Claude Sonnet | 0.78 | 0.70 |
| 10件ずつ順に渡し、20件で一度振り分け直す | GPT-5.6 Sol | 0.84 | 0.80 |
| 10件ずつ順に渡し、20件で一度振り分け直す | Claude Sonnet | 0.71 | 0.76 |

- 「でも可」の話題を当たりにしない厳しいFでは、全文・返信先ありで GPT-5.6 Sol 0.88、Claude Sonnet 0.89 だった。
- AIと人では、話を分ける軸が違った（AIは中身の種類、人は場所も軸にする）。
- 各条件1回ずつの結果で、揺れと費用は測っていない。人が書いた会話は3本だけである。

ここから、AIの解析結果だけで、会話の理解・話題の変化・似ていることの判定を、完全に自動で高い精度にすることは、今の時点では難しいと判断した。

その後、ex-day/poc#34（PR ex-day/poc#35）で、会話から「わかってきたこと」を、根拠の Post の id 付きで取り出す方法を確かめた（会話4本。出典：ex-day/poc の `context/extract/README.md` 途中経過1〜7）。

- 発言ごとの主張を根拠の Post の id 付きで取り出し、それを束ねてわかってきたことにする2段の形で、拾いたいわかってきたことは Claude Sonnet 5.5 で 12／13・11／11、Claude Haiku 5.5 で 11／13・8.5／11、GPT-5.6 Luna で 8.5／13・9.5／11（会話2本。AI による照らし合わせ）
- 主張の根拠が、人の付けた正解の話題をまたいだのは99件中1件だった
- 出してはいけないもの（危険な情報、店の評価、私人についての情報など）は、3つのモデルとも12件中0件の漏れだった（会話2本）
- 一方で、確かさを落として言い切る（「咲いていた気がする」→「咲いていた」）、説を落とす、見逃すといった誤りは、どのモデルにも出た
- どれも各条件1回で、揺れは測っていない

この結果を「AIではできないので妥協する」とは扱わない。完全な自動化のために精度を追うより、不確かさを扱える設計にするほうが、今のAIの能力にも、将来の能力の向上にも合わせやすい、という設計の判断として扱う。

## Decision

### 1. 完全な自動化を、MVPの成立条件にしない

AIによる会話の理解の完全な自動化を、MVPの成立条件にしない。AIの推定には、漏れと誤りがあることを前提とする。

会話の解析の目的は、会話を完全に理解・分類することではない。投稿された会話から、Discoveryを育てるために使える情報を取り出し、その根拠となるPost・資料との関係を持つことである。

### 2. 判断できないものは、不明のまま残す

AIが判断できない情報は、無理に分類・関連付けをしない。未分類・不明の状態を許す。後のPostで文脈がはっきりしたとき、解析し直したときに、後から関連付けられればよい。

### 3. ユーザーが明示した関係を、AIの推定より強く扱う

| 出どころ | 扱い |
|---|---|
| ユーザーの明示的な返信 | 強い関係 |
| 返信なし。AIが文脈から推定 | 推定された関係 |
| 判断できない | 持たない（不明） |

- 返信は、AIの解析を助けるためだけの情報ではない。投稿者自身が「この情報は、この発言に対するものだ」と明示した一次情報として扱う。
- 返信は必須にしない。
- 返信で確かになるのは「このPostは、あのPostへの応答である」までである。同じ話であることの証拠にはしない（返信が話の分かれ目になることがある）。
- 資料についても同じとする。資料の帰属はDiscoveryのまま変えず（DEC-0005 決定8）、提供時のPostの本文と返信先を、「投稿者がその資料をどの文脈で出したか」の一次情報として使う。Postを伴わない資料は、「何を示す資料か不明」を許す。

### 4. わかってきたこと（Finding）は、事実の認定ではない

わかってきたことは、ex-dayによる事実の認定ではなく、「会話から寄せられている情報・説・価値」として扱う。

- 見せ方：「この場所には江戸時代まで〇〇があった」ではなく、「〜という情報が寄せられています」。
- AIの役割は真偽の判定ではなく、会話の中で何が語られているかを取り出すことである。
- 支えが厚くなっても、ex-dayが事実と認定した情報にはならない。
- 将来、事業者・自治体等の公式の情報を扱う場合は、会話から得たわかってきたこととは別の信頼の段階・情報源として扱うことを検討する。

### 5. AIは根拠の関係を取り出し、支えの厚さはex-dayが計算する

- AIには、わかってきたことと、それを支持する／反するPost・資料の関係を取り出してもらう。判断できないものは返させない。
- AIに確度の数字を返してもらうことは、基本としない。
- 支えの厚さ（1人の発言だけか、独立した複数の人か、資料があるか、反する情報があるか、関係が返信によるものかAIの推定だけか等）は、ex-day側のルールで計算する。重みと閾値は別に決める。
- 支えの厚さは「正しさ」ではない。複数の人が言っていることを、事実の正しさに置き換えない（DEC-0009 決定9の原則を維持する）。
- **「裏付けの有無」の二択を廃止する。** DEC-0009 決定4の「資料（出典）の裏付けがあるものを知識として扱う」をやめ、支えの厚さ（段階）に置き換える。資料があることは、支えの厚さの材料の1つになる。
- **説へのReactionは、支えの厚さに含めない。** 「そうかも」の数で、説の支えが厚くなることはない。
- 価値へのReaction（「わかる」「行ってみたい」）は、判断材料の「人の支え」として扱う。これは今の方針（DEC-0009 決定7）のまま変えない。
- 根拠の関係は内部で持ち、個人の寄与として見せない（DEC-0009 決定6を維持する）。

### 6. 解析結果は、原本から作り直せるものとして扱う

- Post・返信の関係・資料を原本として持つ。AIの解析結果は、そこから作り直せるものとして扱う。
- MVPの時点で、解析する項目を漏れなく決め切ることを求めない。解析の方式・モデル・指示・項目が変わったら、必要に応じて過去のDiscoveryを解析し直せるようにする。
- 漏れは後から解析し直して足せる。誤った関連付け・統合は、後から訂正・分離できるようにする。

### 7. 2種類の誤りを、分けて扱う

- **見逃し**（似たDiscoveryを見つけられない等）：後から、Discoveryの更新・新しいPost・解析し直し・定期的な照合で見つかればよい。100%見つけることを成立条件にしない。
- **誤った関連付け**（似ていないものを候補にする等）：既存の構造に影響するため、見逃しより慎重に扱う。AIの判断だけで、元に戻せない統合をしない。提案として出す、必要なら人が承認する、統合の後でも分離できるようにする。ユーザーから「関連していないのでは」という報告を受けられる仕組みを検討する。

### 8. 責務の分け方と、AIの呼び出しの回数を、同じものとして考えない

複数の責務を、1回のAIの呼び出しで処理してよい。Functionの分け方は、同じ入力を使うか、分けたときの費用、独立して変えたい・やり直したい処理はどれかを見て決める。

### 9. 条件を、段階的にゆるめられる作りにする

AIの能力が上がったら、返信のない推定の扱い、自動の関連付け、自動の統合などの条件を、段階的にゆるめられる作りを目指す。

## Reason

- PoCで、全Postの振り分けを自動で高い精度にすることは難しいと分かった。精度を成立条件にすると、MVPが成立しない。
- 不明を許さない設計は、AIに無理な推定をさせ、誤った関連付けを増やす。誤った関連付けは、見逃しより直しにくい。
- 返信は、投稿者自身が示した関係であり、AIの推定より根拠が強い。
- わかってきたことを事実として見せると、ex-dayが真偽の責任を負うことになり、既存の原則（「確定」は真実の保証ではない。数を正しさに置き換えない）とも合わない。
- 確度をAIに返させると、モデルや指示が変わるたびに基準が動く。根拠の関係だけを取り出させ、計算をex-day側に置けば、ルールを変えてもAIを呼び直さずに計算し直せる。
- 解析の項目は、後から「これも取り出しておけばよかった」と分かることが多い。原本を持ち、作り直せるようにしておけば、MVPの時点で決め切らなくてよい。

## Alternatives

- **解析の精度を上げて、完全な自動化を目指す案**：PoCの結果から、MVPの成立条件にはできないため採用しない。
- **AIに確度を返させる案**：基準がモデルに依存し、ルールとして説明・調整できないため採用しない。
- **全Postを必ず分類する案**：判断できないPostに無理な分類を付け、誤りを増やすため採用しない。
- **返信を必須にする案**：投稿の負担を増やすため採用しない（DEC-0004・DEC-0005）。
- **解析結果を原本と同じように固定して持つ案**：解析の方式を変えたときに直せないため採用しない。

## Consequences

| 決定4（わかってきたこと） | 定義を「寄せられている情報・説・価値」と明確にする。**「資料の裏付けがあるものを知識として扱う」という二択は廃止し、支えの厚さ（段階）に置き換える。**同一性のルール・版の履歴は変えない |

### Domain・Logical Entity

- ドメイン設計に、本DECの原則を書く（2章または3.5節）。3.5.3節のわかってきたことの定義を直す。
- 論理設計 6A.3節 Finding：定義、根拠の関係（支持する／反する）、解析の版（モデル・指示・解析した時点）を足す。8.3節 Evidence とのまとめ方を決める。
- 論理設計 8.1節 Media：「提供時のPost」を、文脈の一次情報として使うことを書く。帰属は変えない。

### UI・機能

- [F02（投稿後の会話の解析）](../ui/functions/F02-conversation-analysis.md)に、目的と原則を書く。
- C25（わかってきたこと）の文言を、「〜という情報が寄せられています」の立場に合わせる。「見解が分かれている」の表示を検討する。
- 画面・コンポーネント・機能の一覧（S・C・F）への影響：IDの追加・廃止・名前の変更はない（DEC-0011 決定6の確認）。Functionの分け方は、本DECでは決めない。

## Revisit Conditions

- AIの能力が上がり、返信のない推定や自動の関連付けを、強い関係として扱えると確かめられた場合（決定9のとおり、条件をゆるめる）
- 不明のまま残るPost・資料が多く、わかってきたことがほとんど育たない場合
- 支えの厚さのルールが、ユーザーに「ex-dayが正しいと認めた」と受け取られる見せ方になっている場合
- 解析し直しのたびに、わかってきたことが大きく入れ替わり、Reactionの引き継ぎが保てない場合
