- 状態：案。画面の設計（PR #143〜#148）で決めた各画面の項目と操作を、[論理エンティティ設計 v0.2](ex-day_logical_entity_design.md) の Entity・属性に対応させ、DB V2（物理設計）の入力にする
- 根拠：[MVP スコープ v0.4](ex-day_mvp_scope.md)、[画面一覧](screen-list.md)、[コンポーネント一覧](component-list.md)、[機能一覧](function-list.md)、各画面の定義（`docs/ui/screens/`）

- **位置付け**：物理設計に向けた**中間成果物**であり、詳細設計書として維持しない（2026-11-16 の人の判断、PR #149 のレビュー）。画面の項目の定義・テーブル定義・API 設計と重なる細かさまでは掘り下げない。見つかった不足・矛盾は正式な設計書（論理設計、画面・機能の定義、DB 設計）へ反映し、後続の設計が終わったあとは、本書を続けて直す対象にしない

## 1. 使い方

- **2節**：Entity ごとに、どの画面がどの属性を読むか。MVP で要る Entity と要らない Entity を分ける
- **3節**：画面の操作ごとに、何を作る・変えるか、判断の記録が要るか、誰ができるか
- **4節**：保存せずに導くもの（物理設計で写しを持つかを決めるもの）
- **5節**：画面の設計で出てきた、論理設計に足りない・はっきりしないもの
- **6節**：5節の項目を、いつ・どこで決めるか（論理設計だけを見直す工程は設けず、後続の設計で必要になった時点で決める）
- **7節**：公開制御（2〜4節に共通する方針）
- **8節**：DB V2 への引き継ぎ

画面 ID：S01 TOP、S02 探す、S03 Discovery のページ、S09 自分の話、S12 寄り道、S13 場所のページ、S14 会話のページ、S15 企画のページ、S16 企画の作成・編集、S17 企画の一覧、S18 運営の管理。S07・S08（ユーザー）は v0.3 の定義と論理設計 4.1節のまま。

## 3. 書き込み操作

「判断の記録」は Decision を足すか。「権限」はサーバー側で判定する。

**投稿の成立と解析の分離**：機能の欄の「F10 → F05 → F02」は処理の順番であり、全部が終わることを投稿の成立の条件にしない。投稿は F10（確定時の禁止語などのチェックと暫定公開）を通った時点で成立する。F05（地名の照合）・F02（会話の解析）は成立した投稿に対する後の処理で、未完了・失敗によって成立した投稿を失わない（DEC-0005 決定7、MVP スコープ 11節）。同期・非同期などの方式は後続の設計で決める。

| 操作 | 画面・部品 | 機能 | 作る・変えるもの | 判断の記録 | 権限 |
|---|---|---|---|---|---|
| 会話を始める | C27（S01・S03・S13・S15 から） | F10 → F05 → F02 | Conversation、Post。入口が場所を決められるときは PlaceCandidate（出され方＝入口）と PlaceAdoption（主体＝会話を始めた人） | 入口からの採用は要る | ログイン |

## 4. 保存せずに導くもの

物理設計で写し（キャッシュ・集計の表）を持つかは DB V2 で決める。写しを持つ場合の更新の仕方は、次の2つに分ける（2026-11-16 の人の判断、PR #149 のレビュー）。どちらも、公開制御と権限の整合を損なわないことを前提にする（7節）。

- **即時の整合が要るもの**：正本と同じ処理の中で更新する。場所の採用（PlaceAdoption）と判断の記録、そこから導く採用した場所の紐付き・場所未定・問いの回答の状態・候補の表示、公開状態とそれによる表示の可否
- **反映の遅れを許してよいもの**：あとからまとめて更新してよい。返信の数・新しい返信、企画の新しい声、TOP のこのあたりの数字、検索のための情報（SearchProfile）、寄り道の到達圏の事前計算、Discovery の現在状態

下の表の「整合」の欄は、この分け方の案。具体的な方式は DB V2 で決める。

| 導くもの | 導き方 | 使う画面 | 整合 |
|---|---|---|---|
| 会話と場所の採用した紐付き（ConversationPlace） | 採用中・再検討中の PlaceAdoption（対象＝会話、会話の入口の資料、会話の問い） | S09・S13・S14 | 即時 |
| 会話の「場所未定」 | 上の紐付きが0件 | S01・S02（探しています）・S09・S14 | 即時 |
| 候補の表示の「採用」「取り消し」 | その候補を採用した PlaceAdoption の状態 | S14 | 即時 |
| 場所を探す問いの回答の状態 | 回答した問い＝その問いの PlaceAdoption | S14・S09 | 即時 |
| 「このあたりで探している人がいます」・TOP の「探しています」 | 検討中の PlaceCandidate（対象が会話・問い）。新しい場所の案は、位置を含む既存の場所に寄せる | S01・S02・S13・S14（届くところ） | 遅れを許す |
| Discovery の出す位置の場所 | DiscoveryPlace の役割（体験できる場所・始まり） | S01・S03・S12・S13 | 即時 |

## 5. 論理設計に足りない・はっきりしないもの

画面の設計で出てきたもの。扱いは6節のとおり（論理設計だけを見直す独立した工程・先行の PR は設けず、DB V2 や関連する機能の設計で必要になった時点で決め、そのときに関連する論理設計を併せて直す）。「MVP ではやらない」と決めたことは、ここに挙げない。

| 項目 | 出どころ | 案 |
|---|---|---|
| 新しい動きの既読（ユーザーごとに、どこまで確かめたか） | S09 | 運用・画面の都合の情報として物理設計で持つ（論理 Entity にしない）。詳細の画面から戻っただけで消さない |
| 自動で成立した Discovery の「見直した」 | S18・F12 | Decision の判断の種類に「見直し（変更なし）」を足す |
| 通報の対応の状態の種類 | S18・F10 | ContentReport の状態（受付・確認中・対応済み・対応しない など）を F10 で決める |
| 非公開の理由の分類（作った人に出す） | S09・S15 | 公開状態を変えた Decision の理由の分類から出す。分類の一覧は F10 で決める |
| 通報の理由の分類 | C39 | 規約違反・権利侵害・安全上の問題など。内容への異論は含めない |
| 統合された Place・Discovery を開いたときの統合先 | S03・S13 | Place は状態と統合先、Discovery は DiscoveryRelation（統合）から。Place の統合先の持ち方を論理設計で明記する |
| 入口＝Discovery・企画の項目（Discovery）の会話で採用する場所 | S03・S15 | 出す位置の場所。複数・一意に決められないときは検討事項（論理設計 4.3節） |
| 解析の状態（反映が遅れていること） | S14 | 運用の記録（DEC-0018）から出す。論理 Entity にしない |
| 起点の既定のエリア | S01・S02・S12 | 始める地域（設定）、またはログインしている人の UserInterest（興味のある地域） |
| TOP の並びを同じセッション・その日のうちに保つための種 | S01 | 非永続（日付などを種にする）。保存しない |
| 寄り道の到達圏の事前計算 | F06 | 運用・実装のデータ（論理設計 14節）。駅・路線・表定速度とともに物理設計で持つ |
| 企画そのものの会話をいつ作るか | S15・S16 | **決定**（2026-11-16 の人の判断、PR #149 のレビュー）：最初の発言のときに作る。Project 1 : 企画そのものの Conversation 0..1 とし、Conversation と最初の Post は同じトランザクションで作る。論理設計 4.6節と関係図を合わせて直した。同時に投稿されたときの重複を防ぐ方法は DB V2 で検討する |

## 6. 後続の設計への引き継ぎ

5節の項目の扱いは次のとおり（2026-11-16 の人の判断、PR #149 のレビュー）。

- **論理設計だけを見直す独立した工程・先行の PR は設けない**。後続の設計で不足・矛盾が見つかったら、そのときに関連する論理設計を併せて直す
- **決めたもの**：企画そのものの会話は最初の発言のときに作る（論理設計を併せて直した）
- **DB V2 や関連する機能の設計で、必要になった時点で決めるもの**：「見直し（変更なし）」の判断の種類、Place の統合先の持ち方、通報の対応の状態・理由の分類、非公開の理由の分類、既読、解析の状態、起点の既定のエリア、TOP の並びの種、寄り道の到達圏の事前計算、企画そのものの会話の同時投稿の重複防止
- **会話を始める機能の設計で扱うもの**：Discovery・企画の項目（Discovery）を入口とする会話で、出す位置の場所が複数あり、場所を1つに決められない場合
- 「MVP ではやらない」と決めたこと（企画を閉じる機能とその状態の持ち方など）は未決定の事項ではない。新しく必要になるまで再検討せず、将来その機能を足すときに設計する

## 7. 公開制御（2〜4節に共通）

集計・導出、AI が作る要約などを通して、非公開の情報が意図せず見えないようにする（2026-11-16 の人の判断、PR #149 のレビュー）。

- 検索（SearchProfile）、返信の数・新しい返信、企画の新しい声、このあたりの数字、探しています、わかってきたこと・要約などは、**公開状態と、見ている人の権限を考えて**出す。一般のユーザーに対しては、非公開の会話・Post・Discovery・企画を数・要約・検索の結果に含めない
- 自分の非公開の Post・企画は、本人には見える（S09・S15）。運営は運営の権限で見られる（画面一覧「運営の権限」）
- 非公開になった Post を材料にして作られた見立て（Finding・要約）や検索のための情報は、作り直すか、出さないようにする。具体的な再集計・再解析の方式は後続の設計で決める
- 写しを遅れて更新するもの（4節）でも、公開状態が変わったことによる表示の可否は遅らせない

## 8. DB V2 への引き継ぎ

- 今の DB（[DB 設計 v0.1](ex-day_db_design.md)、`db/migration/V1__*`）は v0.1 の論理設計（Discovery を器とする形）に基づくので、2.1節の Entity で作り直す
- 「いずれか1種類を指す」関係（会話の入口、企画の項目の指す先、場所の候補の対象と候補の場所、場所の採用の対象、Reaction の対象、通報の対象）は、汎用の ID に決めず、整合性と参照の制約を比べて決める（論理設計 12節）
- 3節の「判断の記録が要る」操作は、データの変更と Decision の追加を1つの処理（トランザクション）で行う
- 4節の導くもののうち、一覧・TOP でよく使うもの（返信の数、場所未定、出す位置の場所、探しています）は、写しを持つかを性能と整合の面から決める
- 座標を URL に出さないため、Place・Discovery・企画・会話には画面・URL に出す識別子を持たせる（内部の連番は出さない）
